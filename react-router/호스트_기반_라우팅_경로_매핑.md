# 한 SPA를 두 도메인에서 쓰기: 호스트 기반 라우팅과 경로 매핑 (React Router)

기존 웹 프로젝트 안에 **경로 접두어로 분리해 둔 하위 화면 묶음**을, 별도 도메인으로 접속했을 때는 **그 도메인에 맞는 경로**로 보여 주는 방법 정리.
프로젝트를 새로 만들지 않고 기존 SPA 하나를 그대로 재사용하는 게 목표.

> 배포·DNS·인증서·API 연결 등 전체 흐름은 [프론트엔드 배포와 도메인 연결](../frontend-deploy/프론트_배포와_도메인_연결.md) 참고.

> 표기 규칙: `<...>` 는 프로젝트마다 다른 값으로 바꿔서 사용
> - `<기존 도메인>`: 원래 서비스 도메인
> - `<신규 도메인>`: 하위 화면 묶음만 보여 줄 새 도메인
> - 예시 접두어 `/sub`, 예시 화면 `intro`·`verify`·`done` 은 설명용 이름
> - React Router v6 data router(`createBrowserRouter`) 기준

---

## 한눈에 보기

| | 내용 |
|---|---|
| 상황 | 기존 라우트는 `/home`, `/login` … / 하위 묶음은 `/sub/intro`, `/sub/verify` … 처럼 접두어가 붙은 절대경로 |
| 원하는 것 | `<신규 도메인>` 으로 접속하면 주소창엔 `/sub` 없이, 화면은 하위 묶음을 보여 줌 |
| 주의 | 경로가 **1:1로 대응하지 않는다.** 예: 신규 도메인의 첫 화면 `/` 는 `/sub/home` 이 아니라 `/sub/intro`. 이름이 다른 화면도 있음 |
| 흔한 오답 1 | 인프라 리다이렉트 → 주소창에 `/sub` 가 그대로 보임 |
| 흔한 오답 2 | `basename="/sub"` → basename 은 URL에 **있는** 접두어를 떼는 기능이라, 오히려 주소창에 `/sub` 가 붙음 |
| 흔한 오답 3 | 하위 폴더의 index 만 따로 배포 → SPA는 라우터·컴포넌트·번들이 하나로 묶여 있어 폴더만 떼어 올릴 수 없음 |
| 흔한 오답 4 | "앞의 `/sub` 만 잘라내기" → 경로가 1:1이 아니면 첫 화면부터 틀어짐 |
| 해결 | 같은 빌드를 두 도메인에 연결하고, **경로 매핑표 한 장**으로 라우트 등록과 이동을 모두 변환 |
| 이름 | 호스트 기반 라우팅(host-based routing) + 경로 매핑(path mapping) |

## 1. 선택지 비교

| 방법 | 주소창 | 누가 처리 | 메모 |
|---|---|---|---|
| **리다이렉트** `<신규 도메인>/` → `<신규 도메인>/sub/intro` | `/sub/...` 보임 | 인프라 | 제일 간단. 접두어가 보여도 괜찮으면 이걸로 충분 |
| **서버 리라이트(리버스 프록시)** | 접두어 없음 | 인프라 + 프론트 | 서버가 경로를 바꿔도 SPA 라우터는 **브라우저 주소**를 보고 매칭한다. 결국 프론트 라우터도 손봐야 해서 이점이 적음 |
| **호스트 기반 라우팅 + 경로 매핑 (이 문서)** | 접두어 없음, 경로도 자유롭게 | 프론트 (인프라는 도메인 연결만) | 앱 안에서 해결. 매핑표 하나로 관리 |

> 리다이렉트는 "URL을 바꿔서 다른 곳으로 보내는 것", 이 문서의 방법은 "URL은 그대로 두고 그 자리에 다른 화면을 그리는 것". 이동이 없다.

---

## 2. basename 과 무엇이 다른가

예전에 쓴 basename 은 방향이 반대다.

| | basename | 호스트 기반 라우팅 |
|---|---|---|
| 상황 | 앱이 `<다른 도메인>/우리앱/` 처럼 **하위 경로에 얹혀** 배포됨 | 앱이 도메인 **루트**에 배포됨 |
| 주소창 | `/우리앱/login` (접두어가 **실제로 있음**) | `/verify` (접두어 **없음**) |
| 라우터가 하는 일 | URL 앞의 `/우리앱` 을 떼고 나머지로 매칭 | 라우트 정의 쪽을 신규 도메인용 경로로 바꿔 등록 |
| 경로 대응 | 접두어만 다르고 나머지는 같음 | 화면마다 다르게 지정 가능 |

basename 은 없는 접두어를 만들어 주지 않고, 화면별로 다른 경로를 붙여 주지도 못한다.

## 3. 인프라 요청

리다이렉트·리라이트는 필요 없다.

1. `<신규 도메인>` 을 기존과 **같은 빌드 산출물**에 연결
2. 모든 경로 요청에 `index.html` 을 반환 (SPA fallback)

## 4. 핵심: 경로 매핑표

경로가 1:1이 아니므로 규칙(접두어 자르기)으로 계산하지 않고 **표로 적는다.** 이 표 한 장이 기준이다.

| 앱 라우트 (기존 도메인) | 신규 도메인 | 메모 |
|---|---|---|
| `/sub/intro` | `/` | 신규 도메인 첫 화면 |
| `/sub/verify` | `/verify` | 경로 같음 |
| `/sub/terms/:type` | `/terms/:type` | 파라미터 있는 경로 |
| `/sub/complete` | `/done` | 이름이 다른 경우 |
| `/sub/home` | (없음) | 신규 도메인에선 쓰지 않는 화면 → 표에 안 적음 |

규칙:

- **표에 있는 화면만** 신규 도메인에 등록된다. 없는 화면은 신규 도메인에서 열리지 않는다.
- 왼쪽(앱 라우트)은 기존 코드에 쓰인 경로 그대로. 코드에서는 계속 이 경로로 이동한다.
- 오른쪽(신규 도메인)은 겹치면 안 된다.

## 5. 구현

### 5-1. 매핑표와 변환 함수

```ts
// subHostRoutes.ts
import { generatePath, matchPath } from 'react-router-dom';

export interface PathMapping {
  /** 기존 앱 라우트 경로 (기존 도메인 기준) */
  app: string;
  /** 신규 도메인에서 쓸 경로 */
  sub: string;
}

/**
 * 신규 도메인 경로 매핑표. 여기 없는 화면은 신규 도메인에 노출하지 않는다.
 * 같은 모양의 경로가 겹치면 구체적인 것(`/terms/privacy`)을 위(`/terms/:type` 보다 먼저)에 둔다.
 */
export const SUB_HOST_PATHS: PathMapping[] = [
  { app: '/sub/intro', sub: '/' },
  { app: '/sub/verify', sub: '/verify' },
  { app: '/sub/terms/:type', sub: '/terms/:type' },
  { app: '/sub/complete', sub: '/done' }
];

export const isSubHost =
  window.location.hostname === import.meta.env.VITE_SUB_HOST; // <신규 도메인>

/** 매핑표로 경로를 양방향 변환하는 함수를 만든다. 호스트를 인자로 받아 테스트하기 쉽게. */
export function createPathMapper(table: PathMapping[], enabled: boolean) {
  const convert = (path: string, from: 'app' | 'sub', to: 'app' | 'sub') => {
    const [, pathname, rest = ''] = path.match(/^([^?#]*)(.*)$/)!; // 쿼리·해시는 그대로 붙인다
    for (const row of table) {
      const m = matchPath({ path: row[from], end: true }, pathname);
      if (m) return generatePath(row[to], m.params as Record<string, string>) + rest;
    }
    return null;
  };

  return {
    /** 앱 라우트 경로 → 지금 도메인에서 써야 할 경로 */
    toPath(path: string) {
      if (!enabled) return path;
      const converted = convert(path, 'app', 'sub');
      if (converted === null && import.meta.env.DEV) {
        console.warn(`[sub-host] 매핑표에 없는 경로로 이동: ${path}`);
      }
      return converted ?? path;
    },
    /** 지금 주소창 경로 → 앱 라우트 경로 (화면 판별·로그용) */
    toAppPath(pathname: string) {
      return enabled ? convert(pathname, 'sub', 'app') ?? pathname : pathname;
    }
  };
}

export const { toPath, toAppPath } = createPathMapper(SUB_HOST_PATHS, isSubHost);
```

- `matchPath` 로 `/sub/terms/privacy` 가 `/sub/terms/:type` 에 맞는지 보고, `generatePath` 로 `/terms/privacy` 를 만든다. 파라미터가 있어도 표에 한 줄이면 된다.
- 매핑표에 없는 경로로 이동하면 개발 중에 경고를 띄운다. 빠뜨린 화면을 빨리 찾는 용도.

### 5-2. 라우트 등록: 표에 있는 것만 신규 도메인 경로로

```tsx
// router.tsx
const allRoutes: RouteObject[] = [
  { path: '/home', element: <HomePage /> },
  { path: '/login', element: <LoginPage /> },
  { path: '/sub/intro', element: <SubIntroPage /> },
  { path: '/sub/verify', element: <SubVerifyPage /> },
  { path: '/sub/terms/:type', element: <SubTermsPage /> },
  { path: '/sub/complete', element: <SubCompletePage /> },
  { path: '/sub/home', element: <SubHomePage /> }
  // ...
];

const subRoutes: RouteObject[] = SUB_HOST_PATHS.map(({ app, sub }) => {
  const route = allRoutes.find((r) => r.path === app);
  if (!route) throw new Error(`[sub-host] 매핑표의 라우트가 없음: ${app}`);
  return { ...route, path: sub };
});

export const router = createBrowserRouter(
  isSubHost
    ? [...subRoutes, { path: '*', element: <Navigate to="/" replace /> }]
    : allRoutes
);
```

결과:

| 접속 | 보이는 화면 |
|---|---|
| `<기존 도메인>/sub/intro` | SubIntroPage (기존 그대로) |
| `<기존 도메인>/sub/complete` | SubCompletePage (기존 그대로) |
| `<신규 도메인>/` | SubIntroPage |
| `<신규 도메인>/done` | SubCompletePage |
| `<신규 도메인>/terms/privacy` | SubTermsPage (`type = privacy`) |
| `<신규 도메인>/home`, `/login` | 등록 안 됨 → `*` 에 걸려 `/` 로 |

- 신규 도메인에는 기존 화면이 아예 등록되지 않는다. 두 화면 묶음이 섞일 일이 없다.
- 매핑표에 적었는데 라우트가 없으면 앱 시작 시 바로 에러가 나서 오타를 놓치지 않는다.

**하위 묶음에 공통 레이아웃이 있는 경우** (`/sub` 레이아웃 아래 `children` 으로 묶여 있으면):

```tsx
const subRoutes: RouteObject[] = [
  {
    element: <SubLayout />,          // path 없는 레이아웃 라우트
    children: SUB_HOST_PATHS.map(({ app, sub }) => ({
      path: sub,
      element: findSubElement(app)   // 기존 children 에서 app 경로에 해당하는 element 찾기
    }))
  }
];
```

`path` 없이 `element` 만 있는 라우트는 URL에 아무것도 붙이지 않고 레이아웃만 감싼다.

### 5-3. 이동: 기존 경로를 쓰되 변환을 거치게

하위 묶음 코드에는 `navigate('/sub/complete')` 같은 이동이 이미 있다. 코드는 계속 **앱 라우트 경로**로 쓰고, 이동할 때만 변환한다.

```ts
// useAppNavigate.ts
export function useAppNavigate() {
  const navigate = useNavigate();
  return (to: To | number, opts?: NavigateOptions) => {
    if (typeof to === 'number') return navigate(to);
    if (typeof to === 'string') return navigate(toPath(to), opts);
    return navigate({ ...to, ...(to.pathname && { pathname: toPath(to.pathname) }) }, opts);
  };
}
```

```tsx
// 바꾸기 전
const navigate = useNavigate();
navigate('/sub/complete');
<Link to="/sub/intro">처음으로</Link>

// 바꾼 뒤
const navigate = useAppNavigate();
navigate('/sub/complete');                  // 신규 도메인에선 '/done'
<Link to={toPath('/sub/intro')}>처음으로</Link>   // 신규 도메인에선 '/'
```

빠뜨리기 쉬운 곳:

- `<Navigate to=...>`, loader·action 의 `redirect()`
- `window.location.href = ...`, `window.open(...)`
- 외부 서비스에 넘기는 **리턴 URL** (본인인증 등). 도메인과 경로 둘 다 바뀐다
- 문자 메시지·푸시 등에 들어가는 링크 (신규 도메인 경로로 만들어야 함)

`'/sub/` 로 전체 검색하면 대부분 나온다.

> **상대경로 이동은 쓰지 않는다.** `navigate('verify')` 나 `navigate('../done')` 은 지금 URL 구조를 기준으로 계산되는데, 두 도메인의 URL 구조가 다르기 때문에 한쪽에서 엉뚱한 곳으로 간다. 항상 앱 라우트 절대경로 + `toPath` 로 쓴다.

### 5-4. 지금 화면 판별: 주소창 경로를 직접 비교하지 않기

```ts
// ❌ 신규 도메인에선 pathname 이 '/done' 이라 항상 false
if (location.pathname === '/sub/complete') { ... }

// ✅ 앱 라우트 경로로 바꿔서 비교
if (toAppPath(location.pathname) === '/sub/complete') { ... }
```

- 탭·헤더 활성 표시, 화면별 분기, 분석 로그의 화면 이름 등에서 `pathname` 을 직접 쓰는 곳을 찾는다.
- 로그에 `toAppPath` 결과를 남기면 두 도메인의 같은 화면이 하나로 집계된다.

### 5-5. (선택) 예전 경로로 들어온 경우

신규 도메인에 `/sub/verify` 처럼 앱 라우트 경로가 그대로 붙은 링크로 들어오는 경우가 있다면, 매핑된 경로로 바꿔 준다.

```tsx
function RedirectToSubPath() {
  const { pathname, search, hash } = useLocation();
  return <Navigate to={toPath(pathname + search + hash)} replace />;
}

// subRoutes 에 추가
...SUB_HOST_PATHS.map(({ app }) => ({ path: app, element: <RedirectToSubPath /> }))
```

## 6. 확인할 것

| 항목 | 이유 |
|---|---|
| 매핑표가 하위 묶음 전체를 덮는지 | 빠진 화면은 신규 도메인에서 `/` 로 튕긴다. 개발 중 콘솔 경고 확인 |
| 본인인증 등 외부 서비스의 리턴·콜백 URL | `<신규 도메인>` 등록 + 리턴 경로가 `toPath` 를 거쳤는지 |
| 쿠키·세션 도메인 | 쿠키가 `<기존 도메인>` 에 묶여 있으면 신규 도메인에서 로그인 상태가 안 보인다 |
| CORS | API 서버가 허용 Origin 목록을 쓰면 `<신규 도메인>` 추가 필요 |
| localStorage·sessionStorage | 도메인(오리진)별로 따로 저장된다. 기존 도메인에서 저장한 값은 안 보임 |
| 하위 묶음 → 기존 화면으로 가는 링크 | 신규 도메인엔 기존 라우트가 없다. 기존 도메인 전체 URL로 보내거나 없앤다 |
| `pathname` 직접 비교 | 5-4 참고 |

## 7. 테스트

### 로컬에서 신규 도메인 흉내 내기

- `sub.localhost` 처럼 `.localhost` 로 끝나는 이름은 대부분의 브라우저가 로컬로 연결해 준다. 안 되면 hosts 파일에 로컬 주소로 추가
- 환경변수 `VITE_SUB_HOST=sub.localhost` 로 실행
- Vite 개발 서버는 낯선 호스트를 막을 수 있으니 `server.allowedHosts` 에 추가

### 체크리스트

1. `<기존 도메인>` 의 기존 화면과 `/sub/...` 화면이 **이전과 똑같이** 동작하는지 (회귀 확인이 제일 중요)
2. `<신규 도메인>/` → intro 화면, 주소창에 `/sub` 없음
3. 하위 묶음을 처음부터 끝까지 진행 → 주소창이 매핑표의 오른쪽 경로대로만 바뀌는지 (`/sub` 가 한 번도 안 나타나야 함)
4. 각 화면에서 새로고침 → 같은 화면 (SPA fallback 확인)
5. 신규 도메인에서 `/home`, `/login` 직접 입력 → `/` 로
6. 파라미터 있는 화면(`/terms/privacy`)이 값까지 제대로 넘어가는지
7. 본인인증 등 외부 다녀오는 흐름 → 돌아왔을 때 도메인과 경로가 맞는지
8. 뒤로가기·앞으로가기로 오갈 때 주소와 화면이 맞는지

### 단위 테스트

`createPathMapper` 는 호스트를 인자로 받으므로 바로 테스트할 수 있다.

```ts
const { toPath, toAppPath } = createPathMapper(SUB_HOST_PATHS, true);
const off = createPathMapper(SUB_HOST_PATHS, false);

it.each([
  ['/sub/intro', '/'],
  ['/sub/complete', '/done'],
  ['/sub/terms/privacy', '/terms/privacy'],
  ['/sub/verify?step=2#top', '/verify?step=2#top'],
  ['/sub/home', '/sub/home'] // 매핑 없음 → 그대로 (개발 중 경고)
])('신규 도메인: %s → %s', (input, expected) => {
  expect(toPath(input)).toBe(expected);
});

it('신규 도메인 주소 → 앱 라우트', () => {
  expect(toAppPath('/')).toBe('/sub/intro');
  expect(toAppPath('/done')).toBe('/sub/complete');
});

it('기존 도메인에선 아무것도 바꾸지 않는다', () => {
  expect(off.toPath('/sub/complete')).toBe('/sub/complete');
});

it('신규 도메인 경로는 겹치지 않는다', () => {
  const subs = SUB_HOST_PATHS.map((r) => r.sub);
  expect(new Set(subs).size).toBe(subs.length);
});
```

## 8. 경로가 대부분 같다면: 기본 규칙 + 예외

화면 대부분이 "`/sub` 만 떼면 되는" 경우라면 표를 다 적지 않고 **예외만** 적어도 된다.

```ts
const PREFIX = '/sub';
const EXCEPTIONS: Record<string, string | null> = {
  '/sub/intro': '/',      // 첫 화면
  '/sub/complete': '/done',
  '/sub/home': null       // 신규 도메인에 노출 안 함
};

export const SUB_HOST_PATHS: PathMapping[] = allRoutes
  .map((r) => r.path!)
  .filter((p) => p.startsWith(`${PREFIX}/`))
  .flatMap((app) => {
    const sub = app in EXCEPTIONS ? EXCEPTIONS[app] : app.slice(PREFIX.length);
    return sub === null ? [] : [{ app, sub }];
  });
```

나머지 코드(5장)는 그대로 쓴다. 다만 이렇게 하면 **새 화면을 추가할 때 자동으로 신규 도메인에도 노출된다.** 노출을 의도적으로 관리하고 싶으면 4장처럼 표를 직접 적는 쪽이 안전하다.

## 9. 정리

- 같은 SPA를 두 도메인에서 쓸 때, 주소창 경로를 바꾸고 싶으면 **리다이렉트가 아니라 라우트 등록을 바꾼다.**
- 두 도메인의 경로가 1:1이 아니면 규칙으로 계산하지 말고 **매핑표 한 장**을 기준으로 둔다. 라우트 등록·이동·화면 판별이 모두 이 표를 쓴다.
- 코드에서는 계속 **기존 앱 라우트 경로**로 쓰고, 이동할 때 `toPath`, 판별할 때 `toAppPath` 로 바꾼다. 기존 도메인 동작은 그대로다.
- 두 도메인의 URL 구조가 달라서 **상대경로 이동은 쓰지 않는다.**
- basename 은 URL에 **있는** 접두어를 떼는 기능이다. 이 상황엔 맞지 않는다.
- 인프라에는 **같은 빌드 연결 + SPA fallback** 만 요청한다.
- 도메인이 바뀌면 **콜백 URL·쿠키·CORS·스토리지**를 같이 확인한다.
