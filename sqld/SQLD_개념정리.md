## 자주 출제되는 개념

기출 18회차(제45회 2022년 5월 ~ 제62회 2026년 8월, 회차당 50문항 = 900문항)를 개념별로 분류해 센 결과다.

- **출제 회차**: 그 개념이 나온 회차 수(18회 중). 한 회차에 여러 문제가 나와도 1회로 센다.
- **문항 수**: 900문항 중 그 개념을 주로 묻는 문항 수. 한 문항이 두 개념에 걸치면 둘 다 센다.
- **연도별**: 연도별로 나온 회차 수. 시행 회차는 2022년 3회, 2023~2025년 각 4회, 2026년 3회다.
- 각 섹션 제목 옆에도 같은 형식으로 적었다. 사이트의 기출은 공식 공개본이 아니라 **복원 문제**라 참고용이다.

## 1과목 — 데이터 모델링의 이해

### 데이터 모델링 개요 · 특징 — 기출 8회 (2025 3 · 2024 2 · 2023 2 · 2022 1)
- **모델링의 특징**: **추상화 · 단순화 · 명확화(정확화)**
  - 명확화: 애매모호함을 없애고 정확하게 기술한다.
  - 함정: "최적화", "내부화", "그룹화" → 틀림. 모델링 특징이 아니다.
  - 함정: "모델링은 시스템 구현만을 위한 사전 작업이다" → 틀림. 업무 흐름을 설명·분석하는 의미도 있다.
  - 함정: "DB 구축 용도로만 모델링하고 업무 설명은 별도 표기법을 쓴다" → 틀림
- **데이터 모델링의 3요소**: **Things**(업무가 관여하는 어떤 것) · **Attributes**(성격) · **Relationships**(관계)
  - 함정: "행위(Events)", "Process" → 틀림. 3요소가 아니다.
- **모델링 유의점 3가지**

| 유의점 | 뜻 |
|--------|----|
| **중복**(Duplication) | 같은 정보를 여러 곳에 저장해 값이 어긋날 수 있음. 최소화한다 |
| **비유연성**(Inflexibility) | 업무·프로세스 변화에 모델이 유연하게 대응하지 못함. **데이터 정의를 사용 프로세스와 분리**해 막는다 |
| **비일관성**(Inconsistency) | 데이터 간 상호 연관 관계를 명확히 정의하지 않아 생김. 없앤다 |

  - 함정: "프로그램과 테이블 간 연계성을 높인다" → 틀림. 연계성은 **낮춰야** 업무 변화에 유연하다.
  - 함정: "초기 설계 단계부터 반정규화를 적극 수행한다" → 틀림. 유의점이 아니다.
- **업무 규칙(비즈니스 룰)은 반드시 모델에 포함**한다. 데이터 모델 작성의 기준이 된다.
  - 함정: "업무 규칙이 모델에 포함되지 않아도 된다" → 틀림
- **DBMS 특징**: 데이터를 **통합·공유**하고, 중복과 불일치를 줄이며, 보안·무결성을 제공한다.
  - 함정: "다른 사용자와 공유할 수 없다" → 틀림
- 관계형 DB의 특징
  - 무결성을 보장하고, 분류·정렬·탐색이 빠르다.
  - 이미 만든 스키마는 수정하기 어렵고, **부하 분석은 어렵다**.
  - 함정: "부하 분석이 쉽다" → 틀림
  - **선언형 언어(SQL)**를 쓴다. 함정: "절차적 데이터 저장" → 틀림. 특징이 아니다.
- **릴레이션**은 집합이라 **행 순서가 보장되지 않는다**. 순서가 필요하면 ORDER BY를 쓴다.
- **데이터 사전**(시스템 카탈로그): 테이블·칼럼·제약조건 같은 **메타데이터**를 저장한다. 업무 데이터는 저장하지 않는다.
- 릴레이션 용어: **차수**(Degree) = 칼럼(속성) 수, **카디널리티** = 행(튜플) 수
  - 조인 조건 없이 두 테이블을 FROM에 나열하면 **카티션 곱**이 된다. FK 관계가 있어도 자동 조인되지 않는다.
  - 예: 칼럼 5개·3행 테이블과 칼럼 3개·3행 테이블 → 차수 8, 카디널리티 9
- **계층형 데이터 모델**: 트리 구조, 부모:자식 = **1:M**, **같은 레벨 개체끼리는 관계를 표현하지 않는다**.
  - 함정: "계층형 모델의 개체 간 관계는 1:1" → 틀림

### 데이터 모델링 단계 — 기출 6회 (2024 2 · 2023 2 · 2022 2)
| 단계 | 특징 |
|------|------|
| **개념적** | 전사적 관점, **추상화 수준이 가장 높음**, DB 종류(계층형·네트워크·관계형)와 무관하게 업무 측면에서 모델링. **주제영역 설계·업무 범위 정의**, 엔터티·관계 식별 |
| **논리적** | 키·속성·관계를 정확히 표현. **식별자 확정, 속성 정제·도메인 정의, 정규화, 슈퍼·서브타입 분리·통합, M:N 해소**. 재사용성이 높음 |
| **물리적** | 실제 DB에 구현하기 위한 성능·저장 구조 설계. **인덱스·파티션·저장 구조·접근 경로**, **데이터 용량 산정** |

- **개념 → 논리 → 물리** 순으로 갈수록 구체적(상세화)이다. 개념이 가장 추상적이다.
  - 함정: "개념적 모델링은 추상화 수준이 **낮고** 재사용성이 높다" → 틀림. 추상화 수준이 **높다**.
- 개념적 모델링에서는 주로 **ER 모델**을 쓴다. **인덱스 구성은 하지 않는다**(물리 단계).
- 논리 모델링
  - "**어떻게** 데이터에 접근하고 **누가** 접근하는지"를 정의하는 단계로 출제된다.
  - 논리 모델 = **데이터 모델링이 최종 완료된 상태**(물리 스키마 설계 바로 전 단계)
  - 함정: "주제영역을 설계하고 업무 전반의 범위를 정의한다"를 논리 모델링으로 고른 보기 → 틀림. 개념 단계다.
- 실제 DB 구축 때 참고하는 모델은 **물리** 모델이다.
- **논리 모델의 FK가 물리 모델에서 반드시 구현되지는 않는다.** (선택 사항)

- **데이터와 프로세스의 상관 관점**: 프로세스가 데이터에 주는 영향 → **CRUD 매트릭스**가 여기에 속한다.

### 3단계 스키마 · 데이터 독립성 — 기출 8회 (2026 1 · 2025 2 · 2024 2 · 2023 2 · 2022 1)
- **ANSI-SPARC 3단계(3층) 스키마**: 외부 · 개념 · 내부

| 스키마 | 관점 주체 | 내용 | 예 |
|--------|-----------|------|----|
| **외부** | 사용자 | 사용자·응용 프로그램별 **뷰**. **여러 개** 존재 가능. 필요한 데이터만 정의해 접근 범위 제한 | **VIEW** |
| **개념** | 설계자 | 모든 사용자 관점을 **통합한 조직 전체 구조**. 규칙·관계 표현. **하나**만 존재 | 전사 ERD |
| **내부** | 개발자 | **물리적 저장 구조·저장 방법** | 테이블스페이스·인덱스·파티션 설계 |

- 관점 주체는 **사용자·설계자·개발자**다. 함정: "구조자" → 틀림. 없는 용어다.
- 함정: "외부 스키마는 전체 저장 구조·물리적 저장 방법을 정의한다" → 틀림. **내부 스키마** 설명이다.
- 함정: "외부 스키마는 모든 사용자 관점을 통합한다" → 틀림. **개념 스키마** 설명이다.
- 함정: "개념 스키마는 물리적 저장 구조를 표현한다" → 틀림. **내부 스키마** 설명이다.
- 3단계 스키마가 아닌 것: 응용 스키마, 논리 스키마, 물리 스키마, 구조 스키마, 사용 단계
- **데이터 독립성**
  - **논리적 독립성**: **개념 스키마**가 바뀌어도 외부 스키마·응용 프로그램이 영향받지 않음
  - **물리적 독립성**: **내부 스키마**(인덱스·파티션·저장 구조)가 바뀌어도 개념·외부 스키마가 영향받지 않음
  - 함정: "저장 구조를 바꿔도 응용 프로그램에 영향이 없다"를 논리적 독립성으로 고른 보기 → 틀림. 물리적 독립성이다.

### 엔터티의 특징 — 기출 2회 (2026 1 · 2024 1)
- 엔터티 정의의 **공통점 3가지**: ① 사람·장소·사건·개념 같은 **명사** ② 업무상 **관리가 필요한 관심사** ③ **저장이 필요한 어떤 것(Thing)**
  - 함정: "데이터베이스 내에서 변별 가능한 객체" → 틀림. 공통점 3가지가 아니다.
- 업무에서 필요하고 관리하려는 정보여야 한다. 데이터로 존재해도 **업무에서 필요 없으면** 엔터티가 아니다.
- **유일한 식별자**로 식별할 수 있어야 한다.
- 영속적으로 존재하는 **인스턴스가 2개 이상**이어야 한다.
  - 함정: "싱글턴 패턴처럼 인스턴스 1개만으로도 엔터티가 될 수 있다" → 틀림
- **업무 프로세스에 의해 이용**되어야 한다.
- **반드시 속성**을 포함해야 한다. 예외로 **관계 엔터티**는 주식별자 속성만 있어도(일반 속성 없이) 인정된다.
  - 함정: "주식별자와 일반 속성이 없어도 엔터티는 존재할 수 있다" → 틀림. 테이블은 PK를 지워도 존재하지만 **엔터티**는 안 된다.
- **다른 엔터티와 최소 1개 이상의 관계**가 있어야 한다.
  - 함정: "다른 엔터티와의 관계를 가지지 않는다" → 틀림
  - 단, **통계성·코드성 엔터티는 관계를 생략**할 수 있다.
  - 어디에도 쓰이지 않는 **고립 엔터티는 제거를 고려**한다.
- 엔터티는 **두 개 이상의 속성**과 **두 개 이상의 인스턴스**를 가진다. 그래서 '회원', '환자'는 엔터티이고 '이름', '주소', '나이'는 속성이다.

### 엔터티 분류 — 기출 13회 (2026 3 · 2025 3 · 2024 3 · 2023 4)
| 기준 | 종류 |
|------|------|
| 유무형 | **유형**(물리적 실체: 사원, 물품) · **개념**(실체 없는 개념: 조직, 보험상품) · **사건**(업무 수행 중 발생: 주문, 청구) |
| 발생 시점 | **기본**(원래 존재: 사원, 고객) · **중심**(기본에서 파생, 업무의 중심: 주문, 계약) · **행위**(두 개 이상 엔터티에서 발생, 자주 바뀜: 주문내역, 이력) |

- 함정: "유무형 분류가 아닌 것" → **행위 엔터티**(발생 시점 분류에 속함)
- 함정: "발생 시점 분류가 아닌 것" → **사건 엔터티**(유무형 분류에 속함)
  - 발생 시점 분류에 **없는 이름**: 사건·개념·유형·관계 엔터티 (사건·개념·유형은 유무형 기준)
- **기본 엔터티 = 키 엔터티**
  - 다른 엔터티의 영향 없이 **독립적으로 생성**된다. 다른 엔터티로부터 주식별자를 **상속받지 않고** 자기 고유 주식별자를 가진다.
  - 예: 사원·부서·고객·상품·자재·회사
  - 함정: "기본 엔터티는 다른 엔터티로부터 주식별자를 상속받는다" → 틀림
  - 다른 엔터티의 부모 역할을 해도 업무에 원래 존재하면 기본 엔터티다.
- **행위 엔터티**: 두 개 이상 부모의 행위로 생긴다. 분석 초기엔 잘 안 보이고 **상세 설계 단계**에서 드러난다.
  - 예: 주문상세, 배송추적, 서비스이용, 청구, 납부
  - 함정: "서비스이용은 개념 엔터티" → 틀림. 행위 엔터티다.
- 주의: 문제마다 주문을 보는 기준이 다르다.
  - 교재에서는 보통 주문을 **중심 엔터티**로 분류한다.
  - 다른 문제에서는 주문을 고객·상품 두 부모에서 생기는 **행위 엔터티**로 보고, **프로젝트**를 중심 엔터티로 골랐다.
  - 보기에 '프로젝트'처럼 기본 엔터티에서 생기면서 다른 행위 엔터티의 부모가 되는 것이 있으면 그게 중심 엔터티다.
- 추가 예시
  - "중심 엔터티가 아닌 것" → **사원**(기본 엔터티). 매출·주문·계약은 중심이다.
  - **주문상품**은 주문과 상품의 M:N 관계를 해소하는 **행위 엔터티**(교차 엔터티)다.
- **교차 엔터티**: M:N 관계를 해소하려고 **인위적으로 만든** 엔터티
- **약한 엔터티**(Weak Entity): 스스로 식별되지 못하고 **강한 엔터티의 식별자에 의존**한다.

### 엔터티 · 인스턴스 · 속성 — 기출 6회 (2026 1 · 2024 2 · 2023 2 · 2022 1)
- 포함 순서: **엔터티**(집합) → **인스턴스**(행) → **속성**(칼럼) → **속성값**(셀)
- 관계: 엔터티 ─ 인스턴스 **1:M** ─ 속성 **1:M** ─ 속성값 **1:1**
  - 한 엔터티는 인스턴스 **2개 이상**, 속성 **2개 이상**을 가진다.
  - **하나의 속성은 하나의 속성값**만 가진다. 여러 값이면 정규화(1NF) 대상이다.
  - 함정: "하나의 속성은 하나 이상의 속성값을 가진다" → 틀림
  - 함정: "인스턴스는 두 가지 속성값을 가진다" → 틀림. 속성값 수는 엔터티의 속성 수에 따라 달라진다.
- **속성**: 업무에서 관리하려는, 의미상 **더 이상 분리되지 않는 최소의 데이터 단위**
  - 속성은 인스턴스의 구성 요소다. 그래서 **인스턴스 없이 독립적으로 존재할 수 없고**, 속성 없는 인스턴스도 없다.
  - 속성은 엔터티에 대한 **구체적인 정보**다. 함정: "속성은 추상적인 값을 갖는다" → 틀림
- **식별자**: 여러 속성 중 엔터티를 **대표**하는 속성

### 속성 분류 — 기출 11회 (2026 1 · 2025 3 · 2024 1 · 2023 3 · 2022 3)
| 기준 | 종류 |
|------|------|
| **특성** | **기본 · 설계 · 파생** |
| **엔터티 구성 방식** | **PK 속성 · FK 속성 · 일반 속성** |
| 분해 여부 | **단순 속성**(더 못 나눔: 나이, 성별) · **복합 속성**(나눌 수 있음: 주소 → 시·구·동) |
| 값 개수 | **단일값 속성**(값 1개) · **다중값 속성**(값 여러 개: 연락처 여러 개 → 별도 엔터티로 분리) |

- 주의: 단순·복합·단일값·다중값을 "구성 방식에 따른 분류"로 묶은 자료도 있다. 교재에서 "구성 방식"은 PK·FK·일반 속성 분류다.
- 함정: "속성의 특성에 따른 분류가 아닌 것" → **일반 속성**(구성 방식 분류에 속함)
- **주소는 복합 속성**이다. "단일 속성이 아닌 것"을 물으면 주소를 고른다.
- **특성 기준 분류**
  - **기본 속성**: 업무에서 원래 도출되는 속성
  - **설계 속성**: 업무에는 없지만 설계 중에 규칙화·코드화하려고 만든 속성 (예: 일련번호, 코드)
  - **파생 속성**: 다른 속성에서 **계산·변형**되어 생기는 속성 (예: 합계, 잔액). 데이터 정합성 관리를 위해 되도록 적게 정의한다.
- 파생 속성 예: 주문 엔터티의 **총주문금액**(단가 × 수량), 주문금액, **연령**(생년월일에서 계산), **최종·최초주문일자**(주문일자의 MAX·MIN), 이자
  - 함정: "이자와 이자율은 파생 속성" → 틀림. **이자율은 기본 속성**, 이자만 파생이다.
- 구분 예
  - 예금: 원금·예치기간 = 기본, 예금분류(코드) = 설계, 이자 = 파생
  - 상품: 단가·할인율 = **기본**, 할인가(단가·할인율로 계산) = **파생**, 재고상태코드(1: 정상, 2: 품절) = **설계**
- 파생 속성은 **조회 성능**을 위해 계산값을 저장해 두는 속성이다.
  - 저장(반정규화)하면 조회는 빨라지지만, 원천 값이 바뀔 때 함께 갱신하지 않으면 **데이터 불일치**가 생긴다.
  - 꼭 저장해야 하는 건 아니다. 함정: "파생 속성은 무조건 저장되어야 한다" → 틀림

### 도메인 — 기출 5회 (2026 1 · 2025 1 · 2023 2 · 2022 1)
- **도메인**: 속성이 가질 수 있는 **값의 범위**
  - 데이터 타입·크기(길이)·허용값·기본값·NOT NULL 여부 같은 제약을 정의한다.
  - 함정: "도메인은 FOREIGN KEY 제약을 정의한다" → 틀림. FK는 테이블 간 참조에서 정의한다.
  - 헷갈리는 보기: 속성 사전·용어 사전·시스템 카탈로그 → 도메인이 아니다.
- **도메인 설계**: 속성을 명사로 분리 → **공통 명사는 하나의 도메인**으로 만든다 → 도메인별 타입·길이 지정 → 속성에 할당
  - 함정: "공통으로 발생하는 명사는 여러 개의 도메인으로 생성한다" → 틀림
  - 예: 성별 도메인 = 'M', 'F'

### 명명 규칙 — 기출 2회 (2026 1 · 2024 1)
- **엔터티명**: 현업 업무 용어, **약어 금지**, **단수 명사**, 모든 엔터티에서 **유일**, 생성 의미대로 자연스럽게
  - 함정: "가능하면 약어를 사용해 간결하게" → 틀림
- **속성명**: 간결한 **명사형**, **서술식 이름 금지**, 약어 제한, 현업 업무 용어, **모델 전체에서 유일**
  - 함정: "가급적 서술적 속성명을 사용한다" → 틀림
  - 함정: "직원.이름, 고객.이름처럼 엔터티마다 같은 속성명을 써서 일관성을 확보" → 틀림. 속성명은 유일해야 한다(직원명, 고객명).

### 관계의 구성 · 종류 — 기출 12회 (2026 2 · 2025 2 · 2024 3 · 2023 4 · 2022 1)
- **관계**: 두 엔터티 사이의 연관성을 표현한 것
- 한 엔터티의 인스턴스와 다른 엔터티의 인스턴스 사이의 관계를 **페어링(Pairing)**이라 한다.
- 엔터티는 관계를 **여러 개** 가질 수 있다. 함정: "관계를 두 개까지만 가질 수 있다" → 틀림
- **정규화로 분리된 엔터티끼리는 관계를 맺는다.** 이 관계를 따라 다시 연결하는 것이 **조인**이다. (상속된 식별자를 매핑키로 사용)
- **관계의 표기 요소**

| 요소 | 영문 | 뜻 |
|------|------|----|
| **관계명** | **Membership**(Relationship Name) | 관계의 이름 (예: 소속, 보유) |
| **관계차수** | **Cardinality**(Degree) | 참여하는 인스턴스 수 (1:1, 1:M, M:N) |
| **관계선택사양** | **Optionality** | 필수 참여인지 선택 참여인지. **업무 규칙**에 따라 정한다 |

  - 참여자 수를 표현하는 건 관계차수다. 관계선택사양이 아니다.
  - 함정: 관계 빈도, 관계분류, 관계정의, **식별성**, Attribute → 틀림. 관계 표기 요소가 아니다.
- **관계 종류**
  - **존재적 관계**: 엔터티 사이의 상태를 나타낸다. (예: 부서와 사원의 '소속' 관계)
  - **행위적 관계**: 엔터티 사이의 행위로 생긴다. (예: 고객과 주문, 주문-배송의 **'배송근거'** 관계)
  - **ERD는 존재·행위 관계를 구분하지 않는다**(단일 표기). UML은 연관관계(실선)와 의존관계(점선)로 구분한다.
  - 함정: "ERD는 존재·행위 관계를 실선·점선으로 구분한다" → 틀림
  - 함정: "UML은 연관·의존을 구분하지 않고 단일 표기법을 쓴다" → 틀림. 단일 표기는 **ERD** 쪽이다.
- **UML 클래스 다이어그램**: 연관 관계는 **멤버 변수**로 계속 참조, 의존 관계는 **오퍼레이션의 파라미터·지역 변수**로 일시적으로 사용한다.
  - 함정: 두 구현 방식을 바꿔 쓴 보기 → 틀림
- **배타적(Arc) 관계**: 하나의 인스턴스가 여러 후보 엔터티 중 **하나와만** 관계를 맺는다.
  - 예: 고객은 개인이거나 법인이고, 둘 다일 수는 없음
  - 분기되는 두 관계선을 가로지르는 **반원(아크)**으로 표기한다. 선택된 쪽 외의 FK는 NULL이다.
- 세 엔터티가 삼각형으로 연결돼 있어도 **각 관계는 독립적인 의미**를 가진다.
  - 함정: "병원-수술 직접 관계는 병원-의사 + 의사-수술 관계를 합친 것과 같다" → 틀림. 의사가 집도하지 않은 수술도 병원에 속할 수 있다.

### ERD 표기법 · 읽는 법 — 기출 15회 (2026 2 · 2025 4 · 2024 3 · 2023 3 · 2022 3)
- ER 표기법 종류: **IE**(정보공학, 까마귀발) · **Barker**(Case Method) · IDEF1X · UML · Chen
  - 그림을 주고 어떤 표기법인지 묻는 문제가 나온다. 까마귀발 + 식별 실선/비식별 점선이면 IE다.
- **Chen(피터 첸, 1976) 표기법**: 엔터티 **사각형(□)**, 속성 **타원(○)**, 관계 **마름모(◇)**, 주식별자 속성은 밑줄
- **IE vs Barker**

| 구분 | IE | Barker |
|------|----|--------|
| 실선·점선 | 식별·비식별 관계 | **필수·선택 참여** |
| 식별 관계 표시 | 실선 | 관계선 끝(자식 쪽)의 **UID bar(\|)** |

  - 함정: "IE 표기법에서 식별 관계는 점선, 비식별 관계는 실선" → 틀림. 반대로 서술했다.
  - 함정: "바커 표기법의 실선·점선은 식별 여부를 뜻한다" → 틀림. **필수·선택 참여**를 뜻한다.
  - 함정: "바커 표기법은 NULL 허용 여부를 알 수 없고 IE 표기법은 알 수 있다" → 틀림. 오답 보기로 출제됐다.
- **까마귀발 기호**
  - `||` : 반드시 1개 / `|o` : 0 또는 1개(선택)
  - `|<`·`|{` : **1개 이상**(필수) / `o<`·`o{` : **0개 이상**(선택)
- **읽는 법**: 상대 엔터티 쪽 끝에 붙은 기호가 **나의 참여 조건**이다.
  - 고객 ─|──○< 주문: 고객 입장에서 주문 쪽에 ○ → 주문이 없어도 되는 **선택 참여**. 주문 입장에서 고객 쪽에 | → 고객이 반드시 있어야 하는 **필수 참여**.
  - 함정: "`고객 ||--o{ 주문`에서 고객은 주문을 최소 1건 가져야 한다" → 틀림
  - 예: `직원 |o--o| 사원증` → 양쪽 다 0 또는 1. 사원증 하나를 여러 직원이 공유(1:N)하는 해석은 틀림
- 선택 참여(○) 쪽은 상대가 없어도 존재할 수 있다. 부모 쪽이 선택 참여면 **자식 없이도 인스턴스를 등록**할 수 있다.
  - 함정: "상품엔 주문이 무조건 포함된다" → 틀림. 상품은 주문 없이도 등록된다.
  - 함정: "고객에 데이터를 넣을 때는 주문이 있는 고객만 입력할 수 있다" → 틀림. 고객 쪽은 주문 없이 존재 가능
  - 함정: "과목을 추가하려면 학생이 필요하다" → 틀림. 과목은 수강 없이 독립적으로 등록된다.
- **PK 구성으로 업무 규칙을 읽는다** (관계·교차 엔터티)
  - 서비스이용 PK = (고객번호, 서비스번호, **이용일자**) → 같은 고객이 같은 서비스를 다른 날 **재이용 가능**(행이 따로 생김)
  - 이용내역 PK = (이용일자, 사원번호) → 같은 사원이 **같은 날 여러 콘도를 이용할 수 없다**.
- **ERD 작성 순서**: 엔터티 도출(그리기) → 엔터티 **배치** → 관계 설정 → **관계명** 기술 → 관계 **참여도** 기술 → 관계 **필수 여부** 기술
  - 가장 중요한 엔터티는 **왼쪽 상단**에 둔다. 함정: "오른쪽 상단에 배치" → 틀림

### 식별 관계 · 비식별 관계 — 기출 12회 (2026 3 · 2025 2 · 2024 3 · 2023 2 · 2022 2)
| 구분 | 식별 관계 | 비식별 관계 |
|------|-----------|-------------|
| 부모 식별자 | 자식의 **주식별자(PK)에 포함** | 자식의 **일반 속성(FK)** |
| 연결 강도 | 강한 연결 | 약한 연결 |
| IE 표기 | **실선** | **점선** |
| 부모 참여 | 부모가 있어야 자식 생성 | 부모 없이도 자식 생성 가능. **부모 참여가 필수 조건이 아니다** |

- **식별 관계의 관계 차수**
  - 자식이 **부모 속성만으로** PK를 구성 → **1:1**
  - 부모 속성 + 자기 속성으로 PK를 구성 → **1:M**
  - 함정: "식별 관계는 항상 1:1이다" → 틀림
- **식별 관계가 연쇄되면 PK가 계속 전파**된다. (A → B → C → D)
  - 그래서 A와 C는 **B를 거치지 않고 바로 조인**할 수 있다.
- 함정: "비식별 관계는 반드시 부모 엔터티에 종속한다" → 틀림. 식별 관계 설명이다.
- **비식별 관계를 고려하는 경우**
  - 상속받은 식별자가 계속 이어져서 **PK 속성 수가 많아지고 복잡해질 때**
  - 자식의 FK가 **필수가 아니어도 되는**(부모 없는 자식이 있을 수 있는) 경우
  - 부모·자식의 **데이터 생명주기(Life Cycle)를 따로 관리**하는 경우 (부모가 먼저 삭제될 수 있음)
  - 여러 엔터티를 하나로 **통합**했지만 각자 별도 관계를 가지는 경우
  - 자식 PK를 부모와 **별도로 만드는 게 유리**한 경우
- **식별 관계를 유지하는 경우**: 부모 없이는 존재 의미가 없거나 부모와 함께 생성·소멸해야 할 때
  - 함정: "부모와 자식의 생명주기가 같다 / 부모가 자식과 함께 소멸된다"를 비식별 기준으로 고른 보기 → 틀림. **식별 관계** 기준이다.
- 비식별로 바꾸면 손자 엔터티까지 키가 전파되지 않는다. 그래서 상위 엔터티에 접근할 때 **조인이 오히려 늘어난다**.
  - 함정: "A-B를 비식별로 바꾸면 A와 C 조인이 더 쉬워진다" → 틀림. C에 A의 키가 없어져 B를 반드시 경유해야 한다.
  - 함정: "비식별 관계는 테이블 간 조인을 최소화한다" → 틀림

### 관계 도출 시 체크 사항 — 기출 없음
- 두 엔터티 사이에 관심 있는 연관 규칙이 존재하는가?
- 두 엔터티 사이에 정보의 조합이 발생하는가?
- 업무기술서·장표에 관계 연결에 대한 규칙이 서술되어 있는가?
- 업무기술서·장표에 관계 연결을 가능하게 하는 동사(Verb)가 있는가?
- 위 네 가지 **모두** 체크 사항이다. ("모두 고른 것"으로 출제)
- 함정: "관계 연결을 가능하게 하는 **명사**가 있는가?" → 틀림. **동사**가 맞다.

### 식별자 — 기출 15회 (2026 3 · 2025 3 · 2024 3 · 2023 4 · 2022 2)
| 기준 | 종류 |
|------|------|
| 대표성 | **주식별자** · **보조식별자** |
| 생성 여부 | **내부식별자**(스스로 생성) · **외부식별자**(다른 엔터티에서 관계로 받아옴) |
| 속성 수 | **단일식별자** · **복합식별자** |
| **대체 여부** | **본질식별자**(업무에 의해 생김) · **인조식별자**(인위적으로 만듦. 예: 일련번호) |

- 보조·본질·복합은 **서로 다른 분류 기준**(대표성·대체 여부·속성 수)이다. 하나의 사실로 셋을 다 묶은 보기는 틀림
- **주식별자의 특징**
  - **유일성**: 모든 인스턴스를 유일하게 구분한다.
  - **최소성**: 속성 수가 유일성을 만족하는 최소한이다. 하나라도 빼면 구분이 안 된다.
  - **불변성**: 값이 자주 바뀌지 않는다. 값이 바뀌면 상속받은 자식 키까지 다 고쳐야 한다.
    - 함정: "업무 변화에 따라 유연하게 변경할 수 있다" → 틀림
  - **존재성**: 반드시 값이 있다. NULL이면 안 된다(NOT NULL).
    - 유일해도 **NULL이 허용되는 속성**(예: 이메일)은 주식별자가 될 수 없다.
  - 함정: 주식별자 특징 보기에 **종속성** → 틀림. 유일성·최소성·불변성·존재성만 해당한다.
- **주식별자 도출 기준**
  - 업무에서 **자주 이용되는 속성**으로 정한다.
  - **명칭·내역**처럼 이름으로 기술되는 속성은 피한다. 함정: "명칭을 주식별자로 지정한다" → 틀림
  - 복합 식별자라면 속성을 너무 많이 넣지 않는다.
- 주식별자 고르기 예: 이름(동명이인 → **유일성** 위배), 이메일(NULL 가능 → **존재성** 위배), 휴대폰번호(변경 가능 → **불변성** 위배) → **사원번호**가 적절
- **복합 기본키**는 구성 칼럼 **모두 NOT NULL**이다. 함정: "하나만 값이 있으면 된다" → 틀림
- **보조식별자**: 인스턴스를 구분할 수는 있지만 **대표성이 없다**. 다른 엔터티와 참조 연결에 쓰지 않는다.
- **외래키(FK)**는 다른 엔터티에서 받아온 **외부 식별자**다. 함정: "FK는 내부 식별자" → 틀림
  - 예: 리뷰 PK가 (고객ID, 리뷰번호)이면 고객ID = 외부 식별자, 리뷰번호 = 내부 식별자
- **본질 식별자**는 **업무 행위**를 통해 값이 정해진다. 업무 행위 없이 부여되는 값은 인조 식별자다.
  - 예: 주민등록번호 = 본질 / 일련번호·IDENTITY·시퀀스 = 인조
- **인조 식별자**
  - 주로 **본질식별자가 복잡할 때** 만든다. 일련번호처럼 관리 편의를 위해 인위적으로 만든다.
  - 본질 식별자가 있어도 관리 편의를 위해 따로 둘 수 있다.
  - 장점: 업무 값 변경 영향을 받지 않는 안정적인 단일 칼럼 PK
  - 단점: **중복 데이터가 생길 수 있고**, 본질식별자용 **인덱스가 추가로 필요**하다.
  - 함정: "속성 수가 적으면 인조 식별자를 반드시 써야 한다" → 틀림
  - 함정: "인조식별자는 다른 엔터티의 기본키를 그대로 쓰는 것" → 틀림. 외래키(외부식별자) 설명이다.
- **이력 관리**가 필요하면 PK에 **일자·순번**을 넣는다.
  - 예: (고객번호, 서비스번호)만 PK면 해지 후 재이용을 새 행으로 저장할 수 없다. → (고객번호, 서비스번호, 이용일자)

### 정규화 — 기출 15회 (2026 3 · 2025 4 · 2024 4 · 2023 1 · 2022 3)
- **정규화의 목적**: **중복 제거(최소화)** + **이상 현상 방지** + 무결성 확보 + 정보 손실 방지 + **유연성 향상**
  - 정규화하면 테이블 사이의 **독립성이 향상**된다.
  - 함정: "정규화하면 유연성이 떨어진다", "정규화는 데이터의 중복성과 유연성을 최소화한다" → 틀림. 유연성은 **높인다**.
  - 함정: "정규화의 이점 = 처리 성능 향상" → 틀림
  - 함정: "정규화는 정보의 **보안**을 목적으로 한다" → 틀림. 보안과 관련 있는 것은 **뷰**다.
  - 함정: "반드시 모든 데이터를 정규화해야 한다" → 틀림. 성능 때문에 반정규화도 한다.
- **이상 현상**: 정규화하지 않아 중복 저장되면서 생기는 문제

| 종류 | 뜻 · 예 |
|------|--------|
| **삽입 이상** | 다른 데이터가 있어야만 저장할 수 있음. 예: 주문이 없으면 신규 고객·고객등급을 저장할 수 없다 |
| **갱신(수정) 이상** | 같은 값이 여러 행에 중복 저장돼 하나를 바꿀 때 **여러 행을 모두 수정**해야 함. 일부만 고치면 불일치. 예: 주문 행마다 반복 저장된 고객등급 변경 |
| **삭제 이상** | 한 행을 지우면 다른 정보까지 함께 사라짐 |

- **정규형 단계**

| 단계 | 내용 |
|------|------|
| **1NF** | 한 속성이 **하나의 값(원자값)만** 갖도록 반복되는 값·다중값을 분해 |
| **2NF** | **부분 함수 종속 제거**. 모든 일반 속성이 PK **전체에 완전 함수 종속**. 복합 식별자의 일부에만 종속된 속성을 분리 |
| **3NF** | **이행 함수 종속 제거**. 일반 속성끼리 종속되는 관계를 분리 |
| **BCNF** | 모든 결정자가 후보키가 되도록 분해 |
| 4NF | 다치 종속 제거 |

- **정규형 단계는 누적**이다. 3NF는 1NF·2NF를 만족한 뒤에만 된다.
  - 함정: "3정규화는 1·2정규화를 만족하지 않아도 수행할 수 있다" → 틀림
- 함정: "주식별자 전체에 종속" 조건을 1NF 설명으로 쓴 보기 → 틀림. 2NF 조건이다.
- 보기 구분: "다수의 주식별자를 분리" → BCNF / "모든 속성은 하나의 값" → 1NF / "기본키 전부에 종속" → 2NF / "속성 간 종속 금지" → 3NF
- **1NF — 다중값·반복 칼럼**
  - 다중값 속성은 칼럼을 반복하거나(직원1, 직원2) 구분자로 이어 붙이지 않는다. **별도 엔터티(행)로 분리**한다.
  - **같은 유형의 속성이 칼럼 단위로 반복**(코드1, 코드2, …)되면 **1NF 위배**다.
  - 칼럼마다 인덱스를 만들면 입력·수정·삭제 성능이 떨어진다. **1차 정규화 후 인덱스**를 거는 게 맞다.
- **PK가 단일 속성이면 부분 함수 종속이 없어 2NF는 자동 만족**한다. 이행 종속이 있으면 3NF만 위배한다.
  - 함정: "주식별자가 단일 속성이라 3NF까지 모두 만족한다" → 틀림
  - 함정: "기본키가 복합키면 3NF는 자동으로 만족한다" → 틀림
- **복합 식별자라고 무조건 2NF 문제인 것은 아니다.** 일반 속성끼리 종속(할인쿠폰코드 → 할인쿠폰명)이면 **3NF 위배**다.
- **위반 판별 예**
  - PK (주문번호, 상품번호)에서 상품명이 상품번호에만 종속 → 복합키 일부에 종속 → **2NF 위반**(부분 함수 종속)
  - 일반 속성이 다른 일반 속성을 결정(고객번호 → 고객명, 고객명 → 고객등급) → **3NF 위반**(이행 종속). 분리 대상은 결정되는 쪽(예: **고객등급**)이다.
  - "몇 정규형이고 몇 정규화 대상인가" 유형: PK(학번, 과목번호)에서 지도교수명·학과명이 **과목번호에만** 종속 → 부분 종속 → **1차 정규형 – 2차 정규화 대상**
- 함수 종속은 **방향이 있다**. 함정: "상품번호가 상품명에 종속되면 상품명도 상품번호에 종속된다" → 틀림
- 주식별자 선정과 **가장 관련이 적은 정규화는 3NF**다. 3NF는 일반 속성끼리의 종속을 다루기 때문이다.
- 정규화는 **논리 모델링** 단계의 작업이다.
  - 함정: "개념 모델링 단계의 엔터티를 상세화하는 과정" → 틀림
- **M:N 관계는 물리 모델(테이블)로 바로 구현할 수 없다.** 두 PK를 상속받는 교차 엔터티로 1:M, M:1로 분해한다. 이 해소는 **논리적 모델링** 단계에서 한다.
- **정규화와 성능**
  - 함정: "정규화 수준이 높을수록 조인이 줄어 조회 성능이 무조건 좋아진다" → 틀림
    - 정규화하면 테이블이 쪼개져 **조인이 늘어나므로** 조회 성능이 떨어질 수 있다.
    - 이를 보완하려고 **반정규화**를 한다. 입력·수정·삭제 성능과 정합성은 정규화 쪽이 유리하다.
  - 함정: "정규화는 **항상** 조회 성능을 떨어뜨린다" → 틀림. 반정규화된 엔터티를 정규화해서 **조회 성능이 좋아지는** 경우도 있다.

### 반정규화 — 기출 1회 (2022 1)
- **반정규화 목적**: 조인 경로 단축, 디스크 I/O 분산, 집계 데이터 미리 계산
  - 함정: "무결성과 일관성을 완벽히 보장하기 위해" → 틀림. 그건 정규화의 목적이다.
- 반정규화는 **정규화된 모델을 기준으로** 성능 요구를 검토한 뒤 필요할 때만 한다.
- **반정규화는 중복이 생겨 데이터 독립성이 떨어진다.**
- **수직 분할**: 자주 쓰는 칼럼(예: 로그인 정보)과 드물게 쓰는 칼럼을 **별도 테이블로 분리**해 한 번에 읽는 양을 줄인다.
- 파생 속성 저장도 반정규화다. 조회는 빨라지지만 원천 값과 함께 갱신해야 한다.

### 성능 데이터 모델링 — 기출 1회 (2022 1)
- **기본 원칙**: **완전 정규화를 먼저** 하고, 성능 이슈가 있는 부분만 **반정규화**한다.
  - 함정: "분석 단계부터 반정규화를 수행한다" → 틀림
- **성능 데이터 모델링 순서**
  1. 정규화를 정확히 수행 (가장 먼저)
  2. DB **용량 산정**
  3. 발생하는 **트랜잭션 유형** 파악
  4. 용량·트랜잭션 유형에 따라 **반정규화**
  5. **이력 모델 조정, PK/FK 조정, 슈퍼·서브타입 조정**
  6. **성능 관점에서 데이터 모델 검증** (가장 마지막)
  - 함정: "트랜잭션 유형은 무시해도 된다" → 틀림
- 분석·설계 단계에서 성능을 고려하면 **Rework 비용**과 이후 튜닝 비용을 줄인다. 데이터가 빨리 늘수록 성능 개선 비용도 커진다.
  - 함정: "성능이 떨어지면 모델보다 문제 시점의 SQL 중심으로 튜닝한다" → 틀림. 모델 설계부터 봐야 한다.
  - 튜닝 과정에서 모델이 바뀔 수도 있다.
- 이력 데이터는 대량일 가능성이 높아 특별히 성능을 고려한다.
- PK/FK **칼럼 순서 조정**, **FK 인덱스 생성**도 중요하다.
- 처리량이 큰 테이블은 **접근 패턴에 맞는 인덱스·파티션 전략**을 먼저 검토한다.

### 슈퍼타입 · 서브타입 — 기출 1회 (2022 1)
- **공통 속성은 슈퍼타입, 유형별 속성은 서브타입**에 둔다. 공통 속성과 유형별 속성을 함께 관리할 때 쓴다.
- 슈퍼타입·서브타입의 **구분 속성**(예: 고객구분)을 **차별자**(Discriminator)라 한다.
- 관계: **배타적**(한 순간에 하나의 서브타입만) · **포괄적**(동시에 여러 서브타입 가능)
  - 함정: "고객 = 개인고객 또는 기업고객인데 동시에 둘 다 되는 포괄적 관계" → 틀림. **배타적** 관계다.
- **변환 방식**

| 방식 | 구조 | 적합한 경우 |
|------|------|-------------|
| **One To One** | 슈퍼·서브 각각 별도 테이블 | **개별 테이블 접근이 많을 때** |
| **Plus** | 서브마다 테이블, 슈퍼 공통 속성을 각 서브에 포함 | 슈퍼+서브를 묶어 처리할 때 |
| **Single** | 전체를 하나의 테이블로 통합 | 전체를 일괄 처리할 때 |

- 슈퍼·서브 엔터티를 **각각 테이블로 만들면 조인이 많아져** 조회가 느려질 수 있다.

### 분산 데이터베이스 · 파티션 — 기출 없음
- **장점**: **지역 자치성**, **점증적 시스템 용량 확장**, 빠른 응답 속도, 통신 비용 절감, 신뢰성·가용성 향상
- **단점**: **처리 비용 증가**, 오류의 잠재성 증대, 설계·관리 복잡, 데이터 무결성 보장이 어려움
  - 함정: "처리 비용의 감소" → 틀림. 여러 곳을 관리해야 해서 **처리 비용이 늘어난다**.
- **투명성 종류**: 분할 · 위치 · 지역 사상 · 중복 · 장애 · 병행

| 투명성 | 의미 |
|--------|------|
| **분할 투명성** | 하나의 테이블이 여러 조각으로 나뉘어 저장돼도 사용자는 모름 |
| **위치 투명성** | 데이터 **저장 장소를 명시할 필요가 없다**. 위치 정보는 시스템 카탈로그에 유지 |
| **지역 사상 투명성** | 지역 DBMS와 물리적 DB 사이의 매핑 보장. 지역 시스템 이름과 무관한 이름 사용 가능 |
| **중복 투명성** | 같은 데이터가 여러 곳에 중복 저장돼도 사용자는 모름 |
| **장애 투명성** | 일부 사이트·네트워크 장애에도 무결성 보장 |
| **병행 투명성** | 여러 트랜잭션이 동시에 수행돼도 결과 일관성 유지 |

  - 함정: "병렬 투명성", "이행 투명성" → 틀림. 없는 용어다.
- **파티션 종류**

| 파티션 | 기준 |
|--------|------|
| **Range** | 날짜·숫자처럼 **연속된 값의 범위** |
| **List** | **특정 값**을 지정 |
| **Hash** | 해시 함수 결과 |
| Composite | 여러 기법을 조합 (예: Range + Hash) |

### 트랜잭션 (모델링 관점) — 기출 2회 (2026 1 · 2024 1)
- 모델링 관점에서 트랜잭션은 **함께 처리되어야 하는 데이터의 논리적 범위를 하나의 단위로 규정해 무결성을 지키는 것**이다.
  - 예: 출금과 입금은 하나의 업무 흐름이라 나눠지면 안 됨
- 오답 보기와 구분하기: 아래는 물리적·기술적 특징이다.
  - "동시 접근해도 서로 간섭하지 않음" → 고립성
  - "전부 반영되거나 전부 취소됨" → 원자성
  - "백업·장애 복구" → 복구 기능
- 트랜잭션은 데이터 모델에 **표현할 수 있다**. 함정: "트랜잭션을 모델에 표현할 수 없다" → 틀림
- 두 엔터티의 관계가 **서로 필수적**이면 하나의 트랜잭션을 이룬다. 각자 **독립적으로 수행 가능**하면 **선택적 관계**로 표현한다.
  - 함정: "트랜잭션에 의한 관계는 선택적인 관계 형태를 가진다" → 틀림. **필수적 관계**다.
- 하나의 트랜잭션은 **부분 COMMIT이 불가**하다. A·B가 한 트랜잭션인데 A만 실행되고 장애가 나면 A를 **UNDO**해야 한다.
- **ACID**

| 특성 | 뜻 |
|------|----|
| **원자성**(Atomicity) | All or Nothing. 모두 성공하거나 모두 실행되지 않음. 일부만 반영되면 안 됨 |
| **일관성**(Consistency) | 실행 전 데이터가 올바르면 실행 후에도 올바름. DB가 **모든 무결성 제약을 만족**하는 유효한 상태 |
| **고립성·격리성**(Isolation) | 동시에 실행돼도 다른 트랜잭션의 영향을 받지 않음 |
| **영속성·지속성**(Durability) | 커밋된(성공한) 결과는 **영구 반영**. 시스템 재시작 후에도 롤백되지 않음 |

  - 함정: "상호성(Interactivity)" → 틀림. ACID가 아니다.
  - 함정: 일관성 자리에 영속성 설명, 영속성 자리에 일관성 설명을 넣은 보기 → 틀림
- **격리성이 낮을 때 생기는 문제**

| 현상 | 뜻 |
|------|----|
| **Dirty Read** | 다른 트랜잭션이 수정하고 **아직 커밋하지 않은** 데이터를 읽음 |
| **Non-Repeatable Read** | 같은 쿼리를 두 번 했는데 그 사이 다른 트랜잭션의 **수정·삭제**로 결과가 다름 |
| **Phantom Read** | 두 번째 조회에서 처음엔 없던 **유령 레코드**가 나타남 |

  - 함정: "Dirty Read는 이미 **커밋된** 데이터를 읽는 것" → 틀림
- **무결성 확보 방법**: 제약조건 · 트리거 · 애플리케이션 로직
  - 함정: "Lock(2PL)" → 틀림. **동시성 제어** 수단이라 무결성 확보 방법이 아니다.
- **무결성 종류**: **엔터티 무결성**(PK) · **참조 무결성**(FK) · **도메인 무결성**(타입·CHECK)

## 2과목 — SQL 기본 및 활용

### SQL 문장 분류 — 기출 13회 (2026 2 · 2025 2 · 2024 3 · 2023 3 · 2022 3)
| 분류 | 역할 | 명령어 |
|------|------|--------|
| DDL | 테이블 같은 **구조 정의·변경** | CREATE, ALTER, DROP, RENAME, TRUNCATE |
| DML | 데이터 **입력·변경·삭제·조회** | INSERT, UPDATE, DELETE, MERGE, (SELECT) |
| DCL | **권한** 부여·회수 | GRANT, REVOKE |
| TCL | **트랜잭션** 제어 | COMMIT, ROLLBACK, SAVEPOINT |

- 함정: "DCL은 테이블의 데이터를 변경한다" → 틀림. DML 설명이다.
- **TRUNCATE·RENAME은 DDL**이다. **MERGE는 DML**이다.
  - 함정: "DML: RENAME", "TRUNCATE는 DML" → 틀림
- 함정: "DCL은 데이터베이스 **구동·종료**를 수행한다" → 틀림. 구동·종료(STARTUP·SHUTDOWN)는 시스템 관리 명령이다. DCL은 **권한·보안 제어**다.
- SQL은 **선언적(비절차적)·집합적·구조적** 언어다. 무엇(WHAT)을 원하는지만 쓰고, 어떻게(HOW) 처리할지는 DBMS가 정한다.
  - 함정: "SQL은 절차적 언어이며 반복문을 포함한다" → 틀림. 절차적 처리는 PL/SQL·T-SQL의 영역이다.
- **비절차적 DML**: 사용자가 **무슨 데이터**를 원하는지만 명세한다. "어떻게 접근하는지"까지 명세하는 것은 **절차적 DML**이다.
  - 함정: "비절차적 DML은 무슨 데이터를 원하며 **어떻게** 접근해야 하는지 명세한다" → 틀림
- **데이터 부속어(Data Sub Language)**: 호스트 프로그램 속에 삽입되어 쓰이는 DML 명령어
- **절차형 SQL**로 만드는 것: **PROCEDURE**, **TRIGGER**, **사용자 정의 함수(UDF)**
  - 함정: "BUILT-IN FUNCTION(내장 함수)" → 틀림. 내장 함수는 DBMS가 이미 제공한다.

### 테이블 기본 — 기출 4회 (2026 1 · 2024 2 · 2023 1)
- 모든 자료는 실제로 **테이블에 저장**되고, 테이블에서 조회·수정·삭제한다.
- 데이터베이스에는 자료의 성격에 따라 **N개의 테이블**을 만든다. 테이블 하나에 몰아넣지 않는다.

- **테이블명·칼럼명 규칙**
  - 반드시 **문자로 시작**한다. (`100EMP`, `2023_TBL` → 불가)
  - 쓸 수 있는 것: A–Z, a–z, 0–9, `_`, `$`, `#`
  - **하이픈(`-`)은 불가** (`EMP-100` → 불가). `EMP100`, `TBL_2023#`은 가능하다.
  - **SQL 예약어(예: `table`)는 쓸 수 없다.**
  - 이름은 **대소문자를 구분하지 않는다**. 테이블명은 가능한 **단수형**을 쓴다.
  - 칼럼마다 **데이터 유형은 반드시** 지정한다.
- **소유자(스키마)가 다르면 같은 이름의 테이블**을 만들 수 있다. (예: `SCOTT.T1`과 `HR.T1`) 한 테이블을 두 계정이 동시에 소유할 수는 없다.
  - 두 스키마의 같은 이름 테이블을 함께 쓰면 **스키마명이나 별칭**으로 구분해야 한다.
  - 함정: `SELECT STADIUM.NAME FROM HR.STADIUM, SPORT.STADIUM` → 어느 테이블인지 모호해서 틀림
- **키 종류**
  - 수퍼키: 유일성만 만족
  - **후보키**: **유일성 + 최소성**
  - 기본키: 후보키 중에서 고른 하나
  - 대체키: 기본키로 뽑히지 않은 나머지 후보키
  - 외래키: 다른 테이블의 키를 참조
- SQL의 주요 기능은 정의(DDL)·조작(DML)·제어(DCL)다. UI 디자인 같은 건 해당하지 않는다.

### 데이터 타입·암시적 변환 — 기출 3회 (2026 1 · 2025 1 · 2024 1)
| 타입 | 특징 |
|------|------|
| `CHAR(n)` | **고정 길이 문자**. 값이 짧으면 나머지를 **공백으로 채운다** |
| `VARCHAR2(n)` / `VARCHAR` | **가변 길이 문자**. 최대 n바이트까지 저장 |
| `NUMBER(p, s)` | 숫자. `NUMBER(5,2)` → 전체 5자리 중 소수 2자리(정수 3자리). 크기 생략 가능 |
| `DATE` | **날짜 + 시간(시·분·초)**까지 저장 |

- 문자형은 **최대 크기를 지정**한다. **날짜형은 크기를 지정하지 않는다.**
- 함정: "VARCHAR는 가변 길이 숫자형" → 틀림. **문자형**이다.
- 함정: "DATE는 날짜만 저장하고 시간은 따로 저장해야 한다" → 틀림
- 숫자형이 아닌 것 고르기: `DECIMAL`, `FLOAT`, `INT`는 숫자형, **`CHAR`는 문자형**
- `NUMBER(5,2)`에 값 넣기: **정수부는 최대 3자리**
  - `1234.5` → 오류. `123.456` → 소수 둘째 자리로 반올림되어 저장
- **문자 비교 규칙**

| 비교 대상 | 길이가 다를 때 |
|-----------|----------------|
| 양쪽 모두 **CHAR** | 짧은 쪽에 **공백(SPACE)을 채워** 길이를 맞춘 뒤 비교 |
| 한쪽이라도 **VARCHAR** | 서로 다른 문자가 나올 때까지 비교. 짧은 쪽이 끝날 때까지 같으면 **길이가 긴 쪽이 크다** |

  - 함정: VARCHAR 비교에서 "작은 쪽에 SPACE를 추가해 길이를 맞춘다" → 틀림. CHAR끼리 비교할 때의 규칙이다.
- **암시적(묵시적) 형변환**: 숫자로 바꿀 수 있는 문자는 산술 연산 때 자동으로 숫자가 된다.
  - 예: `'0050' + 25` → **75** (문자 `'75'`나 `5025`가 아님)
  - 예: `10 + '90'` → 100, `100 + '1'` → 101
- 날짜 포맷 **`RR`과 `YY`** (두 자리 연도)
  - `RR`: 00~49 → **2000년대**, 50~99 → **1900년대** (현재가 2000년대 전반일 때)
  - `YY`: 항상 **현재 세기**
  - 예: 주민번호 앞자리 `751023`을 `RR`로 변환 → **1975-10-23**, `YY`로 변환 → 2075-10-23

### 문자열 리터럴 — 기출 1회 (2025 1)
- Oracle 문자열 안에서 작은따옴표를 쓰려면 **두 번 연속(`''`)** 쓴다. `''` 하나가 `'` 한 글자가 된다.
  - 예: `'''''A'''''` → 바깥 양 끝은 구분자, 안쪽 `''''`는 `''`(작은따옴표 2개) → 결과 **`''A''`**

### ALTER TABLE 문법 — 기출 8회 (2026 2 · 2025 1 · 2024 2 · 2023 3)
| 작업 | Oracle | SQL Server |
|------|--------|------------|
| 칼럼 추가 | `ALTER TABLE T ADD 칼럼 타입` / `ADD (칼럼 타입, …)` | `ALTER TABLE T ADD 칼럼 타입` |
| 칼럼 변경 | `ALTER TABLE T MODIFY 칼럼 타입` / `MODIFY (칼럼 타입)` | `ALTER TABLE T ALTER COLUMN 칼럼 타입` |
| 칼럼 삭제 | `ALTER TABLE T DROP COLUMN 칼럼` | 같음 |

- 함정: Oracle에서 `ADD COLUMN` → 오류. `COLUMN` 키워드를 쓰지 않는다.
- 함정: `CHANGE`(MySQL), `ALTER COLUMN`(SQL Server), `UPDATE TABLE` → Oracle에서 오류
- SQL Server `ALTER COLUMN`은 **한 문장에 한 칼럼**만 바꾼다. 괄호로 여러 칼럼을 묶을 수 없다. NOT NULL도 다시 적어야 유지된다.
- `MODIFY`로 타입과 함께 `DEFAULT`·`NOT NULL`을 지정할 수 있다.
- 칼럼의 데이터 유형은 생성 후에도 **ALTER로 변경**할 수 있다.
- **제약조건 추가·삭제**
  - 추가: `ALTER TABLE EMP ADD CONSTRAINT FK_DEPT FOREIGN KEY (DEPTNO) REFERENCES DEPT(DEPTNO)`
  - FK 삭제: `ALTER TABLE EMP DROP CONSTRAINT 제약명`
  - `DROP PRIMARY KEY`는 Oracle에서 된다. `DROP FOREIGN KEY`는 **MySQL 문법**이라 Oracle에서 오류다.
- **CREATE TABLE 안에서 제약 선언**: `CONSTRAINT PK명 PRIMARY KEY (칼럼)` (테이블 수준)
  - 함정: CREATE TABLE 안에 `ADD CONSTRAINT`를 쓰면 오류. `ADD`는 ALTER TABLE에서만 쓴다.
- **변경 가능 여부**

| 작업 | 결과 |
|------|------|
| 칼럼 추가 (NULL 허용) | 항상 가능 |
| 데이터가 있는 테이블에 **DEFAULT 없이 NOT NULL 칼럼 추가** | **오류**. 기존 행에 NULL이 들어가기 때문 |
| DEFAULT와 함께 칼럼 **추가** | 기존 행의 새 칼럼에도 **DEFAULT 값이 채워짐** |
| 기존 칼럼의 DEFAULT **변경** | **이후 입력분에만** 적용. 기존 데이터에 소급 안 됨 |
| 칼럼 크기 늘리기 | 언제든 가능 |
| 칼럼 크기 줄이기 | 교재: 행이 없거나 **NULL만 있을 때** 가능. 실제 Oracle은 **저장된 값의 최대 길이까지는** 줄일 수 있다 |
| 데이터 타입 변경 | 원칙적으로 칼럼에 **NULL만 있을 때** 가능 |
| DATE → TIMESTAMP 변경 | 가능 (호환 변환) |
| 이미 NULL이 있는 칼럼에 NOT NULL 추가 | **오류**. DBMS가 데이터를 바꾸거나 지우지 않는다. 기존에 NULL이 없으면 `MODIFY`로 추가 |
| 중복 값이 있는 칼럼에 PK 추가 | 오류 |

- 함정: "칼럼 크기는 늘릴 수만 있다" → 틀림. 조건을 만족하면 줄일 수 있다.
- 함정: "DEFAULT를 설정하면 전체 성능이 떨어진다" → 틀림. 성능과 직접 관련 없다.
- 함정: "DEFAULT 때문에 값을 입력해도 기본값이 들어간다" → 틀림. 값을 **지정하지 않았을 때만** 적용된다.

### DELETE · TRUNCATE · DROP — 기출 10회 (2026 1 · 2025 2 · 2024 4 · 2023 2 · 2022 1)
| 구분 | DELETE | TRUNCATE | DROP |
|------|--------|----------|------|
| 분류 | DML | DDL | DDL |
| 커밋 | 사용자 COMMIT 필요 | **Auto Commit** | Auto Commit |
| ROLLBACK | 가능 (COMMIT 전) | 불가 | 불가 |
| WHERE | 가능 | **불가** (전체 삭제만) | — |
| 구조 | 유지 | 유지 (**초기 상태**, 저장 공간 반환) | **정의까지 삭제** |
| 로그 | 행 단위 로그·UNDO 생성 | UNDO 생성 안 함 → 대량 삭제 시 **더 빠름** | — |

- 함정: "WHERE 없는 DELETE는 DROP TABLE과 같은 결과" → 틀림. 구조가 남는다.
- 함정: "DELETE와 TRUNCATE는 사용자 COMMIT으로 수행" → 틀림. TRUNCATE도 Auto Commit이다.
- 함정: "TRUNCATE는 행마다 로그를 남겨 DELETE보다 느리다" → 틀림
- 구조는 남기고 행만 지우는 명령: **DELETE, TRUNCATE**
- **삭제 로그를 남겨야** 하거나 일부 행만 지울 때는 DELETE를 쓴다. 로그 없이 전체를 빠르게 비울 때는 TRUNCATE다.
- `DELETE * FROM T` → 문법 오류. Oracle은 `DELETE T`처럼 **FROM 생략이 가능**하다.
- 순서 함정: DELETE → ROLLBACK(복구) → TRUNCATE → ROLLBACK이면, TRUNCATE가 자동 커밋되어 **0건**이 된다.
- **DROP 옵션**
  - `DROP TABLE T CASCADE CONSTRAINTS`: T를 지우면서 **T를 참조하는 다른 테이블의 FK 제약만** 함께 삭제한다. 자식 테이블 자체는 남는다.
  - `DROP ... RESTRICT`(표준 SQL): 참조하는 객체(뷰 등)가 있으면 **삭제를 거부**한다. 아무것도 삭제되지 않는다.
  - `DROP USER 사용자 CASCADE`: 그 사용자가 소유한 **모든 객체까지** 함께 삭제한다. 옵션 없이 객체가 있으면 삭제가 거부된다.

### 제약 조건 — 기출 15회 (2026 3 · 2025 3 · 2024 4 · 2023 3 · 2022 2)
| 제약 조건 | 역할 |
|-----------|------|
| PRIMARY KEY | 유일 + NOT NULL. 테이블당 1개 |
| UNIQUE | 유일. NULL은 허용 |
| NOT NULL | NULL 금지 |
| **CHECK** | 값의 범위·목록 제한 (예: 성별은 'M', 'F'만) |
| FOREIGN KEY | 다른 테이블의 PK·UK 참조 |

- **PRIMARY KEY**
  - **PK = UNIQUE + NOT NULL**이다. 함정: "PK는 고유키 + 외래키" → 틀림
  - **기본키는 테이블당 하나**다. 여러 칼럼으로 만든 복합키도 **하나의 PK 제약**이다.
  - PK를 만들면 **인덱스가 자동 생성**된다. PK 칼럼에 NOT NULL을 따로 지정하지 않아도 된다.
- **UNIQUE**
  - **UNIQUE는 NULL을 여러 개 허용**한다. ("NULL이 여러 개면 위반" → 틀림)
  - 한 테이블에 **여러 개** 정의할 수 있고, **인덱스가 자동 생성**된다. NOT NULL이 자동으로 붙지 않는다.
  - **복합 UNIQUE (A, B)**: **조합 전체**가 같을 때만 위반이다. A만 같거나 B만 같으면 허용된다.
  - **이미 NULL이 있어도 중복만 없으면** UNIQUE 제약을 추가할 수 있다.
- **FOREIGN KEY**
  - **FK도 NOT NULL 제약이 없으면 NULL을 허용**한다.
  - **FK는 한 테이블에 여러 개** 둘 수 있다.
    - 함정: "FK는 한 테이블에 하나만 존재한다", "FK 값은 NULL을 가질 수 없다" → 둘 다 틀림
  - **복합 칼럼**으로도 정의할 수 있고, **같은 테이블**을 참조할 수도 있다(자기 참조).
  - FK는 **자식 테이블**에 만든다. CASCADE 옵션도 자식 FK에 지정한다.
  - FK가 참조하는 **부모 테이블의 참조 칼럼은 삭제할 수 없다**.
- **CHECK**
  - CHECK 식은 TRUE/FALSE로 판별할 수 있어야 한다.
  - CHECK는 **입력 전에** 검사한다. 제약을 위반한 문장만 실패하고 테이블에는 반영되지 않는다. 앞뒤의 정상 문장은 반영된다.
- 제약조건을 추가할 때 **이름은 생략**할 수 있다. (`CONSTRAINT 이름`은 선택)
- **참조 무결성**
  - 부모 테이블에 새 행을 넣는 건 자유다. 위배되지 않는다.
  - 자식이 참조 중인 부모 행을 지우면 위배된다.
    - FK가 NULL 허용이어도 이미 부모를 참조 중인 자식이 있으면, CASCADE 없이 **부모 삭제가 거부**된다.
  - 부모에 없는 값으로 자식 행을 넣으면 위배된다.
  - 자식 행의 **FK 칼럼 값을 부모에 없는 값으로 UPDATE**해도 위배다. FK와 무관한 칼럼 수정은 괜찮다.
  - **FK 제약이 없는 칼럼**은 다른 테이블에 없는 값을 넣어도 **참조 무결성과 무관**하다. 참조 무결성은 FK가 정의된 경우에만 적용된다.
- **FK 삭제·수정 옵션**
  - `ON DELETE CASCADE`: 부모를 삭제하면 자식도 함께 삭제된다.
  - `ON DELETE SET NULL`: 부모를 삭제하면 자식의 FK가 NULL이 된다.
  - 기본(RESTRICT·NO ACTION): 자식이 있으면 부모를 삭제할 수 없다.
  - **`ON UPDATE CASCADE`**: 부모 키 값을 바꾸면 자식 FK 값도 함께 바뀐다.
  - **CASCADE 연쇄**: T → S가 CASCADE, S → R이 SET NULL이면, T를 삭제할 때 S 행은 삭제되고 R의 FK는 NULL이 된다.
- **참조 동작 — 입력(INSERT) 쪽**

| 동작 | 자식 입력 시 |
|------|-------------|
| **Dependent** | 부모에 PK가 **있을 때만** 자식 입력 허용 |
| Automatic | 부모 PK가 없으면 부모를 먼저 만들고 자식 입력 |
| Set Null / Set Default | 부모가 없으면 자식 FK를 NULL / 기본값으로 입력 |
| No Action | 참조 무결성을 위반하는 입력만 막음 |

  - 삭제 쪽 동작(Cascade, Set Null, Restrict 등)과 헷갈리지 않는다.

### 무결성 종류 — 기출 4회 (2026 1 · 2024 1 · 2022 2)
| 무결성 | 구현 수단 | 위반 예 |
|--------|----------|--------|
| **개체 무결성** | PRIMARY KEY | PK에 NULL·중복 |
| **참조 무결성** | FOREIGN KEY | 부모에 없는 값으로 자식 입력 |
| **도메인 무결성** | 데이터 타입, CHECK | 허용 범위를 벗어난 값 |

- 참조 무결성: 자식의 FK 값은 **부모 PK에 존재하거나 NULL**이어야 한다.

### CTAS — 기출 5회 (2026 1 · 2025 1 · 2024 2 · 2022 1)
- `CREATE TABLE 새테이블 AS SELECT …`
- **복사되는 것**: 칼럼 **순서·데이터 타입**, 칼럼에 직접 건 **NOT NULL** 제약, 데이터
- **복사되지 않는 것**: PK, UNIQUE, FK, CHECK, **DEFAULT**, 인덱스
  - 함정: "NOT NULL은 전달되지 않는다", "CHECK·DEFAULT는 전달된다", "제약조건이 모두 복사된다" → 틀림
  - 그래서 복제본에는 PK 중복이나 CHECK 위반 값도 들어간다. **NOT NULL 위반만 오류**다.
- `WHERE 1 = 2`를 붙이면 데이터 없이 **구조만** 복제한다.
- 빠진 제약은 ALTER TABLE로 따로 추가한다.

### INSERT 문법 — 기출 6회 (2026 2 · 2024 1 · 2023 2 · 2022 1)
- **칼럼 목록을 생략**하면 테이블의 **모든 칼럼 값을 순서대로** 다 적어야 한다. 하나라도 모자라면 오류다.
- INSERT에서 칼럼을 빼면 DEFAULT 값이, DEFAULT가 없으면 NULL이 들어간다. 그 칼럼이 NOT NULL이면 **오류**가 난다.
- **INSERT가 실패하는 대표 원인**
  - 칼럼 수와 값 수 **불일치**
  - 정의한 **길이 초과** (예: `VARCHAR2(5)`에 6글자)
  - **데이터 타입 불일치** (예: 문자 칼럼 자리에 날짜를 넣어 변환 실패)
  - `NOT NULL` 칼럼에 NULL
  - **PK 값 누락**
- **서브쿼리로 삽입**: `INSERT INTO 테이블 SELECT …` (`AS` 없음)
  - 함정: `INSERT INTO T AS SELECT …` → 오류. `AS SELECT`는 CTAS 문법이다.
  - 함정: `INSERT INTO T VALUES (SELECT …)` → 오류
  - `INSERT INTO T (SELECT …)`처럼 괄호로 감싸는 것은 가능하다.
  - 두 테이블의 칼럼 수가 다르면 SELECT 쪽에서 `NULL` 등으로 개수를 맞춘다.
- **DATE 칼럼에 값 넣기**
  - `SYSDATE`, `TO_DATE('2024-06-06','YYYY-MM-DD')`, `DATE '2024-06-06'` → 정상
  - **숫자 리터럴**(`20240606`) → 타입 불일치 오류
  - 문자열(`'2024/01/01'`) → 세션의 **기본 날짜 포맷과 다르면 오류**가 날 수 있다.
- **다중 테이블 INSERT** (Oracle)

| 구문 | 동작 |
|------|------|
| `INSERT ALL WHEN … THEN INTO …` | 조건을 만족하는 **모든 WHEN**에 삽입 |
| `INSERT FIRST WHEN … THEN INTO …` | **처음 만족한 WHEN 하나**에만 삽입. 뒤 조건은 평가 안 함 |
| `ELSE INTO …` | **어떤 WHEN도 만족하지 않은 행**만 삽입 |

- 예: 값 1, 2, 5 / 조건 `>= 2` → T1, `>= 5` → T2, ELSE → T3
  - FIRST: T1 = 2, T2 = 0, T3 = 1
  - ALL: T1 = 2, T2 = 1, T3 = 1

### UPDATE · DELETE 함정 — 기출 3회 (2025 1 · 2024 1 · 2023 1)
- **WHERE 없는 UPDATE + 상관 서브쿼리**: 모든 행이 갱신 대상이다. 서브쿼리에 맞는 행이 없는 행은 **NULL로 덮어써진다**(기존 값이 유지되지 않음).
  - 그래서 일부 행만 바꾸려면 `WHERE 키 IN (SELECT 키 FROM 원본)`처럼 **갱신 범위를 WHERE로 제한**해야 한다.
- **집계 서브쿼리는 행이 없어도 1행(NULL)을 반환**한다.
  - `SET 칼럼 = (SELECT MAX(NULL) FROM …)` → 조건과 무관하게 항상 NULL → `SET 칼럼 = NULL`과 같다.
  - `COALESCE(MAX(NULL), 0)` → 0이 되므로 다르다.
- **상관되지 않은 EXISTS**: 서브쿼리가 메인 행을 참조하지 않으면, 결과가 한 건이라도 있을 때 **모든 행에 대해 참**이다. 전체 행이 갱신된다.
- `SET 칼럼 = (단일 행 서브쿼리)`에서 서브쿼리가 **2행 이상**을 반환하면 오류다. 동명이인처럼 중복 가능성이 있으면 `WHERE 키 IN (서브쿼리)`를 쓴다.
  - 서브쿼리 검색 칼럼에 **UNIQUE** 제약이 있으면 항상 1건 이하가 보장된다. (NOT NULL로는 보장 안 됨)
- UPDATE는 `SET A = 1, B = 2`처럼 **여러 칼럼을 동시에** 수정할 수 있다.
- **그룹별 최소 ID만 남기고 중복 삭제**: `DELETE FROM T WHERE ID NOT IN (SELECT MIN(ID) FROM T GROUP BY NAME)`
  - 함정: `DELETE … GROUP BY … HAVING`, `WHERE ID = MIN(ID)` → 오류
- 부모에 없는 자식 행 삭제: `DELETE FROM EMP WHERE DEPTNO NOT IN (SELECT DEPTNO FROM DEPT)`. DEPT.DEPTNO가 PK라 NULL 걱정이 없다.

### MERGE — 기출 8회 (2026 3 · 2025 2 · 2024 1 · 2023 1 · 2022 1)
- ON 조건이 맞으면 `WHEN MATCHED THEN UPDATE`(+ `DELETE`), 안 맞으면 `WHEN NOT MATCHED THEN INSERT`. 한 문장으로 **INSERT·UPDATE·DELETE**를 처리한다(DML).
- 대상에만 있고 원본에 없는 행은 **변경 없이 그대로** 남는다.
- **WHEN MATCHED와 WHEN NOT MATCHED는 하나만 써도 된다.**
  - 함정: "둘 다 반드시 명시해야 한다" → 틀림
- **ON 절에 쓴 조인 칼럼은 UPDATE SET으로 바꿀 수 없다.** (오류)
  - 함정: "ON 절 칼럼 값도 수정할 수 있다" → 틀림
- ON 조건이 항상 거짓이어도 오류가 아니다. NOT MATCHED(INSERT)만 수행된다.
- **`DELETE WHERE`**: MATCHED에서 **UPDATE된 행 중** 조건을 만족하는 행만 삭제한다. 갱신 **후** 값으로 판단한다.
  - 원본과 매칭되지 않은 대상 행은 DELETE 대상이 아니다.
- MATCHED의 UPDATE에 없는 칼럼은 기존 값이 유지된다. NOT MATCHED의 INSERT는 적은 값으로 새 행을 만든다.
- **원본에서 대상 한 행에 2건 이상 매칭**되면 어느 값으로 갱신할지 정할 수 없어 **오류**가 난다. 원본 키를 미리 유일하게 만든다.
- SELECT 후 분기하는 방식보다 I/O 효율이 좋다.

### TCL과 트랜잭션 흐름 — 기출 15회 (2026 2 · 2025 3 · 2024 3 · 2023 4 · 2022 3)
- 트랜잭션: 데이터베이스의 **논리적 업무 최소 단위**(분리할 수 없는 작업 단위)
- **COMMIT**: 변경 내용을 영구 저장
- **ROLLBACK**: 직전 COMMIT 이후의 변경을 모두 취소
- **SAVEPOINT 이름** / **ROLLBACK TO 이름**: 저장점까지만 부분 취소
- **저장점 규칙**
  - **COMMIT하면 그 이전의 SAVEPOINT는 모두 사라진다.** 그 뒤 `ROLLBACK TO 저장점`을 하면 **그 문장만 오류**가 나고 아무것도 취소되지 않는다. 트랜잭션은 계속 유지된다.
    - 함정: "COMMIT 이전 저장점으로 ROLLBACK하면 COMMIT 이후까지만 취소된다" → 틀림. **오류**가 난다.
  - `ROLLBACK TO A`를 하면 A **이후에 만든 저장점(B 등)도 함께 사라진다.** 이후 `ROLLBACK TO B`는 오류다.
  - **같은 이름의 SAVEPOINT를 다시 선언**하면 이전 것은 사라지고 **마지막(뒤쪽) 위치**가 그 이름의 저장점이 된다.
  - ROLLBACK한 것을 다시 ROLLBACK으로 취소할 수 없다.
- Oracle에서는 **DDL(CREATE 등)을 실행하면 자동 COMMIT**된다.
  - 예: 작업1 → CREATE TABLE → 작업3 → ROLLBACK 순서면, 작업1과 CREATE TABLE은 유지되고 **작업3만 취소**된다.
  - ALTER TABLE ADD·DROP COLUMN, TRUNCATE도 DDL이다. 그 직전까지의 미커밋 DML이 확정되어 이후 ROLLBACK으로 취소되지 않는다.
  - 함정: "Oracle에서 UPDATE → CREATE TABLE → ROLLBACK 후 테이블이 생성되지 않았다" → 틀림. UPDATE와 테이블 모두 **유지**된다.
- DDL 자동 COMMIT은 **DBMS마다 다르다.**

| 구분 | Oracle | SQL Server |
|------|--------|------------|
| DDL 실행 | 자동 COMMIT. ROLLBACK해도 생성된 테이블·앞의 DML 유지 | DDL도 트랜잭션에 포함(AUTO COMMIT FALSE일 때). ROLLBACK하면 앞의 UPDATE와 **CREATE까지 취소** |
| 저장점 문법 | `SAVEPOINT 이름` / `ROLLBACK TO 이름` | `SAVE TRAN 이름` / `ROLLBACK TRAN 이름` |

- **COMMIT 전 상태**
  - 본인 세션: SELECT로 변경 내용을 볼 수 있고 계속 수정할 수 있다.
  - 다른 사용자: 변경 내용을 **볼 수도, 수정할 수도 없다**(변경된 행에 잠금).
  - 함정: "다른 사용자가 커밋 전 데이터를 수정할 수 있다" → 틀림
- **COMMIT 후 상태**: 영구 저장, **잠금 해제**, **모든 사용자가 조회** 가능, 이전 데이터로 되돌릴 수 없음
  - 함정: "COMMIT한 사용자만 결과를 볼 수 있다" → 틀림
- **Lock 대기**: 같은 행을 두 트랜잭션이 UPDATE하면 뒤 트랜잭션은 **배타적 Lock** 때문에 **대기**한다. 앞 트랜잭션이 COMMIT한 **바뀐 값을 읽어** 이어서 처리한다.
  - 예: 1000 → TX1이 +100 후 COMMIT, 대기하던 TX2가 +200 → **1300**
- **COMMIT·ROLLBACK의 장점**: 데이터 무결성 보장, 영구 반영 전 변경 확인, 연관 작업을 묶어서 처리
  - 함정: "영구적인 변경을 할 수 없게 한다" → 틀림
- 풀이 요령: COMMIT 지점, SAVEPOINT 위치, 최종 ROLLBACK 범위를 시간순으로 표시하고 남는 변경만 계산한다.

### 트랜잭션 특성(ACID)·격리 수준 — 기출 10회 (2026 2 · 2025 3 · 2024 2 · 2023 2 · 2022 1)
| 특성 | 의미 |
|------|------|
| **원자성** | 전부 반영되거나 전부 취소 (All or Nothing) |
| **일관성** | 트랜잭션 전후로 데이터 정합성(무결성) 유지 |
| **고립성(격리성)** | 다른 트랜잭션의 중간 결과에 영향받지 않음 |
| **지속성** | COMMIT된 결과는 장애에도 영구 보존 |

- 함정: "통합성", "중복성"은 트랜잭션 특성이 아니다.
- 함정: "성공한 변경이 영구 저장되는 것을 고립성이라 한다" → 틀림. **지속성**이다.
- 커밋되지 않은 다른 트랜잭션의 값을 읽었다(Dirty Read) → **고립성 위반**
- **격리 수준과 발생 현상**

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|-----------|-----------|---------------------|--------------|
| Read Uncommitted | 발생 | 발생 | 발생 |
| Read Committed | 방지 | 발생 | 발생 |
| Repeatable Read | 방지 | 방지 | **발생 가능** |
| Serializable | 방지 | 방지 | 방지 (동시성 가장 낮음) |

- 함정: "Repeatable Read는 Phantom Read가 절대 발생하지 않는다" → 틀림. 신규 INSERT는 막지 못한다.
- **Lock은 동시성(병행) 제어** 수단이다. 무결성 보장 수단은 **제약조건·트리거·애플리케이션 로직**이다.

### DCL — 권한 부여·회수 — 기출 9회 (2026 2 · 2025 2 · 2024 1 · 2023 3 · 2022 1)
- 부여: `GRANT 권한 ON 객체 TO 사용자;`
  - 예: `GRANT SELECT, UPDATE ON A_USER.TB_A TO B_USER;`
- 회수: `REVOKE 권한 ON 객체 FROM 사용자;` (TO가 아니라 **FROM**)
- `ON 객체`를 빠뜨리면 오류가 난다. (`GRANT 권한 TO 사용자` → 오류)
- 시스템 권한 부여 예: `GRANT CREATE TABLE TO AAA;`
- WHERE 조건이 있는 **UPDATE를 하려면 SELECT 권한도 필요**하다. 조건을 평가하려면 읽어야 하기 때문이다.
- `DENY`는 SQL Server 전용이다.
- **다른 유저의 테이블**은 소유자에게 권한을 받기 전에는 조회할 수 없다.
- 유저를 만들어도 바로 로그인할 수는 없다. 접속 권한(CREATE SESSION)을 따로 받아야 한다.
- 권한 부여·회수는 **즉시 반영**된다. 재접속하지 않아도 된다.
- **권한 부여 주체**: DBA만 GRANT할 수 있는 게 아니다. **객체 소유자**는 자기 테이블 권한을 줄 수 있고, `WITH GRANT OPTION`으로 받은 사용자도 재부여할 수 있다.
  - 함정: "GRANT는 반드시 DBA만 사용할 수 있다" → 틀림
- **재부여 옵션**
  - **`WITH GRANT OPTION`**: 받은 **객체 권한**을 **제3자에게 다시 부여**할 수 있게 한다.
  - **`WITH ADMIN OPTION`**: **시스템 권한·롤**을 재부여할 수 있게 한다.
- **연쇄 회수 비교**

| 부여 방식 | 대상 | 중간 사용자 권한을 회수하면 |
|-----------|------|---------------------------|
| `WITH GRANT OPTION` | 객체 권한 | 제3자에게 준 권한도 **함께 회수** |
| `WITH ADMIN OPTION` | 시스템 권한·롤 | 제3자 권한은 **유지** |

- WITH GRANT OPTION으로 전파된 제3자 권한은 원 부여자가 **직접 회수할 수 없다.** 중간 사용자를 회수해야 연쇄로 사라진다.
- `REVOKE … CASCADE`: 재부여된 권한까지 함께 회수
- `REVOKE … RESTRICT`(표준 SQL): 재부여된 권한이 있으면 **REVOKE가 거부**되어 모두의 권한이 그대로 유지된다.
- 권한은 **일부만** 회수할 수 있다. (`REVOKE INSERT` → INSERT만 회수, SELECT 유지)
- **ROLE**: 권한의 묶음. GRANT·REVOKE로 똑같이 관리한다.
  - 롤을 다른 롤에 부여할 수 있다. 롤을 **DROP ROLE**하면 그 롤을 거쳐 받은 권한도 모두 사라진다.
  - 권한을 회수할 때는 **그 권한을 가진 롤**에서 회수하면 된다. 롤에서 회수하면 그 롤을 받은 유저도 **즉시** 권한을 잃는다.
- **SYNONYM은 별칭일 뿐** 권한을 자동으로 주지 않는다.

### 뷰(VIEW) — 기출 6회 (2026 1 · 2024 1 · 2023 4)
- 뷰는 **SELECT 정의만** 데이터 사전에 저장하는 **가상(논리) 테이블**이다. 데이터·저장 공간·인덱스를 갖지 않는다.
  - 조회할 때마다 **기본 테이블을 참조**한다. 그래서 기본 테이블 데이터가 바뀌면 뷰 조회 결과도 바뀐다.
  - 실제 데이터를 저장하는 것은 **구체화된 뷰(Materialized View)**다. 이를 지원하는 DBMS도 있다.
- 장점: **독립성**(테이블 구조가 바뀌어도 응용 프로그램은 그대로), **편리성**(복잡한 질의 단순화), **보안성**(원본 테이블을 숨기고 필요한 칼럼만 노출)
- 함정: "뷰는 조회 성능을 높이려고 쓴다" → 틀림. 조회할 때마다 정의된 쿼리가 실행된다.
- 함정: "테이블 구조가 바뀌면 뷰를 쓰는 응용 프로그램도 고쳐야 한다" → 틀림 (독립성)
- 함정: "논리적 데이터 독립성을 제공하지 않는다" → 틀림
- 뷰는 데이터 보정·처리 과정 시험 같은 **임시적인 작업** 용도다. ("영구적인 작업" → 틀림)
- **뷰를 기반으로 또 다른 뷰를 만들 수 있다.** ("생성 불가" → 틀림)
- 뷰 정의에 **WHERE**를 쓸 수 있다. 뷰 조건과 바깥 조회 조건은 **AND로 결합**되어 적용된다.
- 기본 테이블이 **삭제되면 뷰는 남지만 실행 시 오류**가 난다. 기본 테이블 구조가 바뀌어도 오류가 날 수 있다(뷰는 기본 테이블 정의에 의존).
- 뷰 정의는 **ALTER로 바꿀 수 없다.** `CREATE OR REPLACE VIEW`로 다시 만든다.
- **단순 뷰**(단일 테이블)는 DML이 가능하다. **조인·집계·GROUP BY가 있는 복합 뷰**는 원본 행과 1:1로 대응하지 않아 INSERT·UPDATE 등 DML 제약이 크다.
- **WITH CHECK OPTION**: 뷰 조건을 **벗어나는 값으로 INSERT·UPDATE하는 것을 막는다**.

### 시퀀스 · 프로시저 · 트리거 — 기출 1회 (2022 1)
- **시퀀스**는 트랜잭션과 **독립적**이다. ROLLBACK해도 이미 뽑은 번호는 되돌아가지 않는다(**결번** 발생).
  - `NEXTVAL`: 호출할 때마다 INCREMENT BY만큼 증가
  - `CURRVAL`: 현재 세션에서 NEXTVAL을 **한 번 이상 호출한 뒤**에만 참조 가능
  - `CACHE`: 메모리에 미리 할당해 빠르지만, 비정상 종료 시 결번이 생길 수 있다.
- **저장 프로시저**: 미리 만든 SQL 묶음. 네트워크 트래픽을 줄이고 성능을 높인다. 안에서 COMMIT·ROLLBACK을 쓸 수 있다.
- **트리거**: DML 이벤트에 자동 실행된다. **안에서 COMMIT·ROLLBACK을 쓸 수 없다.** 호출한 트랜잭션의 일부로 동작하기 때문이다.
  - 함정: "프로시저와 트리거 모두에서 COMMIT·ROLLBACK을 쓸 수 있다" → 틀림
- **사용자 정의 함수**는 반드시 **RETURN**으로 값을 돌려준다.

### SELECT 문 실행 순서 — 기출 5회 (2026 2 · 2025 1 · 2024 1 · 2023 1)
- 논리적 실행 순서: **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY**
  - SELECT 절은 **마지막이 아니다**. 가장 마지막은 ORDER BY다. ("SELECT 절이 가장 마지막에 실행된다" → 틀림)
  - 함정: "FROM → WHERE → GROUP BY → HAVING → ORDER BY → SELECT" → 틀림
- 이 순서에서 나오는 규칙
  - WHERE는 SELECT보다 먼저라 **SELECT 별칭을 못 쓴다**. ORDER BY는 SELECT 뒤라 쓸 수 있다.
  - WHERE는 GROUP BY보다 먼저라 **집계 함수를 못 쓴다**. 집계 조건은 HAVING에 쓴다.
- WHERE는 **행 단위** 필터(그룹 만들기 전), HAVING은 **그룹 단위** 필터(그룹 만든 후)다.
  - 함정: "HAVING은 GROUP BY 이전에 행을 제거한다" → 틀림
  - 예: "2000년 이후 10권 이상 발행한 출판사" → `WHERE 발행연도 >= 2000 GROUP BY 출판사명 HAVING COUNT(도서번호) >= 10`
- 작성 순서: `WHERE`는 `ORDER BY` 뒤에 올 수 없다. (문법 오류)
- `DISTINCT`는 항상 **SELECT 바로 뒤**에 온다.
  - `SELECT UNIQUE 칼럼`: Oracle에서 **DISTINCT와 같은 동작**이다. 표준 키워드는 DISTINCT다.
- Oracle에서 **FROM 절은 생략할 수 없다**. 그래서 `FROM DUAL`을 쓴다. ("FROM 절은 모든 DBMS에서 생략 가능" → 틀림)

### WHERE 조건 · 연산자 우선순위 — 기출 15회 (2026 3 · 2025 3 · 2024 3 · 2023 3 · 2022 3)
- 우선순위: **괄호** → 산술 → 비교 연산자 → `NOT` → **`AND`** → `OR`. 괄호가 가장 높고, AND가 OR보다 먼저 묶인다.
- 예: "2014년 11~12월 + 2015년 1~3월" 조건
  - 정답: `년='2014' AND 월 BETWEEN '11' AND '12' OR 년='2015' AND 월 BETWEEN '01' AND '03'`
  - 오답: 연도와 월을 따로 묶으면 2014년 1~3월, 2015년 11~12월까지 섞여 들어간다.
- 같은 함정의 다른 예: `V1='A' AND V2='T1' OR V2='T2'`는 `(V1='A' AND V2='T1') OR V2='T2'`로 해석된다. 그래서 V1이 'A'가 아닌 행도 섞인다.
- **3값 논리(TRUE·FALSE·UNKNOWN)**

| 식 | 결과 |
|----|------|
| `FALSE AND UNKNOWN` | **FALSE** |
| `TRUE AND UNKNOWN` | UNKNOWN |
| `TRUE OR UNKNOWN` | **TRUE** |
| `FALSE OR UNKNOWN` | UNKNOWN |
| `NOT UNKNOWN` | **UNKNOWN** |

  - WHERE는 **TRUE인 행만** 통과시킨다. FALSE·UNKNOWN은 모두 탈락한다.
  - 예: `NOT (COL <= 2)` → COL이 NULL인 행은 `NOT UNKNOWN` = UNKNOWN이라 **제외**된다. 3, 4만 남는다.
  - 예: `NOT (V1='A' AND V2='T1')`에서 V1이 NULL이고 V2가 'T1'이 아니면 `UNKNOWN AND FALSE` = FALSE → NOT으로 **TRUE**가 되어 **포함**된다.
  - `WHERE 월급 >= 100000 OR 월급 < 100000`처럼 모든 값을 덮는 조건이어도 **월급이 NULL인 행은 빠진다**. 그래서 `COUNT(*)`(전체)와 결과가 다를 수 있다.
- **BETWEEN**
  - `BETWEEN a AND b`는 a, b를 **포함**한다.
  - `BETWEEN`과 같은 조건: `>= AND <=`, `NOT (COL < a OR COL > b)`. `> AND <`는 경계값이 빠져 다르다.
  - `NOT BETWEEN 100 AND 200` = `값 < 100 OR 값 > 200`. 경계값 100, 200은 **제외**되고, NULL도 UNKNOWN이라 **제외**된다.
  - `200 BETWEEN COL3 AND COL4` = `COL3 <= 200 AND COL4 >= 200` (값이 범위 안에 드는지)
  - 경계 함정: 구간 테이블이 정수 경계(0~49, 50~79)만 있으면 **49.5 같은 소수 값은 어느 `BETWEEN`에도 걸리지 않아** 공집합이 된다.
- **IN 목록**
  - `IN (10, 50)`은 10과 50 **두 값만**이다. 범위가 아니다.
  - 같은 값이 중복돼도 오류가 아니다. `IN (100, 200, 100)`은 `IN (100, 200)`과 같다.
  - `IN ('p', NULL)`의 NULL은 어떤 값과도 같지 않아 **무시**된다. 'p'만 매칭되고, NULL 행은 나오지 않는다.
  - `NOT IN (…, NULL)`처럼 목록에 NULL이 있으면 결과는 **공집합**이다.
- **다중 칼럼 IN**: `WHERE (V1, V2) IN (('A','T1'), ('A','T2'))`처럼 쓸 수 있다.
  - 풀어 쓰면 튜플 **안은 AND**, 튜플 **사이는 OR**
  - `(C1, C2) IN (('A',1000), ('B',2000))` = `(C1='A' AND C2=1000) OR (C1='B' AND C2=2000)`
  - `(C1, C2) IN ((1,3), (1,4))` = `C1=1 AND (C2=3 OR C2=4)`
  - 함정: `C1 IN ('A','B') AND C2 IN (1000, 2000)` → 틀림. (A, 2000), (B, 1000)까지 매칭돼 **더 넓다**.
  - 서브쿼리 쪽 칼럼에 NULL이 섞인 튜플은 `= NULL`이 UNKNOWN이라 **매칭되지 않는다**. 오류는 아니다.
- **시분초가 있는 DATE 칼럼 범위 조회**
  - 하루: `HIRE_DT >= DATE '2025-10-21' AND HIRE_DT < DATE '2025-10-22'`, `TRUNC(HIRE_DT) = DATE '2025-10-21'`, `<= DATE '2025-10-21' + 1 - 1/86400` → 맞다.
  - 함정: `BETWEEN DATE '2025-10-21' AND DATE '2025-10-22'` → 틀림. 22일 **00:00:00 정각** 행까지 들어온다.
  - 함정: `COL1 = TO_DATE('2025010113', 'YYYYMMDDHH24')` → 13시 **정각**만 잡는다. 13시대 전체가 아니다.
  - 한 달: `TO_DATE('201501', 'YYYYMM')`은 **2015-01-01 00:00:00** 한 시점이다. `=`로 비교하면 1월 전체가 아니라 그 시각만 맞는다.
    - 한 달 범위는 `>= TO_DATE('20150101', 'YYYYMMDD') AND < TO_DATE('20150201', 'YYYYMMDD')`로 쓴다.
    - `TO_CHAR(날짜, 'YYYYMM') = '201501'`도 결과는 같지만 칼럼을 가공하므로 인덱스를 못 쓴다.
- `EXTRACT(MONTH FROM 날짜) NOT IN (1, 2, 4)`처럼 월만 뽑아 거를 수 있다.

### LIKE 와일드카드 — 기출 15회 (2026 2 · 2025 4 · 2024 4 · 2023 4 · 2022 1)
- `%`: 0개 이상의 아무 문자
- `_`: 정확히 1개의 문자
- 예: `LIKE '%N'`은 **N으로 끝나는** 값만 찾는다. ALLEN, MARTIN은 해당하고, JONES는 N이 중간에 있어서 제외된다.
- 예: `LIKE '_L%'` → **두 번째 글자가 L**인 값 (ALX, CLARE, BLX)
- `%`는 **0글자**도 포함한다. `LIKE '%연구소'`는 '연구소' 단독도 찾는다. `LIKE '_연구소'`는 앞에 정확히 1글자가 있어야 한다.
- 위치·길이 조합
  - 세 번째 글자가 L: `'__L%'`
  - '이'로 시작하는 세 글자: `'이__'` (`'이%'`, `'이_%'`는 길이 보장 안 됨)
  - 두 번째 글자가 S이고 4글자 이상: `'_S__%'`, `'_S%__'`, `'_S_%_'` → 모두 맞다. `'%S__'`는 틀림
  - `'%A_C%'`: A, 아무 1글자, C가 **연속**해야 한다. `AB_C`는 A와 C 사이가 두 글자라 제외
- **`ESCAPE`**: `%`나 `_` 자체를 찾을 때 쓴다.
  - `LIKE '%@_%' ESCAPE '@'` → 밑줄 `_`이 **들어 있는** 값
  - 함정: `LIKE '%_%'` → `_`가 와일드카드라 **한 글자 이상인 모든 값**이 나온다.
  - 함정: `LIKE '%#_%'` → ESCAPE 지정이 없으면 `#`은 그냥 문자다.
- **LIKE는 `=`와 다르다.** `명 = '%연구소'`는 `%연구소`라는 문자열 그대로만 찾는다. 와일드카드는 LIKE에서만 동작한다.
- `NOT LIKE`에서도 **NULL 행은 제외**된다. 비교 결과가 UNKNOWN이기 때문이다.
- Oracle의 LIKE는 **대소문자를 구분**한다. `LIKE 'A%'`는 소문자 a로 시작하는 값을 찾지 않는다.
- **SQL Server의 `[ ]`**: 괄호 안 문자 중 1글자
  - `LIKE '[KT]im'` → Kim, Tim
  - Oracle LIKE는 `%`, `_`만 지원한다. `[A-Z]` 같은 패턴은 `REGEXP_LIKE`로 쓴다.

### NULL의 특성 — 기출 16회 (2026 3 · 2025 4 · 2024 3 · 2023 3 · 2022 3)
- NULL은 **0이나 공백이 아니라** "값을 알 수 없음"을 뜻한다. DBMS 종류와 상관없이 같은 뜻이다.
  - 함정: "SQL Server에서 NULL은 0", "Oracle에서 NULL은 TRUE 혹은 FALSE", "DBMS마다 NULL의 의미가 다르다" → 모두 틀림
- `NULL = NULL`은 TRUE가 아니라 **UNKNOWN**이다. 그래서 비교할 때는 `IS NULL`을 쓴다.
  - `WHERE COL = NULL`은 항상 UNKNOWN이라 **결과가 0건**이다. `COUNT`라면 0이 나온다.
  - 비교 함정: `COL <> NULL`, `COL != NULL`, `COL NOT NULL`, `NOT COL = NULL` → 모두 원하는 결과가 안 나온다. `IS NOT NULL`만 맞다.
  - `NOT NULL`은 WHERE 조건이 아니라 **제약 조건** 문법이다. `WHERE COL NOT NULL` → 오류.
- **행 수와 값을 구분**한다.
  - `SELECT NULL + 1 FROM DUAL` → NULL 값이 **1행** 나온다.
  - `SELECT * FROM DUAL WHERE 1 > NULL` / `WHERE NULL = NULL` → **0행(공집합)**
  - `SELECT * FROM DUAL WHERE NULL IS NULL` → **1행**
- **집계 함수(SUM, AVG, MIN, MAX, COUNT(칼럼))는 NULL을 제외하고 계산**한다.
  - `COUNT(*)`: NULL을 포함한 전체 행 수
  - `COUNT(칼럼)`: NULL을 제외한 행 수
  - 예: 10행 중 NULL 2개 → `COUNT(*)` = 10, `COUNT(NUM2)` = 8

- **Oracle은 빈 문자열 `''`을 NULL로 저장**한다. SQL Server는 `''`과 NULL을 별개로 본다.
  - 그래서 `''`을 넣은 뒤 `WHERE COL IS NULL`로 조회하면 Oracle은 1건, SQL Server는 0건이 나온다.
- 집계 활용 예: `COUNT(고객번호) - COUNT(집주소)` = 집주소가 NULL인 고객 수
- 문자 칼럼에 `SUM`을 쓰면 오류가 난다.

|----|------|
| `0 / 300` | **0** |
| `300 / 0` | **오류**(0으로 나누기) |

### NULL 관련 함수 — 기출 15회 (2026 3 · 2025 3 · 2024 3 · 2023 3 · 2022 3)
| 함수 | 동작 | 예 → 결과 |
|------|------|-----------|
| `NVL(a, b)` | a가 NULL이면 b | `NVL(NULL, 0)` → 0 |
| **`NVL2(a, b, c)`** | a가 NULL이 **아니면 b**, NULL이면 **c** | `NVL2(NULL, 'A', 'B')` → `'B'` |
| `COALESCE(a, b, …)` | 처음으로 NULL이 아닌 값 | `COALESCE('AB','CD',NULL)` → `'AB'` |
| `NULLIF(a, b)` | a = b이면 NULL, 아니면 a | `NULLIF('A','A')` → NULL |
| `DECODE(x, v, r, 기본값)` | x = v이면 r, 아니면 기본값 | `DECODE('AB','CD','EF',NULL)` → NULL |
| `CASE x WHEN v THEN r END` | 일치하는 WHEN이 없고 ELSE도 없으면 NULL | `CASE 'AB' WHEN 'CD' THEN 'EF' END` → NULL |

- **DBMS별 NVL**

| DBMS | 함수 |
|------|------|
| Oracle | `NVL(a, b)` |
| SQL Server | `ISNULL(a, b)` (`ISNULL(NULL, 0)` → 0) |
| MySQL | `IFNULL(a, b)`. Oracle에는 없음 |

- `NULL(PRICE, 0)`이라는 함수는 없다.
- **0으로 나누기 방지**: `값 / NULLIF(분모, 0)` → 분모가 0이면 NULL이 되어 오류가 나지 않는다.
- NVL2는 **인자 3개가 필수**다. ("NVL2(expr, a)처럼 2개로 쓸 수 있다" → 틀림)
- 함정: "`NVL2(SAL, 100, SAL)`은 `NVL(SAL, 100)`과 같다" → 틀림. NVL2는 NOT NULL일 때 두 번째 인자라 **정반대로** 동작한다. `NVL(SAL, 100)`과 같은 건 `NVL2(SAL, SAL, 100)`이다.
- **NULLIF만 성격이 다르다.** NVL·COALESCE·NVL2는 NULL을 다른 값으로 **바꾸고**, NULLIF는 NULL을 **만든다**.
  - `CASE WHEN COL = 'X' THEN NULL ELSE COL END` = `NULLIF(COL, 'X')`
  - `NULLIF(1, NULL)` → 1. `1 = NULL`은 UNKNOWN이라 "같지 않음"으로 보고 첫 값을 돌려준다.
  - 그래서 `COUNT(NULLIF(칼럼, NULL))` = `COUNT(칼럼)` (NULL 아닌 행 수)
- 결과가 NULL인 것 모음: `NVL(NULL, NULL)`, `COALESCE(NULL, NULL)`, `NULLIF('A','A')`, `CASE WHEN 1=2 THEN 'Y' END`, `DECODE('A','B','C',NULL)`
- 중첩 예
  - `NULLIF(COALESCE(NULL, 'A', 'B'), 'A')` → COALESCE가 'A' → NULLIF('A','A') → **NULL**
  - `COALESCE(NULLIF(100, 100), -1)` → NULLIF가 NULL → **-1**
- **NVL은 두 인자의 타입이 호환**되어야 한다. `NVL(100, 'NULL')` → 'NULL'을 숫자로 바꿀 수 없어 **오류**.
- NVL은 NULL 치환만 한다. ("NVL(COMM, SAL)은 덧셈을 수행한다" → 틀림)
- **DECODE는 NULL끼리 같다고 본다.** `DECODE(칼럼, NULL, -1, 0)`은 칼럼이 NULL이면 -1이다.
  - 반대로 단순 CASE `CASE 칼럼 WHEN NULL THEN -1 ELSE 0 END`는 `칼럼 = NULL`로 비교해 UNKNOWN → **항상 0**이다.
  - NULL 판정은 `CASE WHEN 칼럼 IS NULL THEN …`으로 쓴다.

### CASE 평가 규칙 · ELSE — 기출 8회 (2025 2 · 2024 2 · 2023 2 · 2022 2)
- WHEN은 **위에서부터** 평가하고, **처음 참이 된 WHEN**의 결과를 반환한다. 뒤의 WHEN은 보지 않는다.
  - WHEN 순서를 바꾸면 결과가 달라진다.
- **단순 CASE vs 검색 CASE**

| 구분 | 형식 | 특징 |
|------|------|------|
| 단순 CASE | `CASE 칼럼 WHEN 값 THEN …` | `=` 비교만. **비교 대상과 값의 타입이 같아야** 한다 |
| 검색(Searched) CASE | `CASE WHEN 조건식 THEN …` | CASE 뒤에 칼럼을 쓰지 않는다. 조건을 자유롭게 쓴다 |

  - 함정: `CASE SUBSTR(JUMIN, 7, 1) WHEN 1 THEN …` → **오류**. SUBSTR 결과는 문자인데 숫자 1과 비교했다. `WHEN '1'`로 써야 한다.
  - 함정: "Searched CASE는 CASE 바로 뒤에 비교 칼럼을 써야 한다" → 틀림
- **ELSE**
  - ELSE를 생략하면 조건에 맞지 않는 행은 NULL이다.
  - 보기에서 "NULL을 반환하도록 명시"한 것을 묻는다면 `ELSE NULL`을 적은 것이 정답이다.
  - `ELSE 0`은 NULL이 아니라 0을 반환하므로 다르다.
  - **ELSE는 맨 끝에 한 번만** 쓴다. ELSE 뒤에 WHEN이 오면 문법 오류다.
- 중첩 CASE는 `DECODE` 중첩으로 바꿀 수 있다. (`DECODE(DEPTNO, 10, DECODE(JOB, 'CLERK', 'A', 'B'), 20, 'C', 'D')`)

### 문자열 연결 — 기출 1회 (2025 1)
| DBMS | 연결 방법 |
|------|-----------|
| Oracle | `\|\|`, `CONCAT(a, b)` |
| SQL Server | `+`, `CONCAT` |

- `&`는 문자열 연결 연산자가 아니다.
- Oracle에서 `||`는 **NULL을 빈 문자열처럼 취급**한다.
  - 예: `'ABC' || NULL || 'XYZ'` → `ABCXYZ`
- Oracle `CONCAT`은 인자가 **2개**다. 셋 이상은 중첩한다. NULL은 빈 문자열처럼 취급한다. (`CONCAT(CONCAT(NULL, 'BC'), 'D')` → `'BCD'`)
- 산술 연산(`+`, `*` 등)은 NULL이 끼면 결과가 NULL이 된다. 문자열 연결과 다르다.

### 정규표현식 (`REGEXP_SUBSTR`) — 기출 10회 (2026 3 · 2025 4 · 2024 3)
| 함수 | 반환 |
|------|------|
| `REGEXP_LIKE` | 일치 여부 (WHERE 조건) |
| `REGEXP_INSTR` | 처음 일치하는 **시작 위치** |
| `REGEXP_COUNT` | 일치 **횟수** |
| `REGEXP_REPLACE` | 치환 결과 |
| `REGEXP_SUBSTR(s, 패턴, 시작, n번째)` | n번째로 일치한 문자열 |

- **기본 기호**
  - `.`: 아무 문자 1개
  - `|`: OR / `( )`: 그룹
  - **위치 앵커**: `^` = 문자열 **시작**, `$` = 문자열 **끝**
    - `'^010'` → 010으로 **시작**하는 값
    - 함정: `'[^010]'` → 시작이 아니라 **문자 클래스 부정**(0·1이 아닌 한 글자)
- **수량자**

| 기호 | 의미 |
|------|------|
| `?` | **0회 또는 1회** |
| `*` | 0회 이상 |
| `+` | **1회 이상** |
| `{m}` | 정확히 m회 |
| `{m,}` | **m회 이상** |
| `{m,n}` | m회 이상 n회 이하. **탐욕적**이라 가능한 한 길게(n쪽) 매칭 (예: `a{2,4}` → `aaaa`) |

- 매칭은 **왼쪽부터** 시작해 **가장 길게(최장 일치)** 잡는다.
- 예: 문자열 `AABBCC`
  - `'(A|B)+C'` → **`AABBC`**: A·B가 반복된 뒤 C 하나가 온다. C는 반복 대상이 아니다.
  - `'AB+C'` → **`ABBC`**: A 바로 뒤에 B가 1회 이상 와야 한다. 첫 A는 뒤가 A라서 탈락하고, 두 번째 A부터 매칭된다.
- **문자 클래스**
  - `[0-9]`: 숫자 1글자 / `[^0-9]`: 숫자가 **아닌** 1글자 (괄호 안의 `^`는 부정) / `[a-z]`: 소문자 한 글자 / `[0-9]{3}`: 숫자 3자리
  - `\d` = 숫자, `\w` = **영문자·숫자·밑줄(`_`)**. **하이픈(`-`)은 `\w`에 포함되지 않는다**. (`^\w*$`에 `ER-123`은 매칭 안 됨)
  - 대괄호 안에서는 `|`, `.`, `\` 같은 기호도 **그냥 문자**로 취급된다. `[XY-]`처럼 끝에 쓴 `-`도 문자 하이픈이다.
  - `REGEXP_SUBSTR('ORA-00600 …', '[^0-9]+')` → `'ORA-'` (처음 일치한 하나만)
  - `[^0-9]`를 `REGEXP_REPLACE`로 지우면 숫자만 남는다. (예: `A1-B22-C333` → `122333`)
- `REGEXP_COUNT(s, '[0-9]')`는 숫자 한 글자씩, `'[0-9]+'`는 **연속한 덩어리**를 하나로 센다.
  - 예: `'1a22b333'` → 6, 3 / `REGEXP_SUBSTR(s, '[0-9]+', 1, 2)` → `'22'`
- 세 번째 인자(**시작 위치**)부터 찾는다. `REGEXP_SUBSTR('aabbc', 'a.*', 2)` → `'abbc'`
- Oracle 정규식은 기본적으로 **대소문자를 구분**한다. `'b.d'`는 `'BCD'`와 일치하지 않아 NULL이다. 매치옵션 `'i'`를 주면 대소문자를 무시한다.
- 형식 검사 예
  - 대문자로 시작하고 숫자로 끝남 → `REGEXP_LIKE(COL, '^[A-Z].*[0-9]$')`
  - `'^[0-9]{3}-[0-9]{3,4}-[0-9]{4}$'` → `02-1234-5678`은 앞자리가 2자리라 **매칭 안 됨**
- **서브그룹(서브표현식) 번호**: **여는 괄호 `(` 순서**대로 1, 2, 3 … 을 매긴다. 바깥 괄호가 안쪽 괄호보다 먼저다.
  - 예: `((A)-(B))-((C)-(D))` → 1번 `A-B`, 2번 `A`, 3번 `B`, 4번 `C-D`, 5번 `C`, 6번 `D`
  - `REGEXP_SUBSTR(문자열, 패턴, 1, 1, NULL, n)`: n번 서브그룹만 꺼낸다. (예: `'@(.+)'`의 1번 그룹 → `@` 뒤 도메인)
  - `REGEXP_REPLACE`에서 `\1`, `\2`, `\3`으로 캡처한 그룹 순서를 바꿀 수 있다. (예: 연/월/일 → 일/월/연)
- **`REGEXP_INSTR(문자열, 패턴, 시작위치, 발생순번, 반환옵션, 매치옵션, 서브표현식)`**
  - 반환옵션 0: 일치 **시작 위치**, 1: 일치 끝 다음 위치
  - 서브표현식 n을 주면 n번 그룹이 **시작하는 위치**를 반환한다.
  - 예: `'12345678'`, 패턴 `'(123)(4(56)(78))'`, 서브표현식 2 → 그룹 2는 `45678`이라 **4**

### GROUP BY · HAVING · 집계 — 기출 18회 (2026 3 · 2025 4 · 2024 4 · 2023 4 · 2022 3)
- `GROUP BY` 후 `HAVING`으로 **그룹 조건**을 건다. (예: `HAVING COUNT(*) > 2`)
- `GROUP BY` 없이 `HAVING`만 써도 **오류가 아니다**. 전체를 하나의 그룹으로 본다.
- Oracle에서는 HAVING을 **GROUP BY 앞에** 써도 오류 없이 같은 결과를 낸다. 논리적으로는 GROUP BY → HAVING 순서가 맞고, 순서대로 쓰는 것을 권장한다.
- **WHERE 절에는 집계 함수를 쓸 수 없다.** 그래서 HAVING 조건을 WHERE로 옮기면 안 된다.
- **GROUP BY 절 규칙**
  - **집계 함수(SUM, COUNT 등)는 쓸 수 없다.**
  - **단일 행 함수는 쓸 수 있다.** (예: `GROUP BY SUBSTR(…)`)
  - **칼럼 별칭은 쓸 수 없다.**
- GROUP BY가 있을 때 SELECT에 올 수 있는 것: GROUP BY 칼럼, 집계 함수, **상수(NULL, 'X' 등)**. GROUP BY에 없는 일반 칼럼(예: EMPNO)은 오류다.
  - GROUP BY에 없는 일반 칼럼은 HAVING에도 그대로 쓸 수 없다. (`HAVING HEIGHT = MIN(HEIGHT)` → 오류)
- **HAVING에 쓸 수 있는 것**
  - **집계 없는 일반 조건**도 쓸 수 있다. 단, GROUP BY 칼럼이어야 한다. (`HAVING 메뉴ID = 3` → 가능)
  - **SELECT에 없는 집계 함수**도 쓸 수 있다. (`SELECT DEPTNO … HAVING MAX(SAL) > 400` → 가능)
- GROUP BY 기준 칼럼의 **NULL도 하나의 그룹**으로 묶인다.
  - 예: 직급 5종 + NULL → 그룹 6개
- **GROUP BY 칼럼 순서·DISTINCT 칼럼 순서는 결과 건수에 영향이 없다.** `GROUP BY A, B`와 `GROUP BY B, A`는 그룹이 같다. 출력 순서만 다를 수 있다.
  - 첫 칼럼이 UNIQUE하면 뒤에 칼럼을 더 붙여도 그룹 수는 변하지 않는다.
- GROUP BY 기준을 여러 칼럼으로 잡으면 그룹이 더 잘게 나뉜다. (사용자+구매일로 묶으면 같은 사용자도 날짜별로 다른 그룹)
  - `GROUP BY 고객ID, 주문번호 HAVING SUM(수량) >= 10` → **한 주문에서** 10개 이상 산 고객
  - `GROUP BY 고객ID HAVING SUM(수량) >= 10` → 누적 수량 10개 이상
  - `COUNT(주문번호) >= 10` → 주문 횟수 / `COUNT(DISTINCT 상품) >= 10` → 서로 다른 상품 수
- **동명이인**이 있을 수 있으면 `GROUP BY 학번, 이름`처럼 식별자를 함께 묶는다.
- `HAVING MAX(수량) > 10` = "수량이 10을 넘는 주문이 **한 건이라도 있는** 그룹". 합계 조건은 `SUM`, 건수 조건은 `COUNT`다.
- **COUNT**
  - `COUNT(칼럼)`은 NULL 행을 빼고 센다. 예: 전체 670명 중 NULL 25명 → 645

| 식 (5행 테이블) | 결과 |
|----|------|
| `COUNT(*)` | 5 |
| `COUNT(1)`, `COUNT('X')` | 5 (상수는 NULL이 아니라 모든 행을 셈) |
| **`COUNT(NULL)`** | **0** (인자가 항상 NULL) |
| `COUNT(ALL 칼럼)` | `COUNT(칼럼)`과 같음 (ALL이 기본값) |

  - `COUNT(DISTINCT 칼럼)`: 중복을 제거한 뒤 센다. **NULL은 개수에 넣지 않는다**. 반면 `SELECT DISTINCT`는 NULL 여러 개를 **NULL 하나**로 출력한다.
  - **어떤 데이터 타입에도 쓸 수 있는 집계 함수는 `COUNT`**다. `MAX`·`MIN`도 문자·날짜에 쓸 수 있다. `SUM`·`AVG`·`STDDEV`는 숫자 전용이다.
- **조건에 맞는 행이 없을 때 — 결과가 0행인지 1행인지**

| SQL 형태 | 결과 |
|----------|------|
| `SELECT COUNT(*) FROM T WHERE 거짓` | **1행** (값 0) |
| `SELECT MAX(C) FROM T WHERE 거짓` | **1행** (값 NULL) |
| `SELECT COUNT(*) FROM T WHERE 거짓 GROUP BY K` | **0행** (그룹이 안 생김) |
| `SELECT C FROM T WHERE 거짓` (집계 없음) | **0행** |

  - 조건에 맞는 행이 하나도 없으면 `COUNT`는 NULL이 아니라 **0**을 반환한다. (SUM·AVG 등은 NULL)
  - **GROUP BY가 없으면** 전체가 한 그룹이라 1행이 나온다. 이때 `NVL(MAX(COL), 'X')` → 'X'
  - **GROUP BY가 있으면** 그룹 자체가 없어 **0행(공집합)**이다. NVL로 감싸도 바꿀 행이 없다.
  - `NVL(COUNT(*), 9999)` (조건이 거짓) → **0**. COUNT는 0을 반환하므로 NVL이 적용되지 않는다.
  - `HAVING` 조건을 만족하는 그룹이 없어도 **공집합**이다. (`SELECT COUNT(*) FROM DUAL HAVING COUNT(*) > 4` → 공집합)
- 모든 값이 NULL인 칼럼에 `SUM`·`AVG`·`MIN`·`MAX` → **NULL**. `COUNT(칼럼)` → **0**
  - 함정: "NULL로만 구성된 칼럼을 COUNT한 결과는 공집합" → 틀림. **0**이다.
- **평균 계산 비교** (값 10, NULL, 20, 30)

| 식 | 결과 | 이유 |
|----|------|------|
| `AVG(C)` | 20 | NULL 제외, 분모 3 |
| `SUM(C) / COUNT(C)` | 20 | AVG와 같음 |
| `SUM(C) / COUNT(*)` | **15** | 분모에 NULL 행까지 들어감. `AVG(NVL(C, 0))`과 같음 |

  - 0은 NULL이 아니라 **정상 값**이라 AVG 분모에 들어간다.
  - 같은 값이 나오는 조합: `SUM(COL)` = `SUM(NVL(COL,0))` = `AVG(COL) * COUNT(COL)`
  - 함정: `AVG(COL) * COUNT(*)` → 다름. COUNT(*)는 NULL 행까지 센다.
- **`SUM(A + B)`와 `SUM(A) + SUM(B)`는 다르다.** (산술의 NULL 전파 + 집계의 NULL 제외)
  - `SUM(A + B)`: 행마다 먼저 더하므로 A·B 중 하나라도 NULL인 행은 **통째로 빠진다**. 모든 행에 NULL이 끼면 결과는 NULL이다.
  - `SUM(A) + SUM(B)`: 칼럼별로 NULL을 빼고 합한 뒤 더한다. 결과가 `SUM(NVL(A,0) + NVL(B,0))`과 같다. 단, 한쪽 SUM이 NULL(대상 값이 전부 NULL)이면 전체가 NULL이다.
  - `AVG(C1 + C2)`도 NULL 행이 분모에서 빠진다. 예: (10,20), (NULL,30), (40,NULL), (50,50) → `AVG(C1+C2)` = 65, NVL 적용 시 50
- 집계 결과에 산술을 하면 NULL 전파 규칙이 그대로 적용된다. (예: `2800 + MIN(SAL)`에서 MIN이 NULL이면 결과 NULL)
- HAVING에서 집계 결과가 NULL이면 비교가 UNKNOWN이라 **그 그룹은 탈락**한다. (예: `HAVING SUM(금액) > 1000`에서 SUM이 NULL인 그룹 제외)
- 함정: "`SUM(NVL(SAL, 0))`의 NVL은 NULL 합계 오류를 막는다" → 틀림. 집계 함수는 원래 NULL을 빼고 계산하므로 오류가 없다. 행마다 NVL을 돌려 비효율적이다. 결과가 NULL일 때만 바꾸려면 `NVL(SUM(SAL), 0)`처럼 **바깥에 한 번** 쓴다.
- `MIN`·`MAX`는 NVL을 쓰지 않으면 NULL을 빼고 고른다. `AVG(NVL(SAL,0))`과 `MIN(SAL)`을 같이 물으면 둘의 NULL 처리가 다르다.
- **조건부 건수 세기**
  - `COUNT`: 셀 값은 무엇이든 되고, 안 셀 값은 **반드시 NULL**이어야 한다.
  - `SUM`: 셀 값은 1, 안 셀 값은 0이나 NULL이다.
  - 함정: `COUNT(DECODE(COL, 10, 1, 0))` → 0도 값이라 **전체 행 수**가 된다. `SUM(DECODE(COL, 10, 1, 0))`이 맞다.
  - 함정: `SUM(CASE POSITION WHEN 'FW' THEN 1 ELSE 1 END)` → ELSE도 1이라 전체 인원이 나온다.
  - 문자를 반환하는 DECODE(`'O'`, `'X'`)에 SUM을 쓰면 오류다.
- **집계 함수 중첩**: `AVG(COUNT(*))`는 그룹 칼럼을 함께 SELECT하면 **오류**다. 중첩 결과는 1행이라 그룹별 칼럼과 같이 나올 수 없다.
- 함정: 그룹별로 `MAX(회차)`, `MAX(등급)`, `MAX(일자)`를 따로 구하면 **서로 다른 행의 값이 섞인다.** "최종 회차의 행 전체"를 구하려면 `회차 = (SELECT MAX(회차) … 상관 조건)`처럼 행을 먼저 찾는다.
- `SELECT DISTINCT COUNT(*) FROM T` → 집계 결과 1행만 나온다. DISTINCT가 의미 없다.
- 집계 결과로 필터링하려면 인라인 뷰를 쓰는 방법도 있다. 인라인 뷰에서 그룹핑해 별칭을 만든 뒤 바깥 WHERE에서 그 별칭으로 거르면 HAVING과 결과가 같다.

### ORDER BY · 칼럼 별칭 — 기출 12회 (2026 2 · 2025 2 · 2024 3 · 2023 3 · 2022 2)
- 기본 정렬은 오름차순(ASC)이다. 날짜를 오름차순으로 정렬하면 **오래된 날짜가 먼저** 나온다.
- 정렬 옵션은 **칼럼마다 따로** 적용된다. `ORDER BY COL1, COL2 DESC` → COL1은 기본 ASC, COL2만 DESC
  - 정렬 키가 여러 개면 앞 키가 같은 행끼리만 다음 키로 정렬한다.
  - `DESC`는 칼럼 **뒤**에 쓴다. `ORDER BY …, DESC 연봉` → 문법 오류
- **NULL 정렬 위치**
  - **Oracle**: NULL을 가장 큰 값으로 본다. 그래서 ASC에서는 **마지막**, DESC에서는 **처음**에 나온다.
  - **SQL Server**: NULL을 가장 작은 값으로 본다. 그래서 ASC에서는 **처음**에 나온다.
  - `NULLS FIRST`·`NULLS LAST`로 위치를 바꿀 수 있다. 옵션을 명시하면 기본 위치보다 우선한다. (`ORDER BY COL DESC NULLS LAST` → NULL이 **맨 뒤**)
- **ORDER BY에 쓸 수 있는 것**: 칼럼명, 별칭, **SELECT 칼럼 순서 번호**. 섞어 써도 된다. (`ORDER BY 선수명 ASC, 팀명, 3 DESC`) ("혼용할 수 없다" → 틀림)
  - **위치 번호**(`ORDER BY 2`)는 **SELECT 목록의 순서**를 뜻한다. SELECT 목록 개수를 넘는 번호(칼럼 2개인데 `ORDER BY 3`)는 **오류**다.
  - `SELECT N1 FROM (…) ORDER BY 2` → 오류. `ORDER BY N2`처럼 **칼럼명**은 SELECT에 없어도 된다. (GROUP BY가 없을 때)
- **GROUP BY가 있으면 ORDER BY에는 GROUP BY 칼럼·집계 함수·SELECT 별칭만** 쓸 수 있다.
  - `GROUP BY 지역 ORDER BY 년` → 오류 / `GROUP BY COL1, COL2 ORDER BY COL3` → 오류
  - `ORDER BY COUNT(*)`, `ORDER BY SUM(SAL) DESC`처럼 집계 함수는 SELECT에 없어도 된다.
- 정렬 키에 식·함수를 쓸 수 있다.
  - `ORDER BY DECODE(등급, 'VVIP', 1, 'VIP', 2, 3)`, `ORDER BY CASE WHEN ID = 999 THEN 0 ELSE 1 END` → 원하는 값을 맨 앞으로
  - `ORDER BY CASE WHEN ID='A' THEN 1 ELSE 2 END, AMT DESC` → A 행들이 먼저, 그 안에서 AMT 내림차순
  - `ORDER BY TO_CHAR(SAL)` → **문자열 정렬**이라 1300, 2500, 300, 800 순서가 된다.
- **칼럼 별칭**
  - 칼럼 **뒤에만** 붙인다. 앞에는 붙일 수 없다. `AS`는 생략할 수 있다.
  - 공백이나 특수문자가 들어가면 큰따옴표(`"…"`)로 감싼다.
  - ORDER BY에서는 별칭을 쓸 수 있다. WHERE·GROUP BY·HAVING에서는 쓸 수 없다. (SELECT가 ORDER BY보다 먼저 실행되기 때문)
  - `SELECT EMP_ID = 사번`처럼 `=`로 별칭을 붙이면 Oracle에서 오류다.
- **테이블 별칭**
  - **Oracle은 FROM 절 테이블 별칭에 `AS`를 쓸 수 없다.** (`FROM TAB AS T` → 오류, `FROM TAB T` → 정상) 칼럼 별칭에는 AS를 쓸 수 있다.
  - FROM에서 테이블 별칭을 지정하면 칼럼 앞에는 **별칭만** 쓸 수 있다. 원래 테이블명(`PLAYER.PLAYER_NAME`, `TABLE1.COL2`)을 쓰면 **오류**다.
  - **칼럼 별칭 앞에는 테이블 별칭을 붙일 수 없다.** (`ORDER BY T.C1` → 오류) 인라인 뷰의 별칭이면 `I.NN`처럼 가능하다.

### ROWID — 기출 없음
- Oracle에서 행을 구분하는 **유일한 주소값**
- 구성: **오브젝트 번호 + 상대 파일 번호 + 블록 번호 + 데이터(행) 번호**
- ROWID로 원하는 블록을 바로 찾아갈 수 있다.
- **SELECT로 조회할 수 있다**. ("개발자가 확인할 수 없다" → 틀림)

### 순수 관계 연산자 — 기출 1회 (2026 1)
| 연산자 | 의미 | SQL 대응 |
|--------|------|----------|
| **SELECT** | 조건에 맞는 **행** 선택 | **WHERE 절** |
| **PROJECT** | 특정 **칼럼** 추출 | **SELECT 절** |
| JOIN | 테이블 결합 | FROM·JOIN |
| DIVIDE | 조건을 **모두** 만족하는 대상 | 직접 지원 없음 (NOT EXISTS 등으로 표현) |

- 함정: "순수 관계 연산자 SELECT는 SQL의 SELECT 절에 해당한다" → 틀림. WHERE 절이다.
- **일반 집합 연산자**: UNION(합집합) · INTERSECTION(교집합) · DIFFERENCE(차집합) · PRODUCT(곱집합 = CROSS JOIN)
  - 함정: "UNION은 순수 관계 연산자" → 틀림 / "PROJECT는 집합 연산자" → 틀림
- 함정: UPDATE·DELETE는 순수 관계 연산자가 아니다.

### 조인 종류 — 기출 17회 (2026 3 · 2025 4 · 2024 4 · 2023 3 · 2022 3)
- **셀프 조인**: 같은 테이블을 별칭 두 개로 조인한다.
  - 예: 직원과 상사 → `FROM EMP E, EMP M WHERE E.MGR = M.EMPNO`
  - 조건 방향 주의: 직원의 MGR이 상사의 EMPNO와 같아야 한다.
  - 셀프 조인은 **한 테이블 안의 두 칼럼이 서로 연관**될 때 쓴다. (예: EMPNO와 MGR)
  - 부하 찾기: `A.EMP_ID = B.MGR_ID` (B의 상사가 A). 상사 찾기 `A.MGR_ID = B.EMP_ID`와 방향이 반대다.
  - 손자 찾기: `EMP A, EMP B, EMP C WHERE B.MGR = A.EMPNO AND C.MGR = B.EMPNO` (세 번 조인)
  - 부하가 없거나 상사가 없는 사원도 보려면 **LEFT OUTER JOIN**. 상사 이름 칸은 NULL이 된다.
    - 이 NULL을 `'사장'` 같은 값으로 바꾸려면 `COALESCE(M.이름, '사장')`이나 `NVL(M.이름, '사장')`을 쓴다.
  - 순위 구하기: `COUNT(*) + 1` + 조건 `T1.점수 < T2.점수` (나보다 높은 사람 수 + 1)
  - **누적합** (윈도우 함수 없이): `A JOIN B ON A.일자 >= B.일자 GROUP BY A.일자` 후 `SUM(B.매출액)`
- **NATURAL JOIN**: 두 테이블에서 **이름이 같은 모든 칼럼**으로 동등(=) 조인한다.
  - `ON`·`USING` 절을 함께 쓸 수 없다. (`NATURAL JOIN … USING (COL1)` → 오류)
  - 공통 칼럼에 **테이블 접두사(별칭)를 붙이면 오류**가 난다. `EMP.DEPTNO`처럼 테이블명을 붙여도 오류다. `USING`도 마찬가지다.
  - 같은 이름 칼럼의 데이터 타입이 다르면 오류가 난다.
  - 이름이 같은 칼럼이 **여러 개면 모두** 조건이 된다. 그래서 `USING (ID)`·`ON A.ID = B.ID`와 결과가 달라질 수 있다.
    - 예: ID와 NAME이 둘 다 같은 이름이면, ID가 같아도 NAME이 다르면 매칭되지 않는다.
  - 공통 칼럼은 결과에 **한 번만** 나온다. USING도 같다. ON은 양쪽 칼럼이 각각 나온다.
  - **등가(=) 조인만** 한다. 비등가 조인은 불가하다.
  - 공통 칼럼은 있는데 일치하는 값이 없으면 결과는 **0건**이다. 카티션 곱이 되지 않는다.
  - 이름이 같은 칼럼이 **하나도 없으면** **CROSS JOIN과 같은 결과**가 된다.
- **USING 절**
  - 괄호 안에 **칼럼명만** 쓴다. `USING (T.ID = S.ID)`처럼 비교식·별칭을 쓰면 오류, `USING DEPTNO`처럼 괄호가 없어도 오류다.
  - `ON (DEPT_NO)`처럼 칼럼명만 쓰면 **구문 오류**다. ON에는 비교식이 와야 하고, 칼럼명만 쓰려면 `USING (DEPT_NO)`를 쓴다.
  - 결과 칼럼 순서(`SELECT *` 기준): USING 칼럼이 **맨 앞에 한 번만** 나오고, 이어서 왼쪽 테이블의 나머지 칼럼, 오른쪽 테이블의 나머지 칼럼 순이다.
- **ANSI 조인 문법 오류 정리**
  - `A INNER JOIN B`만 쓰고 ON·USING이 없으면 **문법 오류**다. INNER JOIN은 ON이나 USING이 반드시 필요하다.
  - `CROSS JOIN`에는 **ON 절을 쓰지 않는다**.
  - `CROSS JOIN`·일반 조인에서 양쪽에 있는 칼럼(`NO`)을 접두사 없이 쓰면 **칼럼 모호성 오류**가 난다. NATURAL JOIN·USING의 공통 칼럼은 반대로 접두사 없이 써야 한다.
- `LEFT OUTER JOIN`·`RIGHT OUTER JOIN`에서 **OUTER는 생략**할 수 있다. `FULL JOIN`도 `FULL OUTER JOIN`과 같다.
- **CROSS JOIN**: 행 수 = M × N (예: 3 × 5 = 15)
  - **`FROM A, B`에 조인 조건이 없으면** 오류가 아니라 **카티션 곱**이다. ANSI로는 `CROSS JOIN`이다.
  - 자동 조인은 NATURAL JOIN을 명시했을 때만 일어난다.
- **등가 · 비등가 조인**
  - **INNER JOIN은 비등가 조건도 가능**하다. 조인 칼럼명이 서로 달라도 ON으로 조인한다.
    - 함정: "INNER JOIN은 등가 조인만 가능하다" → 틀림
    - 함정: "조인 칼럼은 반드시 칼럼명이 같아야 한다" → 틀림. 그 제약은 USING·NATURAL JOIN에만 있다.
  - **EQUI JOIN은 PK·FK 관계가 아니어도** 된다. 값이 매핑되면 쓸 수 있다.
    - 함정: "EQUI JOIN은 반드시 기본키·외래키 관계로만 성립한다" → 틀림
  - **비등가 조인(NON-EQUI JOIN)** 예
    - `ON 고객.포인트 BETWEEN 상품.최소포인트 AND 상품.최대포인트`: 포인트 구간에 맞는 상품 매칭
    - `ON 이름 LIKE 규칙`: 한 행이 여러 규칙에 맞으면 **여러 행**으로 늘어난다.
    - `ON T1.N < T2.M`: 카티션 곱 중 조건을 만족하는 조합만 남는다.
- **조인 결과 행 수**
  - 조인 키가 중복되면 **곱만큼 행이 늘어난다**. (예: 왼쪽 1이 1건, 오른쪽 1이 3건 → 3행. 1:M이면 M쪽 건수만큼)
  - `IN`·`EXISTS`는 메인 테이블 기준이라 늘지 않는다.
  - **NULL 키는 INNER·NATURAL JOIN에서 매칭되지 않는다.**
  - 카티션 곱 + `OR` 조건: (조건1 만족 조합) + (조건2 만족 조합) − (둘 다 만족 조합)
- **조인 조건 수**
  - N개 테이블을 이으려면 조인 조건이 **최소 N−1개** 필요하다. (5개 → 4개)
  - 함정: "테이블 3개를 조인하려면 조건이 최소 3개 이상" → 틀림. 2개다.
  - 단, **식별 관계로 복합키가 상속**되면 키 칼럼 수만큼 조건이 필요하다.
    - 예: A → B → C → D 식별 관계면 A-B 1개, B-C 2개, C-D 3개로 **등호 6개**

### OUTER JOIN — 기출 14회 (2026 3 · 2025 3 · 2024 2 · 2023 3 · 2022 3)
- `A LEFT OUTER JOIN B`: A의 모든 행을 보존한다. ON 조건에 맞지 않는 B 칼럼은 **NULL로 채워진다**.
- 사원이 없는 부서도 보려면 부서 테이블 쪽을 보존한다. 부서가 오른쪽이면 RIGHT OUTER JOIN이다.
- **조건 위치에 따른 차이** (핵심)

| 안쪽(NULL로 채워지는) 테이블 조건 위치 | 효과 |
|------|------|
| **ON 절** (또는 Oracle `B.칼럼(+) = 값`, 인라인 뷰 안) | **매칭 조건**으로만 작동. 바깥 테이블 행은 줄지 않고 NULL로 **보존**된다 |
| **WHERE 절** | NULL 행이 UNKNOWN으로 빠진다. 결과가 **INNER JOIN과 같아진다** |

  - 예: ON 절에 `B.C2 BETWEEN 1 AND 3`을 넣으면 왼쪽 행은 줄지 않는다.
  - 예: `EMP LEFT JOIN DEPT … WHERE D.LOC = 'SEOUL'` → 부서 없는 사원이 사라짐
  - `WHERE D.LOC <> 'DALLAS'`도 마찬가지다. 매칭 안 된 행은 `NULL <> 'DALLAS'`가 UNKNOWN이라 제외된다.
  - 예: "기간 내 주문 합계를 주문 없는 고객까지 포함" → 기간 조건을 **ON 절**에 둔다.
- 여러 테이블을 OUTER JOIN으로 이은 뒤 **마지막에 INNER JOIN**을 하면, 앞에서 보존했던 미매칭 행도 걸러진다.
- 두 테이블이 모두 서로 매칭되면 LEFT·RIGHT·INNER 결과가 같다.
  - 함정: "RIGHT OUTER JOIN과 LEFT OUTER JOIN 결과는 항상 다르다" → 틀림
- **FULL OUTER JOIN**
  - LEFT와 RIGHT 결과를 **UNION**한 것과 같다.
    - `LEFT JOIN UNION ALL RIGHT JOIN` → 매칭 행이 **두 번** 나와 다르다.
  - Oracle에서 **(+)를 양쪽에 쓸 수 없다**. 그래서 FULL OUTER JOIN 구문을 써야 한다.
  - **NULL 키끼리는 매칭되지 않는다.** 각자 따로 출력된다.
  - 행 수 = 매칭 건수 + 왼쪽 단독 + 오른쪽 단독

### OUTER JOIN과 집계 함수 — 기출 3회 (2026 1 · 2023 1 · 2022 1)
- LEFT OUTER JOIN에서 짝이 없는 오른쪽 칼럼은 **NULL로 채워진다**.
- `AVG(칼럼)`은 NULL을 빼고 평균을 낸다.
  - 예: 40, 40, NULL, NULL → 40
- `AVG(NVL(칼럼, 0))`은 NULL이 0으로 바뀌어 **분모에 포함**된다.
  - 예: 40, 40, 0, 0 → 20
- 같은 데이터라도 NVL을 쓰느냐에 따라 평균이 달라진다. 자주 나오는 함정이다.
- LEFT JOIN 결과를 셀 때는 **오른쪽 테이블 칼럼**을 `COUNT`한다.
  - `COUNT(E.EMPNO)`: 매칭이 없는 부서는 **0**
  - `COUNT(고객.고객번호)`: 왼쪽 칼럼이라 미매칭 행도 1로 세어진다. 이용 횟수가 아니라 고객 수가 된다.
- **ON 절 조건 + COUNT**: `DEPT LEFT JOIN EMP ON … AND E.SAL >= 400`이면 조건에 맞는 사원만 세고, 없는 부서는 0으로 남는다.
- "모든 회원"의 이용 횟수·금액을 구하려면 회원 → 이용내역 → 상품을 **모두 LEFT OUTER JOIN**한다. 중간에 INNER JOIN이 끼면 이용 내역 없는 회원이 사라진다.
- `HAVING COUNT(칼럼) >= 1`은 그 칼럼이 **NULL인 행을 세지 않는다**. 그래서 "행이 하나라도 있는지"와 결과가 다를 수 있다.

### Oracle (+) 외부 조인 — 기출 5회 (2026 2 · 2025 1 · 2023 1 · 2022 1)
- **(+)가 붙은 쪽이 NULL로 채워지는 쪽**이다. (+)가 없는 쪽이 기준(보존) 테이블이다.

| Oracle (+) | ANSI |
|------------|------|
| `WHERE A.ID = B.ID(+)` | `A LEFT OUTER JOIN B` |
| `WHERE A.ID(+) = B.ID` | `A RIGHT OUTER JOIN B` |
| 양쪽 (+) → **불가** | `A FULL OUTER JOIN B` |
| `B.칼럼(+) = 값` | `ON` 절에 둔 안쪽 테이블 조건 |

- 셀프 조인 예: 매니저 없는 사원도 출력 → `WHERE E1.MGR = E2.EMPNO(+)`
- 여러 테이블을 이을 때는 **OUTER로 남길 관계에만** (+)를 붙인다.
  - 예: `TAB1 JOIN TAB2 … LEFT JOIN TAB3` → `TAB1.COL1 = TAB2.COL1 AND TAB1.COL2 = TAB3.COL2(+)`
  - 함정: 체인 중간에 (+)를 빠뜨리면 그 단계가 INNER JOIN이 되어 앞에서 보존한 행이 사라진다.
- ANSI로 바꿀 때는 **조인 조건은 ON에, 일반 필터 조건은 WHERE에** 둔다.

### 모델 구조와 조인 — 기출 4회 (2026 1 · 2024 2 · 2022 1)
- **1:M 관계를 조인하면 결과 건수는 M쪽 건수**와 같다. 1쪽 기준으로 한 번씩만 보려면 `GROUP BY`·`DISTINCT`·`EXISTS`를 쓴다.
- M:N을 푸는 **교차 엔터티를 건너뛰고** 양쪽을 직접 조인하면 조인 키가 없어 **카티션 곱**이 된다.
  - 교차 엔터티를 거쳐 `제품 JOIN 생산제품 … JOIN 생산라인 …`으로 잇는다.
- 필요한 칼럼이 이미 중간 테이블에 있으면 상위 테이블까지 조인할 필요가 없다. 조인 수를 묻는 문제에서 따진다.
- **1:1 양쪽 필수 관계**(키가 같음)일 때
  - `A MINUS B`, `A EXCEPT B` → **0건**
  - `A INTERSECT B` 건수 = 조인 건수 = A 건수
  - `A UNION B` 건수 = A 건수 / `A UNION ALL B` 건수 = **A 건수 × 2**
- ERD에서 양쪽이 선택(○)이면 소속이 없는 행이 있을 수 있다. 전체를 보려면 OUTER JOIN이 필요하다.

### 서브쿼리 — 기출 18회 (2026 3 · 2025 4 · 2024 4 · 2023 4 · 2022 3)
- **위치별 이름**
  - SELECT 절: **스칼라 서브쿼리**. 한 행 한 칼럼만 반환하고, JOIN으로 바꿀 수 있다.
  - FROM 절: **인라인 뷰**(동적 뷰, Dynamic View)
  - WHERE 절: 중첩 서브쿼리
  - 서브쿼리는 **ORDER BY 절에도** 쓸 수 있다(스칼라 서브쿼리).
- **ORDER BY 사용**: 서브쿼리 **안에는 ORDER BY를 쓰지 않는다**. 단 **인라인 뷰 안에는 쓸 수 있다**.
- **서브쿼리 칼럼 사용 범위**
  - 서브쿼리는 메인쿼리 칼럼을 **모두** 쓸 수 있다.
  - 메인쿼리는 **WHERE 절 서브쿼리의 칼럼을 쓸 수 없다**. 단 **인라인 뷰의 칼럼은 쓸 수 있다.**
  - 인라인 뷰 **안에서 정의한 테이블 별칭은 바깥에서 쓸 수 없다.** 바깥에서는 인라인 뷰 별칭으로 참조한다.
    - 예: `SELECT b.X FROM (SELECT b.X FROM T b) a` → 오류. `a.X`가 맞다.
  - 메인 FROM에 없는 테이블 별칭을 WHERE에 쓰면 오류다. 스칼라 서브쿼리 안의 별칭은 메인에서 보이지 않는다.
- **단일 행 vs 복수 행**
  - 단일 행 서브쿼리 → `=, <, >` 같은 단일 행 비교 연산자
  - **복수 행 서브쿼리 → `IN, ALL, ANY(SOME), EXISTS`** 같은 복수 행 연산자를 써야 한다.
  - 단일 행 연산자(`=`, `<>`)에 서브쿼리가 **여러 행을 반환하면 오류**가 난다.
  - `=` 대신 `LIKE`를 써도 단일 행 비교다. 서브쿼리가 여러 행이면 **오류**다.
  - **다중 행 연산자(IN, ANY, ALL)는 단일 행 서브쿼리에도 쓸 수 있다.** 반대(단일 행 연산자에 다중 행)는 안 된다.
    - 상관 서브쿼리가 그룹별 `MAX` 하나만 돌려주면 `=`, `ANY`, `ALL` 어느 것을 써도 결과가 같다.
- **ALL · ANY**
  - `> ALL (서브쿼리)`: 서브쿼리 값 **모두**보다 커야 함 → 최댓값보다 큼
  - `< ALL (서브쿼리)`: 최솟값보다 작음
  - `> ANY (서브쿼리)`: **하나라도** 보다 크면 됨 → 최솟값보다 큼
  - `<= ALL (15, 30)` → 최솟값(15) 이하 / `> ALL (3000, 2000)` → 3000 초과
  - `HAVING AVG(SAL) >= ALL (SELECT AVG(SAL) … GROUP BY DEPTNO)` → 평균 급여가 가장 높은 부서. 그룹 조건이라 HAVING을 쓴다.
- **결과 0건과 2건 이상의 차이**

| 서브쿼리 결과 | 단일 행 서브쿼리 (WHERE) | 스칼라 서브쿼리 (SELECT) |
|------|------|------|
| **0건** | 비교값이 NULL → 결과 **공집합** (오류 아님) | **NULL** 출력. 메인 행은 그대로 남는다 |
| **2건 이상** | **런타임 오류** | **런타임 오류** |

  - 스칼라 서브쿼리에서 `SUM`·`MAX` 같은 집계를 쓰면 한 행이 보장된다.
  - 함정: "서브쿼리 결과가 0건이면 메인 쿼리도 오류" → 틀림
- **연관(상관) vs 비연관(독립)**

| 구분 | 연관(상관) 서브쿼리 | 비연관 서브쿼리 |
|------|------|------|
| 메인 칼럼 참조 | 한다 | 하지 않는다 |
| 실행 | 메인 행마다 **반복** 실행 → 상대적으로 **느리다** | 독립적으로 **한 번만** 실행 |
| 주 용도 | 메인이 먼저 읽고 **조건을 확인** | 메인 쿼리에 **값을 제공** |

  - 함정: "상관 서브쿼리는 처리 속도가 가장 빠르다" → 틀림
  - 함정: "서브쿼리는 항상 메인 쿼리보다 먼저 실행된다" → 틀림. 상관 서브쿼리는 메인 행을 받아 실행된다.
  - 함정: "연관 서브쿼리는 주로 메인 쿼리에 값을 제공한다" → 틀림. 비연관 설명이다.
  - 비연관 서브쿼리로 `0 < (SELECT COUNT(*) …)`를 쓰면 메인 행과 상관없이 **전부 또는 전무**가 된다. 회원별로 확인하려면 상관 조건이 필요하다.
  - 상관 서브쿼리(부서 평균 비교)는 **부서별 집계를 인라인 뷰로 만든 뒤 조인**하는 형태로 바꿀 수 있다.
- **기능별 분류**: 메인 쿼리에 값을 주는 제공자 역할은 **Access Subquery**, 조건 확인 역할은 Filter형, 먼저 걸러 주는 것은 Early Filter형
- **인라인 뷰**는 일반적으로 먼저 수행되어 SQL에 **절차성**을 준다.
- 서브쿼리 결과는 **메인쿼리 레벨**을 따른다. 1:M 조인처럼 M 레벨로 늘어나지 않는다.
- WHERE 절 서브쿼리는 메인 행을 거르는 조건일 뿐이다. 최종 결과를 서브쿼리 결과가 결정하는 것은 아니다.
- **다중 칼럼 서브쿼리**(여러 칼럼을 한꺼번에 비교)
  - **SQL Server에서 지원하지 않는다**. Oracle은 지원한다.
  - `WHERE (DEPTNO, SAL) IN (SELECT DEPTNO, MAX(SAL) … GROUP BY DEPTNO)` → 부서별 최고 급여자. 동점자는 모두 나온다.
  - 칼럼은 **이름이 아니라 위치(순서)**로 짝지어 비교한다.
  - 함정: "칼럼 순서가 달라도 이름만 같으면 된다" → 틀림
- **EXISTS · NOT EXISTS**
  - **행이 있는지만 본다.** 그래서 서브쿼리 SELECT 절에 `1`, `X`, `NULL` 중 무엇을 써도 결과가 같다.
  - 상관 서브쿼리 안에서 건수를 비교하는 로직은 `IN`으로 바꾸면 결과가 달라질 수 있다.
  - **IN과 EXISTS 변환**: IN 서브쿼리 안에 상관 조건이 있으면, EXISTS로 바꿀 때 **IN 비교 조건과 상관 조건을 모두** EXISTS 안에 넣는다.
  - **EXISTS는 중복을 제거하지 않는다.** 메인 테이블의 행을 그대로 돌려준다. (DISTINCT·GROUP BY·UNION은 제거)
  - `NOT EXISTS`에서 메인 쿼리 쪽 값이 NULL이면 `=` 비교가 항상 거짓이다. 그래서 그 행은 **NOT EXISTS를 통과해 결과에 포함**된다.
  - `NOT EXISTS`를 OUTER JOIN으로 바꿀 때는 오른쪽의 **NOT NULL 칼럼**(PK 등)에 `IS NULL`을 건다.
- **"없는 것 찾기"**
  - 맞는 방법은 `NOT IN`, `NOT EXISTS`, `OUTER JOIN … IS NULL`이다.
  - `<> ANY`는 틀린 방법이다. 하나라도 다르면 참이 되기 때문이다.
  - **`<>`를 쓴 EXISTS 함정**
    - `EXISTS (… WHERE O.고객번호 <> C.고객번호)`: 다른 번호 행이 하나만 있어도 참이다. 사실상 **전체 행**이 나온다.
    - `NOT EXISTS (… WHERE M.EMP_ID <> E.MGR_ID)`: 다른 행이 거의 항상 있어 대개 **공집합**이다.
    - "없는 것 찾기"의 NOT EXISTS 안에는 `=`를 쓴다.
- **그룹별 최솟값·최댓값 행 전체 가져오기**
  - `(그룹, MIN(값))`을 인라인 뷰로 만들어 원본과 조인한다.
  - `MAX(값) OVER (PARTITION BY 그룹)`를 인라인 뷰에서 붙이고 `값 = 그룹최대`로 거른다.
  - 다른 방법: `(그룹, 값) IN (SELECT 그룹, MAX(값) … GROUP BY 그룹)`, 상관 서브쿼리
  - **동점자가 있으면 그룹 수보다 결과 행이 많아진다.**
  - 함정: `EXISTS (SELECT 1 FROM T X WHERE X.그룹 = P.그룹)`만 쓰면 같은 그룹이 있는지만 봐서 거의 모든 행이 나온다.

### WITH 절 — 기출 없음
- `WITH 이름 AS (SELECT …) SELECT … FROM 이름`: SELECT 앞에서 미리 정의하는 **임시 결과 집합(CTE)**
- 인라인 뷰와 비슷하지만 **같은 CTE를 여러 번 재사용**할 수 있고 가독성이 좋다.
- SQL Server는 CTE를 **재귀 호출**해 계층형 질의를 만든다. (계층형 질의 참고)

### 집합 연산자와 같은 결과를 내는 SQL — 기출 17회 (2026 3 · 2025 3 · 2024 4 · 2023 4 · 2022 3)
- **집합 연산자 종류**
  - `UNION`: 합집합, **중복 제거**. 중복 제거 과정에서 정렬이 생길 수 있다.
  - `UNION ALL`: 합집합, **중복 포함**. **정렬하지 않아** 더 빠르다.
    - 함정: "UNION ALL은 결과를 정렬하고 중복을 한 번만 표현한다" → 틀림
  - `INTERSECT`: 교집합
  - `MINUS`(SQL Server는 `EXCEPT`): 첫 결과에만 있는 행(차집합). 중복은 제거된다.
  - UNION·INTERSECT·MINUS는 중복 제거를 위해 정렬이 생길 수 있다.
- **구조 규칙**
  - 두 SELECT의 칼럼 **개수**가 같고, 위치별 데이터 타입이 **호환**되어야 한다. MINUS·INTERSECT도 마찬가지다.
  - 칼럼 데이터 타입이 서로 호환되면 오류가 나지 않는다.
  - **칼럼 크기(길이)는 달라도 된다.**
    - 함정: "위 집합보다 아래 집합의 칼럼 사이즈가 크면 연산할 수 없다" → 틀림
  - 결과 칼럼명은 **첫 번째 SELECT의 별칭**을 따른다. 두 번째 SELECT의 별칭은 무시된다.
  - **각 SELECT에 GROUP BY는 쓸 수 있다.**
- **ORDER BY는 맨 마지막에 한 번만** 쓴다.
  - 칼럼명은 **첫 번째 SELECT**의 이름을 따른다. 두 번째 SELECT의 칼럼명을 쓰면 오류가 난다.
  - 위치 번호(`ORDER BY 1`)도 쓸 수 있다.
  - 함정: "집합 연산은 ORDER BY를 쓸 수 없다" → 틀림. 최종 결과에 쓸 수 있다.
- **수행 순서**: 위에서 아래로 차례대로 적용하고, **괄호가 있으면 괄호 먼저**다.
  - 예: `(A UNION ALL B) MINUS C`와 `A UNION ALL (B MINUS C)`는 결과가 다르다.
  - 마지막이 MINUS면 앞에서 생긴 중복도 제거된다.
- **집합 연산에서 NULL은 서로 같은 값**으로 본다. (조인에서 NULL끼리 매칭되지 않는 것과 반대)
  - UNION은 NULL 중복을 하나로 줄이고, INTERSECT도 NULL을 공통 행으로 낸다.
- **행 수**
  - `UNION ALL` 행 수 ≥ `UNION` 행 수. 차이는 **겹치는 행 수**다.
  - 같은 값 둘을 UNION하면 한 행이 된다. 예: `MAX UNION MIN`에서 두 값이 같으면 1행
  - **같은 조건이라도 OR와 UNION ALL은 행 수가 다르다.** OR는 행마다 한 번 평가하고, UNION ALL은 두 조건에 모두 맞는 행을 두 번 낸다.
- **`A MINUS B`와 같은 결과를 내는 방법**
  - `NOT IN (서브쿼리)`: 서브쿼리에 **NULL이 있으면 결과가 0건**이 된다. 그래서 서브쿼리 쪽 NULL을 미리 제거해야 한다.
  - `NOT EXISTS (상관 서브쿼리)`: NULL의 영향을 받지 않는다.
  - `LEFT OUTER JOIN … WHERE B.키 IS NULL`: 안티 조인
  - NULL이 없으면 NOT IN · NOT EXISTS · OUTER JOIN + IS NULL은 **모두 같은 결과**다.
  - `T1, T2 WHERE T1.COL1 <> T2.COL1`은 차집합이 아니다. 카티션 곱에서 다른 조합이 모두 남아 **중복이 섞인** 결과가 된다.
- **NOT IN과 NULL 세부**
  - 서브쿼리의 `IN (100, NULL)`은 OR라서 NULL이 무시된다. 결과는 {100}이다.
  - **메인 쪽 값이 NULL**이면 `NULL NOT IN (…)`이 UNKNOWN이라 그 행은 **빠진다**. 반면 NOT EXISTS는 그 행을 남긴다. (서브쿼리 NULL 함정과 반대 방향)
  - "부서가 없는 사원"에 DEPTNO가 NULL인 사원까지 넣으려면 `DEPTNO IS NULL OR DEPTNO NOT IN (…)`으로 쓴다.
  - **다중 칼럼 NOT IN**은 NULL이 있어도 항상 공집합은 아니다. 한 칼럼이라도 확정적으로 다른 쌍은 참이다.
- **다른 집합 연산으로 바꿔 쓰기**
  - FULL OUTER JOIN = `LEFT JOIN UNION RIGHT JOIN` (UNION ALL이면 매칭 행이 두 번 나온다)
  - **UNION ALL과 같은 조합** (A, B 각각 중복 없음): `(A UNION B) UNION ALL (A INTERSECT B)`
- **"둘 다 해당"은 INTERSECT**로 구한다.
  - 예: 강좌 100과 101을 모두 수강한 학번 → `… WHERE 강의번호 = 100 INTERSECT … WHERE 강의번호 = 101`
  - 함정: `강의번호 = 100 AND 강의번호 = 101` → 공집합. 한 행이 두 값을 가질 수 없다. `IN`·`OR`는 둘 중 하나만 들은 학번도 나온다.

### 그룹 함수 (GROUPING SETS · ROLLUP · CUBE) — 기출 18회 (2026 3 · 2025 4 · 2024 4 · 2023 4 · 2022 3)
| 함수 | 칼럼 3개(A, B, C)일 때 그룹 수 | 만들어지는 그룹 |
|------|------------------|------|
| `GROUPING SETS(A, B, C)` | **3** | 각 칼럼별 개별 집계. 전체 합계는 없음 |
| `ROLLUP(A, B, C)` | **4** (n+1) | (A,B,C), (A,B), (A), 전체. **순서가 중요** |
| `CUBE(A, B, C)` | **8** (2ⁿ) | 가능한 모든 조합 |

- **인수 순서**: **ROLLUP은 인자 순서가 바뀌면 결과가 달라진다.** CUBE·GROUPING SETS는 순서와 상관없이 결과 집합이 같다(출력 순서만 달라질 수 있다). 순서가 결과를 바꾸는 것은 **ROLLUP뿐**이다.
- **ROLLUP(A, B)에는 없고 CUBE(A, B)에만 있는 것**: `(B)` 단독 소계, 즉 (NULL, B) 행.
- **같은 결과 바꿔 쓰기**

| 구문 | 같은 표현 |
|------|-----------|
| `ROLLUP(A, B)` | `GROUPING SETS((A, B), (A), ())` |
| `CUBE(A, B)` | `GROUPING SETS(A, B, (A, B), ())` |
| `GROUPING SETS(A, B)` | `GROUP BY A UNION ALL GROUP BY B` |
| `ROLLUP(A)` | `CUBE(A)` = `GROUP BY A` + 전체 합계 |

  - 세 확장 함수 모두 **일반 GROUP BY + UNION ALL**로 같은 결과를 만들 수 있다. 함정: "ROLLUP과 같은 결과는 추출할 수 없다" → 틀림.
- **빈 괄호 `()`는 전체 합계**를 뜻한다. `GROUPING SETS`에 `()`를 넣어야 전체 합계가 생긴다.
  - 예: `GROUPING SETS(ProductName, ())` → 상품별 합계 + 전체 합계
  - `GROUPING SETS(A, B, ())` → (A), (B), ()
- **괄호로 묶은 칼럼은 하나의 단위**로 취급한다.
  - 예: `GROUPING SETS(자재번호, (발주처ID, 발주일자))` → 자재번호별 소계 + (발주처ID, 발주일자)별 소계
  - `ROLLUP((A, B))` → (A, B), () 두 단계만. **중간 소계 없이** 세부 + 총계.
  - `ROLLUP((A), B)`, `ROLLUP(A, (B))` → `ROLLUP(A, B)`와 같다.
  - `GROUPING SETS(A, (A, B))` → (A) 소계 + (A, B) 세부. 총계 없음.
- **일반 칼럼과 섞기**: GROUP BY의 일반 칼럼은 모든 그룹에 곱해진다.
  - `GROUP BY A, ROLLUP(B)` → (A, B), (A). **전체 총계가 없다.**
  - `GROUP BY ROLLUP(A, B), C` → (A, B, C), (A, C), (C)
  - `GROUP BY ROLLUP(COL1), COL1` → (COL1, COL1), (COL1) → COL1 그룹이 **두 번** 나온다. (그룹 3개면 6행)
- `GROUPING SETS` 안의 `NULL`이나 `ROLLUP(…, NULL)`의 NULL은 상수 그룹이라 전체 합계처럼 동작한다. 중복된 상세 집계는 `DISTINCT`로 없앨 수 있다.
- **결과 행 수 세기**: 각 그룹 단위별 서로 다른 값의 수를 더한다.
  - 예: (D, P) 조합 5개, D 2종, P 3종 → `ROLLUP(D, P)` 5 + 2 + 1 = **8**, `ROLLUP((D, P))` 5 + 1 = **6**, `CUBE(D, P)` 5 + 2 + 3 + 1 = **11**, `GROUPING SETS((D), (P))` 2 + 3 = **5**
  - CUBE도 **데이터에 실제로 있는 조합만** 만든다.
- 소계·총계 행에서 집계 대상이 아닌 그룹 칼럼 값은 **NULL**이다. 함정: "가장 작은 값을 반환한다" → 틀림.
- 정렬이 필요하면 **ORDER BY를 따로** 쓴다. 함정: "ROLLUP·CUBE·GROUPING SETS는 정렬할 수 없다" → 틀림.
- **CUBE는 모든 조합을 계산하므로 시스템 부하가 가장 크다.** 함정: "ROLLUP이 CUBE보다 부하가 크다" → 틀림.
- GROUP BY에 없는 칼럼(예: 지역명)을 출력하려면 `MIN(지역명)`처럼 집계 함수로 감싼다.

### GROUPING 함수 — 기출 3회 (2025 2 · 2023 1)
- **`GROUPING(칼럼)`**: 그 칼럼이 소계·총계 때문에 NULL이 된 행이면 **1**, 일반 그룹 행이면 **0**.
- **데이터의 진짜 NULL과 집계 NULL을 구분**한다.
  - 예: 원본에 A가 NULL인 행이 있으면 `ROLLUP(A)` 결과에 NULL 행이 두 개 생긴다. 데이터 NULL 그룹은 `GROUPING(A) = 0`, 총계 행은 `GROUPING(A) = 1`이다.
  - 그래서 `NVL`·`COALESCE`로는 둘을 구분하지 못한다.
- `ROLLUP(DEPT, JOB)`에서 판별

| 행 | GROUPING(DEPT) | GROUPING(JOB) |
|----|:-:|:-:|
| 세부 (DEPT, JOB) | 0 | 0 |
| 부서별 소계 (DEPT, NULL) | 0 | **1** |
| 전체 총계 (NULL, NULL) | **1** | **1** |

- 라벨 붙이기: `CASE WHEN GROUPING(DEPT) = 1 THEN '전체' ELSE DEPT END`. 함정: `WHEN 0 THEN '전체'` → 틀림.
- `HAVING GROUPING(A) + GROUPING(B) != 1` → 세부 행과 전체 총계만 남고 중간 소계가 빠진다.
- GROUPING은 **ROLLUP·CUBE·GROUPING SETS 모두**에서 쓸 수 있다. 함정: "CUBE에서만", "ROLLUP에서만" → 틀림.
- **`GROUPING_ID(A, B, …)`**: 각 칼럼의 GROUPING 값(0/1)을 이어 붙인 **이진수를 십진수로** 반환한다. 어떤 조합의 소계인지 한 번에 구분한다.
  - 예: A 그대로(0), B 소계(1) → `01` → 1

### 윈도우 함수 기본 · 윈도우 절 (ROWS · RANGE) — 기출 13회 (2026 2 · 2025 2 · 2024 4 · 2023 3 · 2022 2)
- **분류**

| 분류 | 함수 |
|------|------|
| 순위 | RANK, DENSE_RANK, ROW_NUMBER |
| 집계 | SUM, MAX, MIN, AVG, COUNT |
| **행 순서** | **FIRST_VALUE, LAST_VALUE, LAG, LEAD** |
| **비율** | **RATIO_TO_REPORT, PERCENT_RANK, CUME_DIST, NTILE** |

  - 함정: "User Defined Window Function" → 표준 분류가 아니다.
  - 함정: RANK는 행 순서 함수가 아니다. RATIO_TO_REPORT는 순위 함수가 아니다.
- 윈도우 함수는 **결과 건수를 줄이지 않는다.** (GROUP BY와 다른 점)
  - 함정: "윈도우 함수 처리로 결과 건수가 줄어든다" → 틀림
- 윈도우 함수는 **WHERE 절에 직접 쓸 수 없다**. 인라인 뷰에서 계산하고 바깥 WHERE에서 거른다.
- **PARTITION BY**
  - `PARTITION BY`와 `GROUP BY`는 의미가 비슷하다(묶는 기준).
  - `PARTITION BY`가 없으면 **전체를 하나의 파티션**으로 본다. 윈도우 적용 범위는 **파티션을 넘을 수 없다**.
  - 함정: "OVER 절에는 PARTITION BY가 반드시 필요하다" → 틀림. 생략하면 전체 행이 대상이다.
- **OVER 형태별 결과** (집계 윈도우 함수)

| OVER 형태 | 결과 |
|------|------|
| `OVER ()` | 파티션·정렬 없음 → **전체 합계**가 모든 행에 반복 |
| `OVER (PARTITION BY 부서)` | 부서 합계가 같은 부서 모든 행에 반복. **행 수는 줄지 않는다** |
| `OVER (ORDER BY 칼럼)` (프레임 생략) | 기본값 **`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`** → **누적 합계** |

- SUM·MAX·MIN 같은 집계 윈도우 함수에 **윈도우 절**(프레임)을 붙이면 **집계 대상 행 범위**를 정할 수 있다. GROUP BY 없이 누적 합계 같은 계산을 한다.
- **ROWS vs RANGE** (정렬 키에 중복이 있을 때 차이가 난다)

| 키워드 | 기준 | 특징 | 100, 200, 200, 500 누적합 |
|--------|------|------|---------------------------|
| **ROWS** | **물리적 행 개수** | `1 PRECEDING` = 바로 이전 행 하나 | 100, 300, 500, 1000 |
| **RANGE** | **정렬 기준 값의 범위** | `50 PRECEDING` = 현재 값 −50 이상인 행. **값이 같은 행은 항상 서로 포함**(한 묶음) | 100, **500, 500**, 1000 |

  - "일자별 누적합"처럼 같은 키를 한 번에 묶으려면 **RANGE**(또는 생략). 행마다 따로 누적하려면 **ROWS**를 명시한다.
  - 보기 중 결과가 다른 하나 찾기: `ORDER BY X`(생략) = `RANGE UNBOUNDED PRECEDING` = `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` ≠ `ROWS BETWEEN …`
- **축약형**: 시작점만 쓰면 끝점은 **CURRENT ROW**다. `ROWS UNBOUNDED PRECEDING` = `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`
- 자주 나오는 프레임

| 프레임 | 의미 |
|--------|------|
| `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` | 앞 1행 + 현재 행 + 뒤 1행 (이동 합계·평균). 파티션의 첫 행·마지막 행은 2개만 더한다 |
| `ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING` | 현재 행부터 마지막 행까지 |
| `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` | 파티션 전체 |
| `ROWS BETWEEN CURRENT ROW AND CURRENT ROW` | 현재 행 하나 → `MAX(SAL)`이 자기 값 |
| `RANGE BETWEEN 100 PRECEDING AND 200 FOLLOWING` | 현재 **값 −100 ~ +200** 범위의 행 |

- **RANGE 계산 예**
  - ID = 1, 2, 3, 4이고 VAL = 3, 4, 5, 6일 때 `SUM(VAL) OVER (ORDER BY ID RANGE BETWEEN 2 PRECEDING AND 2 FOLLOWING)`
    - ID=1: ID 값 -1~3 → 3+4+5 = 12
    - ID=2: 0~4 → 18 / ID=3: 1~5 → 18 / ID=4: 2~6 → 15
  - VAL 4, 5, 6에 `SUM … ORDER BY VAL RANGE BETWEEN 2 PRECEDING AND 2 FOLLOWING` → 세 값이 모두 서로 ±2 안이라 모든 행이 **15**.
  - 값 50, 100, 150, 150, 450에 `RANGE BETWEEN 50 PRECEDING AND 50 FOLLOWING`으로 COUNT → 100은 50~150 범위라 4, 150은 100~200 범위라 3
- **문법 제약**
  - **UNBOUNDED PRECEDING은 끝점에 쓸 수 없다.** `… AND UNBOUNDED PRECEDING` → 오류. (반대로 UNBOUNDED FOLLOWING은 시작점에 못 쓴다)
  - 프레임(ROWS·RANGE) 절을 쓰려면 **ORDER BY가 있어야** 한다. RANGE n PRECEDING은 정렬 키가 숫자·날짜여야 한다.
  - 함정: "`ROWS BETWEEN 1 AND 2`", "`ROWS CURRENT ROW ONLY`" → 없는 문법.
- **GROUP BY와 윈도우 함수는 함께 쓸 수 있다.** 윈도우 함수는 GROUP BY 결과 행에 적용된다.
  - 예: `GROUP BY 분류코드` + `COUNT(*) OVER (ORDER BY AVG(가격) RANGE BETWEEN 10000 PRECEDING AND 10000 FOLLOWING)` → 평균가가 ±10000 안인 **분류코드의 개수**. 개별 상품 수가 아니다.
  - 함정: "OVER의 ORDER BY에 집계 함수를 써서 오류", "GROUP BY와 함께 써서 오류" → 틀림.
  - 반대로 `SUM(SAL)`(OVER 없음)을 일반 칼럼과 같이 쓰면 일반 집계라 GROUP BY가 필요하다.

### 순위 · 비율 함수 — 기출 16회 (2026 2 · 2025 3 · 2024 4 · 2023 4 · 2022 3)
값이 100, 100, 90일 때 순위:

| 함수 | 결과 | 특징 |
|------|------|------|
| `RANK()` | 1, 1, **3** | 동일 순위 다음 순위를 건너뜀 |
| `DENSE_RANK()` | 1, 1, **2** | 건너뛰지 않음 |
| `ROW_NUMBER()` | 1, 2, 3 | 같은 값이어도 고유한 순번 |

- 순위 함수(RANK, DENSE_RANK, ROW_NUMBER)는 `OVER` 안에 **ORDER BY가 반드시 필요**하다. 함정: "순위 함수 사용 시 ORDER BY절은 입력하지 않아도 된다" → 틀림.
- **PARTITION BY**를 쓰면 파티션마다 순위가 **1부터 다시** 시작한다. (예: 부서 10 → 1, 2 / 부서 20 → 1, 2)
- 같은 "순위 ≤ N" 조건이라도 함수에 따라 결과 행 수가 다르다. 급여 150, 150, 140, 130에서 `≤ 2`일 때:

| 함수 | 부여 순위 | `≤ 2` 행 수 |
|------|-----------|-------------|
| ROW_NUMBER | 1, 2, 3, 4 | 2 |
| RANK | 1, 1, 3, 4 | 2 |
| DENSE_RANK | 1, 1, 2, 3 | **3** |

- "동순위 포함, 다음 순위를 건너뛰지 않고 **상위 N위까지**" → **DENSE_RANK**.
- 순위로 거르기: 인라인 뷰에서 순위를 매기고 바깥 WHERE에서 거른다. (예: 유형별 최신 글 1건 → `ROW_NUMBER() OVER (PARTITION BY 유형 ORDER BY 등록일 DESC)` 후 `RN = 1`)
  - `ROW_NUMBER() … AS RN`을 같은 SELECT의 WHERE에서 `RN <= 2`로 거르면 오류다. 별칭은 WHERE에서 못 쓴다.
- Oracle 내림차순 순위에서는 **NULL이 가장 큰 값**이라 **1위**가 된다. (NULL, 20, 10, 10 → RANK 1, 2, 3, 3)
- `ROWNUM`은 의사 칼럼이라 `OVER` 절과 함께 쓸 수 없다.
- 존재하지 않는 함수: **CUMM_RANK, RCUMM_RANK, PERFECT_RANK, ROW(), ROW_NUM()** → 보기에 나오면 오답이다.
- **비율 함수**

| 함수 | 계산 | 범위 |
|------|------|------|
| **PERCENT_RANK** | (RANK − 1) / (전체 건수 − 1). 값의 비율이 아니라 **위치**의 백분율 | **0 ~ 1** (첫 행 0, 마지막 행 1) |
| **CUME_DIST** | 현재 행 **이하** 건수 / 전체 건수 = 누적 분포 | **0 초과 ~ 1** (첫 행도 0이 아님) |
| **RATIO_TO_REPORT(값)** | 값 / 파티션 **합계** (합계 100, 값 20 → 0.2) | 0 ~ 1 소수 |
| **NTILE(n)** | 전체 행을 n개 그룹으로 최대한 균등하게 나눈다 | **1 ~ n** |

  - 함정: "PERCENT_RANK로 부서 내 급여 비율을 구한다" → 틀림. 급여 비율은 RATIO_TO_REPORT다.
  - 함정: "PERCENT_RANK는 누적된 순위를 부여한다" → 틀림.
  - **NTILE**: 나머지는 **앞 그룹부터** 1개씩 더 받는다.
    - 예: 8행을 `NTILE(3)`으로 나누면 3, 3, 2
    - 함정: "NTILE(4)의 값 범위는 0~3" → 틀림.

### 행 순서 함수 (LAG · LEAD · FIRST_VALUE · LAST_VALUE) — 기출 9회 (2026 2 · 2025 1 · 2024 1 · 2023 3 · 2022 2)
- `LAG(칼럼)`: 정렬 기준 **이전 행**의 값 (첫 행은 NULL)
- `LEAD(칼럼)`: **다음 행**의 값 (마지막 행은 NULL)
- 형식: `LAG(칼럼, 오프셋, 기본값)`, `LEAD(칼럼, 오프셋, 기본값)`
  - 오프셋 기본값은 1, 해당 행이 없을 때 기본값은 NULL이다.
  - 예: `LAG(VAL, 2, 0)` → 두 행 앞 값, 없으면 0 (첫 두 행이 0). `LEAD(VAL, 1, -1)` → 마지막 행이 -1.
- **음수 오프셋**도 쓸 수 있다. `LEAD(VAL, -1)` = `LAG(VAL, 1)`
- `LAG … ORDER BY … DESC`는 오름차순 기준으로 보면 다음 행을 가져온다. 즉 LEAD와 같은 효과다.
  - 같은 "직전 행" 값을 주는 조합: `LAG(1) … ORDER BY ID` = `LEAD(-1) … ORDER BY ID` = `LEAD(1) … ORDER BY ID DESC`. `LAG(1) … ORDER BY ID DESC`만 반대(다음 행)다.
- 결과에 LAG를 섞어 계산하면 첫 행은 NULL이 끼어 **결과도 NULL**이다. (예: `AMT - LAG(AMT)` → 첫 행 NULL)
- LAG·LEAD를 쓰지 않고 전일 대비를 구하려면 ROWNUM 순번을 만든 두 인라인 뷰를 순번으로 조인한다.
- **FIRST_VALUE**: 정렬된 윈도우의 첫 값. `ORDER BY SAL` 오름차순이면 모든 행에서 **최솟값** → **MIN**과 같이 쓸 수 있다.
- **LAST_VALUE의 함정**: 프레임 생략 시 범위가 "처음 ~ 현재 행"이라 **현재 행 자기 값**이 나온다. (10, 20, 30, 40 → 10, 20, 30, 40)
  - 파티션 전체의 마지막 값을 얻으려면 `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`을 명시한다.
- **KEEP (DENSE_RANK FIRST|LAST ORDER BY …)** (Oracle)
  - 정렬 기준으로 **첫(또는 마지막) 순위 그룹의 행들만** 골라 그 안에서 집계한다.
  - 예: COL2가 1인 행이 COL1 = 10, 20이고 COL2가 2인 행이 30이면 `MAX(COL1) KEEP (DENSE_RANK FIRST ORDER BY COL2)` → **20**, `MIN(COL1) KEEP (DENSE_RANK LAST ORDER BY COL2)` → **30**
  - 용도: 부서별 급여 1위 사원의 이름 가져오기 등. LAG·LEAD·백분위와 다르다.

### Top-N (OFFSET · FETCH) — 기출 14회 (2026 3 · 2025 3 · 2024 3 · 2023 3 · 2022 2)
- DBMS별 방법

| DBMS | 방법 |
|------|------|
| Oracle | `ROWNUM`, `FETCH FIRST`(**12c 이상**. 11g 이하는 인라인 뷰 + ROWNUM) |
| SQL Server | `TOP(n)`, `TOP(n) WITH TIES` |
| MySQL | `LIMIT` (Oracle에서는 쓸 수 없다) |

- `OFFSET n ROWS`: 처음 n건을 **건너뛴다**.
- `FETCH FIRST k ROWS ONLY`: **최대 k건**만 반환한다. k건을 넘지 않는다.
  - `OFFSET 2 ROWS FETCH NEXT 1 ROWS ONLY` → 정렬 후 **3번째 행** 1건. `FIRST`·`NEXT`, `ROW`·`ROWS`는 같은 뜻이다.
  - FETCH는 행 개수 대신 **백분율**(`PERCENT`)도 지정할 수 있다.
  - 함정: `ORDER BY` 없이 `FETCH FIRST n ROWS ONLY` → 어떤 n건이 나올지 보장되지 않는다.
- `FETCH … WITH TIES`: 마지막 순위와 값이 같은 행까지 포함한다. SQL Server `TOP(n) WITH TIES`도 n번째와 값이 같은 행까지 포함한다.
  - 함정: "WITH TIES는 **첫 번째** 행의 동순위를 포함" → 틀림. **마지막** 행과 값이 같은 행을 포함한다.
- 동순위 포함 상위 N건: `RANK() … <= N`, `FETCH FIRST N ROWS WITH TIES`, `TOP(N) WITH TIES`
- **Oracle `ROWNUM`의 함정**
  - `WHERE ROWNUM <= 5 ORDER BY SAL`은 ROWNUM이 **정렬보다 먼저** 붙는다. 그래서 임의의 5행을 정렬한 결과가 나온다.
  - 인라인 뷰 **안에서** `ROWNUM`과 `ORDER BY`를 같이 써도 마찬가지다. 정렬을 먼저 한 인라인 뷰 **바깥에서** ROWNUM을 걸어야 한다.
  - 올바른 방법: `SELECT * FROM (SELECT * FROM EMP ORDER BY SAL DESC) WHERE ROWNUM <= 10`
- **ROWNUM 조건 판별**: ROWNUM은 조건을 **통과한 행에만** **1부터 차례로** 붙는다. 탈락하면 다음 행이 다시 같은 번호를 받는다.

| 조건 | 결과 |
|------|------|
| `ROWNUM = 1`, `ROWNUM < 2`, `ROWNUM <= 1` | 1건 |
| `ROWNUM <= 2`, `ROWNUM IN (1, 2)`, `ROWNUM = 1 OR ROWNUM = 2` | 2건 |
| `ROWNUM > 0` | 전체 |
| **`ROWNUM = 2`** (N ≥ 2), **`ROWNUM > 1`**, `ROWNUM < 1` | **0건** (첫 행이 1을 못 받아 탈락하면 다음 행이 다시 1이 됨) |
| `ROWNUM <> 3` | 1, 2번째 행만 (3번째부터 계속 3이라 탈락) |

  - n번째 행만 가져오려면 인라인 뷰에서 ROWNUM에 별칭을 붙인 뒤 바깥에서 거른다.
- `ROWNUM`은 결과 집합에 붙는 **가상 순번**이다. `ROWID`는 행의 **물리적 주소**다.

### 계층형 질의 (Oracle) — 기출 17회 (2026 3 · 2025 3 · 2024 4 · 2023 4 · 2022 3)
- `START WITH 조건`: **루트(시작) 노드** 지정. 부모가 없는 행이면 `부모칼럼 IS NULL`
  - `START WITH 상위번호 IS NULL`에 해당하는 행이 여러 개면 **루트가 여러 개**인 트리가 각각 만들어진다. 오류가 아니다.
- `CONNECT BY PRIOR 자식 = 부모`: **순방향**(부모 → 자식) 전개
  - `PRIOR`가 붙은 쪽이 **이전(이미 읽은) 행**의 값이다.
- 가상 칼럼·함수

| 키워드 | 의미 |
|--------|------|
| `LEVEL` | 계층 깊이 (루트 = 1, 내려갈수록 1씩 증가) |
| **`CONNECT_BY_ISLEAF`** | **리프면 1, 아니면 0** |
| `CONNECT_BY_ISCYCLE` | 순환이 있으면 1 (`NOCYCLE` 옵션과 함께 사용) |
| `CONNECT_BY_ROOT 칼럼` | 해당 행의 루트 노드 값 |
| `SYS_CONNECT_BY_PATH(칼럼, 구분자)` | 루트부터 현재 행까지의 경로 문자열 |

  - 리프 노드는 가장 아래 노드다. 함정: "리프 노드의 LEVEL은 항상 1" → 틀림. 1인 건 **루트**다.
  - `SYS_CONNECT_BY_PATH(칼럼, '-')`의 결과는 **구분자로 시작**한다. (예: `-컴퓨터정보학부-소프트웨어공학과`)
  - `CONNECT_BY_ISCYCLE`: 전개 중 자식을 갖는데 그 자식이 이미 **조상(루트까지 경로)에 있으면 1**. 자식 유무(리프 여부)와는 다르다.
  - TRIM 같은 일반 문자열 함수는 계층형 전용 함수가 아니다.
- **방향 정리** (부모 칼럼 = 상위번호)
  - 순방향(부모 → 자식): `CONNECT BY PRIOR 번호 = 상위번호`
  - **역방향(자식 → 부모)**: `CONNECT BY 번호 = PRIOR 상위번호`
    - 예: `START WITH 카테고리번호 = 11 CONNECT BY 카테고리번호 = PRIOR 상위카테고리번호` → 11 → 5 → 2 → 1로 올라간다.
    - `PRIOR`를 왼쪽에 두고 쓸 수도 있다: `CONNECT BY PRIOR MGR = EMPNO` (= `EMPNO = PRIOR MGR`)
  - **문제마다 '부모·자식' 칼럼 이름 붙이는 방식이 다르다.** 단어보다 칼럼 의미로 판단한다. PRIOR가 **자기 번호(EMPNO)**에 붙으면 순방향, **상위 번호(MGR)**에 붙으면 역방향이다.
  - 하나의 CONNECT BY 조건으로 순방향·역방향이 **동시에** 전개되지는 않는다.
- **조건 위치에 따른 차이** (핵심)

| 위치 | 적용 시점 | 효과 |
|------|-----------|------|
| `START WITH` | 전개 시작 | 루트 행 지정 |
| `CONNECT BY … AND 조건` | **전개 중** | 조건에 안 맞는 노드와 그 **하위 가지 전체**가 빠진다 |
| `WHERE` | **전개가 모두 끝난 뒤** | 그 행만 빠지고 자식·부모는 남는다 |

  - 예: 역방향 SCOTT → JOHN → KING에서 `WHERE 이름 <> 'JOHN'` → SCOTT, KING 2건. `CONNECT BY … AND 이름 <> 'JOHN'` → 위로 이어지지 못해 SCOTT 1건.
  - 함정: "WHERE 절 조건은 계층 전개 이전에 적용된다" → 틀림.
  - 전개 자체를 막으려면 `START WITH`나 `CONNECT BY` 쪽에 조건을 넣는다.
- `CONNECT BY PRIOR 번호 = 상위번호 AND PRIOR 칼럼 = 'B'` → **부모 행**의 칼럼이 'B'일 때만 자식으로 내려간다.
- `PRIOR`는 CONNECT BY 외에 **SELECT 절에도** 쓸 수 있다. 함정: "PRIOR는 CONNECT BY 절에만 사용할 수 있다" → 틀림.
- 특정 노드의 상위 코드를 찾는 방법: 루트부터 전체를 전개한 뒤 `WHERE 코드 = X`로 거르고 SELECT에 상위코드를 쓴다.
- **순환 데이터**
  - `NOCYCLE`: 순환이 생겨도 무한 루프에 빠지지 않게 한다. 붙여서 한 단어로 쓴다. (`NO CYCLE`, `NOCYCLES` → 틀림)
  - NOCYCLE 없이 실행하면 무한 반복이 아니라 **오류**가 난다.
  - NOCYCLE을 주면 순환이 생기는 지점에서 **전개를 멈추고** 그때까지 방문한 행만 반환한다. 함정: "순환 이후 데이터까지 포함해 출력" → 틀림.
- 전개 중 연결할 키가 NULL이면 그 가지는 더 전개되지 않는다. (오류·무한 전개 아님)
- **`ORDER SIBLINGS BY 칼럼`**: 트리 구조를 유지한 채 **같은 부모를 가진 형제끼리만** 정렬한다.
  - 일반 `ORDER BY`를 쓰면 계층 구조가 깨지고 전체가 정렬된다.
  - 예: 루트 A의 자식 B, C, D를 이름 내림차순으로 → A, D, (D의 자식), C, B, (B의 자식) 순으로 **깊이 우선** 배치
  - 함정: "전체 트리를 무시하고 완전히 재정렬" → 틀림.
- **행 생성 패턴**: `SELECT … FROM DUAL CONNECT BY LEVEL <= n` → n개 행 (`LEVEL <= 2`면 COUNT 2)
- 계층형 질의는 한 테이블 안의 부모·자식 관계를 다루므로 **셀프 조인** 개념이다.
- **Oracle vs SQL Server**

| 구분 | Oracle | SQL Server |
|------|--------|------------|
| 문법 | `START WITH` · `CONNECT BY` | **재귀 CTE** (WITH 절) |
| 전개 방식 | PRIOR로 부모·자식 연결 | **앵커 멤버**로 기본 결과를 만들고 **재귀 멤버**를 반복 실행 |

### PIVOT — 기출 6회 (2026 3 · 2025 2 · 2024 1)
- PIVOT은 **행 → 열**(LONG → WIDE), UNPIVOT은 **열 → 행**(WIDE → LONG)이다. 함정: "UNPIVOT은 LONG을 WIDE로" → 틀림.
- 형식: `PIVOT (집계함수(값) FOR 기준칼럼 IN (값1 AS 별칭1, …))`
- `FOR … IN`에 적은 값이 **칼럼명**으로 올라가고, 집계 결과가 그 안을 채운다.
- `AS 별칭`이 있으면 칼럼명은 값(10, 20 …)이 아니라 **별칭**(A, B …)이 된다.
- PIVOT의 `FOR` 앞에는 **반드시 집계 함수**가 와야 한다. 함정: "집계 함수 없이 사용할 수 있다" → 틀림.
- 해당 조합의 데이터가 없는 칸은 0이 아니라 **NULL**이다.
- PIVOT에 쓰이지 않은 나머지 칼럼으로 **자동 GROUP BY**된다.
  - 그래서 필요한 칼럼만 인라인 뷰로 먼저 고른다. 예: `(SELECT EMPNO, DEPTNO FROM EMP) PIVOT (COUNT(EMPNO) FOR DEPTNO IN (10, 20, 30))` → 부서별 인원
  - 결과 칼럼 = 남은 칼럼 + IN 값들 (예: dept, Q1, Q2). 결과 행 수 = 남은 칼럼의 서로 다른 값 수.
- 반대 작업은 `UNPIVOT`이다.
- **UNPIVOT 형식**: `UNPIVOT (값칼럼 FOR 구분칼럼 IN (원본칼럼1, 원본칼럼2, …))`
  - 첫 자리 = 여러 칼럼의 **값이 쌓여 들어갈 칼럼명** (예: 판매량)
  - FOR 뒤 = 원래 **칼럼 이름이 값으로 들어갈 칼럼명** (예: 연도 → 2023, 2024)
  - IN에는 **풀어낼 원본 칼럼명**을 쓴다. 그 칼럼명이 구분칼럼의 값이 되고, 칼럼 값은 값칼럼에 담긴다.
  - IN에 적은 칼럼 순서를 바꿔도 행 수와 값 매핑은 같다. 출력 순서만 바뀐다.
  - 기본적으로 **NULL 값 행은 제외**한다. 유지하려면 `INCLUDE NULLS`
  - 대상 칼럼은 2개 이상이면 된다.

### 인덱스 종류 — 기출 없음
| 종류 | 특징 |
|------|------|
| **B-Tree** | 루트·**브랜치 블록**(분기)과 **리프 블록**(칼럼값 + ROWID)으로 구성. OLTP에서 가장 일반적 |
| Bitmap | 값이 있으면 1, 없으면 0으로 저장. **DW(정보계)**·대량 조회·카디널리티가 낮은 칼럼에 적합 |
| Clustered (SQL Server) | 인덱스 순서대로 데이터가 **물리적으로 정렬**되어 저장됨 |
| **함수 기반 인덱스** | 칼럼에 함수·연산을 적용한 값으로 만든 인덱스 |

- 인덱스는 내림차순으로도 만들 수 있다. ("항상 오름차순" → 틀림)
- 인덱스 범위 스캔은 결과가 없으면 0건을 반환할 수도 있다.
- **인덱스를 못 쓰는 조건**: **인덱스 칼럼 쪽을 가공**한 경우다.
  - `NVL(칼럼, 0)`, `TO_CHAR(칼럼, …)`, `칼럼 || ' '`, `칼럼 + 1 = 5`
  - 이럴 때는 **함수 기반 인덱스**가 필요하다.
  - `LIKE '%홍길동%'`처럼 **앞에 %**가 오는 경우
  - 숫자 칼럼에 `LIKE`를 쓰면 **내부 형변환**이 일어나 Full Scan이 된다. PK라서 인덱스가 있어도 마찬가지다.
  - 상수 쪽만 가공하면 쓸 수 있다: `칼럼 = TO_CHAR(SYSDATE, 'YYYY')`
- **복합 인덱스 (col1, col2)**: **선두 칼럼(col1) 조건**이 있어야 잘 탄다. `col2`만 조건이면 효율이 낮다.
  - 두 칼럼 모두 `=` 조건이면 순서를 바꿔도 스캔 효율 차이가 없다.
- **Full Table Scan이 유리한 경우**
  - 데이터가 아주 적을 때(예: 1건)
  - **선택도가 나쁜 칼럼**(값 종류가 적어 많은 행이 걸림)이나 읽을 행 비율이 아주 높은 조회. 인덱스 + 랜덤 접근보다 낫다.
- 인덱스가 많으면 **INSERT·UPDATE·DELETE가 느려진다.** 데이터를 바꿀 때 인덱스도 함께 유지해야 하기 때문이다.
- **NULL과 인덱스**

| 구분 | Oracle | SQL Server |
|------|--------|------------|
| 모두 NULL인 행 | **인덱스에 저장하지 않는다** (하나라도 값이 있으면 저장) | 저장한다 |
| NULL 위치 | **맨 뒤** | **맨 앞** |

- **인덱스 튜닝**
  - 인덱스 칼럼 순서를 바꿔도 **테이블 랜덤 액세스 횟수는 줄지 않는다**. 스캔 효율만 달라진다.
  - 테이블 액세스 후 대부분 필터링된다면 그 조건 칼럼을 **인덱스에 추가**한다.
  - 랜덤 액세스 부하가 크면 클러스터 테이블·IOT를 고려한다.

### 옵티마이저 · 실행 계획 · 조인 수행 방식 — 기출 2회 (2022 2)
- **옵티마이저**

| 구분 | 규칙 기반(RBO) | 비용 기반(CBO) |
|------|------|------|
| 판단 기준 | 규칙 우선순위. **통계 정보를 쓰지 않는다** | **통계 정보**로 비용을 계산 |
| 인덱스 | 적절한 인덱스가 있으면 **항상 인덱스를 사용**하려 한다 | 인덱스가 있어도 테이블 전체 스캔이 더 유리하다고 판단할 수 있다 |
| 비고 | 우선순위 중 **가장 낮은 것이 전체 테이블 스캔** | |

  - 함정: "CBO는 적절한 인덱스가 있으면 반드시 사용한다" → 틀림. RBO 설명이다.
- **실행 계획**
  - 실행 계획이 달라도 **결과는 같다**. 성능만 달라진다.
  - 구성: 액세스 기법, 조인 순서, 조인 방법
  - 읽는 순서: **안에서 밖으로**, 같은 레벨이면 **위에서 아래로**
  - 인덱스 사용 시 흐름: `INDEX RANGE SCAN` → `TABLE ACCESS BY INDEX ROWID`
  - **SQL 처리 흐름도**는 실행 계획을 시각화한 것이다. 성능(일량) 측면도 표현할 수 있다.
- **조인 수행 방식**
  - FROM에 테이블이 많아도 조인은 **항상 2개씩** 수행한다.

| 방식 | 동작 | 유리한 상황 · 특징 |
|------|------|------|
| **NL(Nested Loop) Join** | 바깥(선행) 테이블 한 행마다 안쪽(후행) 테이블을 탐색한다. 선행 테이블에서 조건을 만족하는 건수만큼 반복 | 소량 데이터. 선행 처리 건수가 **적고** 후행 조인 키에 **인덱스가 있을 때**. **랜덤 액세스**가 생긴다 |
| **Sort Merge Join** | 양쪽을 **정렬한 뒤 병합**한다 | PK–FK 관계에서 **FK에 인덱스가 없을 때** NL보다 유리할 수 있다 |
| **Hash Join** | 해시 테이블을 만든다. **작은 테이블을 선행**으로 둔다 | 대용량. **등가(=) 조인만** 가능. 조인 칼럼에 **인덱스가 없어도** 된다. CPU를 많이 쓰고 랜덤 액세스는 없다 |

  - 함정: "Hash Join은 비등가 조인도 가능" → 틀림 / "Hash Join은 랜덤 액세스 부하가 있다" → 틀림

## 부록 — 정답·해설이 의심스러운 문제

아래 문제는 사이트 정답이나 해설이 일반적인 교재와 다르거나 모순돼서 본문에 넣지 않았거나 교재 기준으로 넣은 것이다.

### 1과목
- **주식별자가 없어도 되는 예외 엔터티**: 사이트 정답 "관계 엔터티" → 교재 내용은 "관계 엔터티는 **주식별자 속성만 있어도**(일반 속성 없이) 엔터티로 인정"이다. 주식별자가 없어도 된다는 뜻이 아니다.
- **고객이 서비스를 하나만 계약할 수 있는 제약을 반영한 모델**: 사이트 정답 "고객─서비스계약─서비스 연결 엔터티" → 고객당 서비스가 하나면 M:N이 아니라 고객에 서비스 FK를 두는 1:M 구조가 맞다. 해설도 "M:N 분해"라고 해서 문제 조건과 모순된다.
- **고객이 서비스를 하나만 가질 때 정규화된 형태**: 사이트 정답 "서비스계약에 고객번호·서비스번호만 둔다" → PK가 (고객번호, 서비스번호)여도 한 고객이 여러 서비스를 가질 수 있다. 문제 조건(고객당 1개)을 보장하지 못한다.
- **ERD 식별자 ①~④ 분류**: 사이트 정답 "주식별자-보조식별자-본질식별자-복합식별자" → 해설이 "인위적으로 부여한 결합 PK = 복합식별자", "수강일자 = 본질식별자"라고 설명해 분류 기준(대체 여부·속성 수)을 섞어 쓴다.
- **'일재고' 엔터티 설명**: 사이트 정답 "1차 정규화 대상, 1:M" → 보기가 다른 문제의 내용을 그대로 복사해 질문과 맞지 않는다.
- **슈퍼·서브타입에서 개별 테이블 접근이 많을 때 변환 방식**: 사이트 정답 "One To One"(교재와 같음) → 해설의 Plus 정의("슈퍼 없이 서브별로 묶는다")가 부정확하다. 본문에는 교재 기준 정의(서브마다 테이블, 슈퍼 공통 속성을 각 서브에 포함)로 넣었다.
- **카디널리티 계산식**: 사이트 정답 "선택도 × 전체 레코드 수" → 이 식은 옵티마이저의 예상 행 수(카디널리티) 개념이다. 해설은 엔터티 관계의 카디널리티(1:1, 1:N)와 섞어서 설명한다.
- **무결성 확보 방안이 아닌 것**: 사이트 정답 "Lock"(교재와 같음) → 해설의 "트리거는 동시성 문제로 실제 업무에서 사용하지 않는다"는 교재에 없는 단정이다. 교재는 트리거를 무결성 확보 방법으로 본다.
- **인조식별자 설명 중 틀린 것**: 사이트 정답 "인조식별자는 대체로 본질식별자가 복잡할 때 만들어진다" → 교재와 다른 문제는 이 문장을 맞는 설명으로 본다. 교재 기준으로 틀린 보기는 "인조식별자를 쓰면 중복 데이터를 막을 수 있다"(중복 발생 가능성이 단점)이다.
- **속성 설명 중 틀린 것**: 사이트 정답 "파생속성은 많이 정의할수록 좋다"(교재와 같음) → 맞는 보기로 둔 "기본속성의 예는 일련번호"가 틀렸다. 일련번호는 설계 속성이다.
- **엔터티 발생 시점 분류가 아닌 것**: 사이트 정답 "중심엔터티" → 교재는 발생 시점 분류를 기본·중심·행위로 본다. 다른 문제에서도 사건 엔터티를 정답으로 한다.
- **논리적 데이터 독립성 설명**: 사이트 정답 "개념 스키마가 바뀌지 않으면 외부 스키마는 물리 저장 방식 변경의 영향을 적게 받는다" → 물리 저장 변경과 무관한 것은 물리적 독립성이다. 논리적 독립성은 개념 스키마가 바뀌어도 외부 스키마가 영향받지 않는 것이다.

### 2과목
- **NULL 설명 중 틀린 것**: 사이트 정답 "NULL 포함 칼럼의 SUM은 항상 NULL"(교재와 같음) → 맞는 보기로 둔 "NULL과의 비교 연산은 FALSE를 리턴"이 부정확하다. 결과는 UNKNOWN이다.
- **뷰 특징 중 틀린 것(두 문제)**: 사이트 정답 "뷰를 참조하는 뷰는 생성 불가", "뷰는 물리적으로 구현되어 있다"(둘 다 교재와 같음) → 맞는 보기로 둔 "기본 테이블을 삭제하면 그 위의 뷰도 자동 삭제된다"가 Oracle 동작과 다르다. 뷰는 남고 INVALID 상태가 되어 실행 시 오류가 난다.
- **서브쿼리 안에서 ORDER BY를 쓸 수 없는 형태**: 사이트 정답 "WHERE 절 다중 행 서브쿼리" → 스칼라 서브쿼리도 ORDER BY를 쓰면 Oracle에서 오류라 정답이 하나로 정해지지 않는다. 교재는 "인라인 뷰 외 서브쿼리에는 ORDER BY 불가"로 설명한다.
- **서브쿼리 설명 중 틀린 것**: 사이트 정답 "메인쿼리는 스칼라 서브쿼리의 칼럼을 쓸 수 없다" → 다른 문제는 "메인쿼리는 서브쿼리 칼럼을 쓸 수 없다"를 옳은 설명으로 채점한다. 해설도 반대 결론이라 문제 사이의 기준이 충돌한다.
- **트랜잭션 특징이 아닌 것**: 사이트 정답 "독립성" → 다른 문제에서는 "독립성(Isolation)"을 고립성과 같은 뜻의 정답 보기로 쓴다. 번역어 차이일 뿐이라 오답 근거가 약하다.
- **칼럼 변경 설명 중 틀린 것**: 사이트 정답 "타입 변경은 반드시 빈 칼럼이어야 한다" → 옳은 설명으로 둔 "칼럼은 동시에 여러 개를 삭제할 수 없다"는 Oracle에서 `DROP (C1, C2)`로 가능하다. 교재의 "타입 변경은 NULL만 있을 때 가능" 서술과도 부딪힌다.
- **FK가 걸린 칼럼 삭제**: 사이트 정답 "FK 칼럼은 직접 삭제할 수 없어 오류" → Oracle은 자식 쪽 단일 칼럼 FK를 DROP COLUMN하면 제약도 함께 지운다. 다른 문제 해설도 "FK 칼럼 DROP COLUMN 가능"이라 모순된다. 해당 보기는 `DROP COLUMN` 대신 `DROP 칼럼`으로 써서 문법 오류이긴 하다.
- **무결성 위배 설명 중 옳지 않은 것**: 사이트 정답 "FK 미정의 칼럼 관련 보기"(교재와 같음) → 옳은 설명으로 둔 "NOT NULL 위반은 개체 무결성 위배"가 교재 분류(개체 무결성 = PK)와 맞지 않는다.
- **테이블 데이터와 종속된 테이블을 함께 삭제하는 명령**: 사이트 정답 `DROP TABLE … CASCADE CONSTRAINTS` → 이 옵션은 참조하는 FK 제약만 지우고 자식 테이블은 남긴다. "종속된 테이블 삭제"라는 질문 표현과 맞지 않는다.
- **PARENT_ID·CHILD_ID 구조의 순방향 CONNECT BY 조건**: 사이트 정답 `PRIOR PARENT_ID = CHILD_ID` → PARENT_ID가 상위 노드 번호를 담는 일반 구조라면 순방향은 `PRIOR CHILD_ID = PARENT_ID`다. 사이트 정답은 역방향이 된다.
- **역방향 전개 조건 문제의 해설**: 해설 "WHERE 절은 PRIOR를 쓸 수 없다" → 교재 기준 다른 해설은 "PRIOR는 SELECT·WHERE 절에서도 쓸 수 있다"고 해 모순된다. 정답 보기(`CONNECT BY EMP_ID = PRIOR MANAGER_ID`) 자체는 맞다.
- **활동점수 상위 10등 선별 SQL**: 사이트 정답 "RANK + PARTITION BY 보기" → 정답 보기에 `WHERE 순위 <= 10`이 빠져 있어 10등까지 거르지 못한다. 보기 텍스트가 잘린 것으로 보인다.
- **파티션·윈도우 절 설명 중 틀린 것**: 사이트 정답 "`AVG(SAL) OVER (PARTITION BY MGR ORDER BY … ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING)` 설명" → 그 설명(앞 1건·현재·뒤 1건 평균)은 사실상 맞다. 오히려 `COUNT(*) OVER (ORDER BY SAL) RANGE …)` 보기가 괄호 위치가 잘못된 문법 오류다.
- **Top N Query 설명 중 틀린 것**: 사이트 정답 "TOP(N)을 쓰면 정렬 순서대로 상위 N개만 출력 가능" → WITH TIES 없이 ORDER BY와 함께 쓰면 이 설명은 맞다. 오답 근거가 약하다.
- **CUBE(REGION, PRODUCT) 결과 행 수**: 사이트 정답 9 → 값은 데이터에 따라 맞을 수 있지만, 해설의 "원 테이블에 없는 조합도 무조건 생성된다"는 틀렸다. CUBE는 데이터에 있는 조합만 만든다.
- **ROLLUP(DEPTNO, JOB) 빈칸 문제**: 사이트 정답 ROLLUP → 해설이 "JOB별 합계"도 조회된다고 해 CUBE 설명과 같다. 정답과 해설이 모순된다.
- **ROLLUP 결과에 CASE-GROUPING 라벨 붙이기**: 사이트 정답 "GROUPING(DEPT)=1 → '부서별 소계'" 포함 보기 → 부서별 소계 행은 GROUPING(JOB)=1, GROUPING(DEPT)=0이다. 정답 보기 후반부가 틀렸고 해설도 스스로 정정하다 끝난다.
- **그룹 내 순위 윈도우 함수 특징 중 틀린 것**: 사이트 정답 ④ → 네 보기가 모두 같은 문장(RANK 설명)이라 문제가 깨져 있다.
- **ORDER BY 없는 조회 결과의 순서(두 문제)**: 사이트 정답 "정렬 없는 `FETCH FIRST 2 ROWS ONLY`는 저장 순서대로 상위 2건", "ORDER BY를 쓰지 않으면 입력된 순서대로 출력된다" → ORDER BY가 없으면 반환 순서는 **보장되지 않는다**. "물리적 저장·입력 순서대로"라는 설명은 일반 이론과 다르다.
- **GROUP BY 없는 SELECT의 오류 원인 분류**: 사이트 정답 "ORDER BY에서 집계 함수를 사용했으므로 오류" → 해설 스스로 "단서대로 한정한다"는 전제를 붙였다. ORDER BY에 집계 함수를 쓰는 것 자체는 허용되고, 진짜 원인은 비집계 칼럼과 섞인 것이라 분류가 애매하다.
- **다중 칼럼 IN 서브쿼리(부서별 최고 점수자) 결과**: 사이트 정답 "(200, 개발, Kim, 90) 포함" → 해설은 서브쿼리 결과를 (200, 95)로, 최종 결과를 (200, 개발, Kim, 95)로 적었다. 정답 보기와 해설이 맞지 않는다.
- **Oracle 조인을 ANSI로 바꾼 것(EMP·DEPT, DNAME 조건)**: 사이트 정답 "조인 조건은 ON, DNAME 조건은 WHERE에 둔 INNER JOIN" → `INNER JOIN … ON (조인 조건 AND DNAME 조건)` 보기도 INNER JOIN이라 결과가 같다. "조건을 나눠야 한다"는 근거만으로 하나를 고르기 어렵다.
- **INTERSECT 결과**: 사이트 정답 "B, C"(교재와 같음) → 해설의 "INTERSECT 결과는 기본적으로 오름차순 정렬된다"는 표준이 보장하지 않는다. 정렬 순서는 ORDER BY로만 보장된다.
- **"번호가 없으면 1, 있으면 MAX(번호)+1"과 같은 SQL**: 사이트 정답 `COALESCE(MAX(번호)+1, 1)` → 해설 스스로 원본 `NVL(MAX(번호),1)+1`은 데이터가 없을 때 2를 반환해 엄밀히 같지 않다고 인정한다.
- **항상 오류가 나는 SQL(`T.COL1 C1, T.COL2 AS "C1" … ORDER BY 1, "C1"`이 정상이라는 해설)**: 사이트 정답 "원래 테이블명을 쓴 보기" → Oracle에서 `C1`과 `"C1"`은 같은 식별자라 ORDER BY에서 모호성 오류가 날 수 있다. "C1을 따로 인식한다"는 해설이 의심스럽다.
- **NVL(SAL, 0) 합계 SQL 설명 중 틀린 것**: 사이트 정답 "NVL은 NULL 합계 오류를 예방한다" → 해설이 보기와 무관한 효율 얘기다. 다른 보기 "총 행 수는 2개"는 같은 문제의 다른 판본에서 5개로 나와 데이터·보기 정합성이 의심스럽다.
- **COUNT(\*)·COUNT(칼럼)·SUM(COL1+COL2+COL3) 결과**: 사이트 정답 "3, 2, 2, NULL" → 해설이 "COUNT(\*)는 모든 칼럼이 NULL일 때만 행을 제외한다"고 한다. 교재 기준으로 COUNT(\*)는 모든 칼럼이 NULL인 행도 센다.
- **윈도우 함수 설명 중 옳은 것**: 사이트 정답 "집계 윈도우 함수에 window 절로 범위 지정"(교재와 같음) → 오답 보기 "GROUP BY와 윈도우 함수는 병행 사용할 수 있다"는 Oracle에서 실제로 가능하고, 해설도 "병행이 불가능한 것은 아니다"라고 해 오답 근거가 모호하다.
- **COL100이 NULL이 아닌 행 찾기**: 사이트 정답 `IS NOT NULL`(교재와 같음) → 해설의 "NULL 값 조회는 IN NULL로 한다"는 틀렸다. `IS NULL`이 맞다.
- **AND·OR 우선순위로 결과가 다른 SQL 고르기(두 문제)**: 사이트 정답 "괄호로 OR를 먼저 묶은 쪽", "괄호 없이 AND가 먼저 묶인 쪽" → 정답은 이론상 맞지만 해설에 적힌 보기 번호가 표시된 정답 번호와 맞지 않는다(보기 순서가 섞인 것으로 보임). 교재 기준 우선순위는 NOT > AND > OR다.
