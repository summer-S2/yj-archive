# 프론트엔드 배포와 도메인 연결 — 처음부터 끝까지

배포를 직접 해 본 적 없는 상태에서 정리한 기록.
"내가 짠 React 코드가 어떻게 도메인 주소로 열리고, API 서버와는 어떻게 연결되는가"를 처음부터 따라가고,
마지막에 **하나의 앱에 도메인 두 개를 연결하는 방법**까지 다룬다.

> 표기 규칙: `<...>` 는 프로젝트마다 다른 값으로 바꿔서 사용
> - `www.example.com`, `api.example.com` 처럼 `example.com` 이 들어간 주소는 설명용 예시 도메인
> - React + Vite 로 만든 SPA 기준. 다른 번들러(webpack, CRA)도 흐름은 같다
> - 특정 클라우드 제품 이름은 "이런 종류가 있다"는 예시일 뿐, 실제 사용 구성과는 무관

---

## 한눈에 보기

```
[개발자]                               [인프라]                           [사용자]

 소스 코드                                                                브라우저 주소창
    │ npm run build                                                      www.example.com
    ▼                                                                         │
 dist/ (정적 파일)  ── 업로드 ──▶  정적 파일 저장소 / 웹 서버  ◀── 요청 ──── DNS 조회
  ├ index.html                     (+ CDN, HTTPS 인증서)                      │
  └ assets/*.js, *.css                     │                                  ▼
                                           └──── 파일 응답 ─────────▶  화면 그림 (JS 실행)
                                                                              │
                                    API 서버  ◀────────── fetch ──────────────┘
                                 api.example.com
```

| 단계 | 한 줄 요약 | 주로 누가 |
|---|---|---|
| 1. 빌드 | 소스 코드를 브라우저가 읽을 수 있는 **정적 파일**로 변환 | 프론트 |
| 2. 업로드(배포) | 그 파일을 인터넷에 열린 **저장소나 웹 서버**에 올림 | 프론트(CI) / 인프라 |
| 3. 도메인 연결 | **DNS** 로 도메인 이름을 그 서버 주소에 연결 | 인프라 |
| 4. HTTPS | 도메인용 **인증서**를 붙임 | 인프라 |
| 5. 라우팅 설정 | 어떤 경로로 와도 `index.html` 을 주도록(SPA fallback) | 인프라 + 프론트 확인 |
| 6. API 연결 | 브라우저에서 실행된 JS 가 **API 서버**를 호출 | 프론트 + 백엔드 |

핵심은 **프론트 코드는 결국 파일 몇 개**라는 것. 서버에서 "실행"되는 게 아니라, 서버는 파일을 **건네주기만** 하고 실행은 **사용자 브라우저**에서 일어난다.

## 1. 용어부터

| 용어 | 뜻 | 비유 |
|---|---|---|
| **도메인** | `www.example.com` 같은 사람이 읽는 이름 | 가게 상호 |
| **IP 주소** | 서버의 실제 네트워크 주소 (`<IP 주소>`) | 가게 실제 번지수 |
| **DNS** | 도메인 → IP(또는 다른 도메인)로 바꿔 주는 전화번호부 | 상호로 번지수 찾기 |
| **호스트(host)** | 요청을 받는 대상 이름. 웹에서는 보통 도메인 그 자체. `window.location.hostname` 이 이 값 | 손님이 말한 가게 이름 |
| **오리진(origin)** | `프로토콜 + 호스트 + 포트`. 둘 다 https 라도 `www.example.com` 과 `api.example.com` 은 호스트가 달라서 **다른 오리진** | 같은 건물이라도 호수가 다르면 다른 가게 |
| **정적 파일** | 요청할 때마다 내용이 안 바뀌는 파일 (html, js, css, 이미지) | 미리 찍어 둔 전단지 |
| **웹 서버** | 요청을 받아 파일을 돌려주는 프로그램 (예: nginx) | 카운터 직원 |
| **CDN** | 전 세계 곳곳에 파일 복사본을 두고 가까운 곳에서 주는 서비스 | 지점마다 전단지 비치 |
| **인증서(TLS)** | HTTPS 를 가능하게 하는 증명서. **도메인마다** 필요 | 사업자 등록증 |
| **리버스 프록시** | 요청을 받아 뒤쪽 다른 서버로 넘겨주는 중간 서버 | 접수처가 담당 부서로 연결 |

## 2. 빌드: 코드가 파일이 되기까지

```bash
npm run build      # vite build
```

```
dist/
├── index.html                    # 거의 빈 HTML. <div id="root"> 와 JS·CSS 링크만 있음
└── assets/
    ├── index-3f9a1c.js           # 우리가 짠 모든 컴포넌트·라우터·라이브러리가 묶인 번들
    ├── index-b72e40.css
    └── logo-91ad0f.png
```

알아 둘 것:

- **SPA 는 `index.html` 하나**다. `/home`, `/login` 같은 화면은 파일로 따로 있지 않다. JS 안의 라우터가 주소를 보고 그때그때 그린다.
- 파일명의 해시(`3f9a1c`)는 **내용이 바뀌면 같이 바뀐다.** 캐시 문제를 피하는 장치다. (8장)
- **환경변수는 빌드할 때 코드에 박힌다.** `import.meta.env.VITE_API_URL` 은 실행 중에 읽는 게 아니라, 빌드 시점 값이 문자열로 치환돼 번들에 들어간다.
  - 그래서 개발 / 스테이징 / 운영 환경마다 **따로 빌드**하는 게 보통이다.
  - 같은 빌드를 여러 환경에 쓰고 싶으면, 런타임에 읽는 설정 파일(`/config.json`)을 따로 두거나 `window.location.hostname` 으로 분기한다.
- 프론트 번들에 들어간 값은 **누구나 볼 수 있다.** 비밀 키는 절대 넣지 않는다.

## 3. 파일을 어디에 올리나

정적 파일만 건네주면 되므로 방법은 여러 가지다. 회사마다 다르니 "우리 회사는 어떤 방식인지"를 인프라 담당에게 먼저 확인한다.

| 방식 | 구조 | 예시 | 특징 |
|---|---|---|---|
| **A. 정적 저장소 + CDN** | 파일 저장소에 `dist/` 업로드 → CDN 이 그 앞에서 응답 | 클라우드 오브젝트 스토리지 + CDN | 서버 관리 없음. 요즘 가장 흔함 |
| **B. 웹 서버 직접 운영** | 서버(VM·컨테이너)에 nginx 를 띄우고 `dist/` 를 그 폴더에 둠 | nginx, Apache | 설정 자유도 높음. 서버 관리 필요 |
| **C. 배포 플랫폼** | 레포를 연결하면 빌드·업로드·도메인·인증서까지 자동 | 프론트 전용 호스팅 서비스 | 가장 쉬움. 설정은 플랫폼 방식대로 |
| **D. 컨테이너 이미지** | nginx + `dist/` 를 Docker 이미지로 만들어 쿠버네티스 등에 배포 | | B 를 이미지로 포장한 것. 앞단에 로드밸런서·Ingress |

어느 방식이든 공통으로 필요한 설정은 같다:

1. 도메인 연결 (4장)
2. HTTPS 인증서 (7장)
3. SPA fallback (5장)
4. 캐시 정책 (8장)

### 방식 B 예시: nginx 설정 한 장으로 보기

```nginx
server {
    listen 443 ssl;
    server_name www.example.com;            # 이 이름으로 온 요청을 이 블록이 받음

    ssl_certificate     <인증서 경로>;
    ssl_certificate_key <인증서 키 경로>;

    root <배포 폴더>;                         # dist/ 내용을 여기에 둠

    # SPA fallback: 파일이 없으면 index.html 을 줌 (5장)
    location / {
        try_files $uri /index.html;
    }

    # index.html 은 매번 새로 받게 (8장)
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # 해시 붙은 파일은 오래 캐시 (8장)
    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    # 같은 도메인의 /api 로 온 요청은 API 서버로 넘김 (6장 방법 2)
    location /api/ {
        proxy_pass <API 서버 내부 주소>;
    }
}
```

방식 A·C 를 써도 화면 이름만 다를 뿐 위 항목을 각각 설정하는 메뉴가 있다.

## 4. 도메인 연결: DNS

사용자가 주소창에 `www.example.com` 을 치면 브라우저는 먼저 DNS 에 "이 이름의 주소가 뭐야?"를 묻는다.

| 레코드 | 하는 일 | 예 |
|---|---|---|
| **A** | 도메인 → IP 주소 | `www.example.com` → `<IP 주소>` |
| **CNAME** | 도메인 → **다른 도메인** (별명) | `www.example.com` → `<CDN이 준 주소>` |
| **TXT** | 소유 확인용 문자열 등 | 인증서 발급할 때 도메인 주인인지 확인 |

- CDN·플랫폼을 쓰면 보통 **CNAME** 으로 "이 도메인은 CDN 주소로 가"라고 연결한다.
- DNS 를 바꾸면 전 세계에 퍼지는 데 시간이 걸린다(TTL). 바로 안 보여도 잠깐 기다린다.
- **DNS 연결만으로는 부족하다.** 받는 쪽(웹 서버·CDN)도 "이 도메인 이름으로 온 요청을 내가 받겠다"고 등록해야 한다.
  - nginx: `server_name`
  - CDN: "대체 도메인(alternate domain)" 같은 항목
  - 이게 빠지면 DNS 는 맞는데 에러 페이지나 엉뚱한 사이트가 뜬다.

확인 명령:

```bash
nslookup www.example.com     # 이 도메인이 어디로 연결되는지
dig www.example.com +short
```

## 5. SPA fallback: 새로고침하면 404 가 나는 이유

서버 입장에서 보면:

```
GET /                  → index.html 있음 → 200 ✅
GET /assets/index.js   → 파일 있음        → 200 ✅
GET /home              → home 이라는 파일이 없음 → 404 ❌
```

앱 안에서 버튼으로 `/home` 으로 가는 건 **JS 가 주소만 바꾼 것**이라 서버에 요청이 안 간다. 그런데 `/home` 에서 **새로고침**하거나 링크로 바로 들어오면 브라우저가 서버에 `/home` 을 요청하고, 그런 파일은 없다.

해결: **"없는 경로는 전부 `index.html` 을 줘라"**. 그러면 `index.html` → JS 로드 → 라우터가 `/home` 을 보고 그림.

| 방식 | 설정 |
|---|---|
| nginx | `try_files $uri /index.html;` |
| CDN | 403·404 에러 응답을 `/index.html` + 200 으로 바꾸는 설정 |
| 플랫폼 | rewrite 규칙 `/* → /index.html` |

> 이걸 안 해 두면 "개발할 땐 됐는데 배포하니 새로고침하면 404" 가 생긴다. 새 도메인을 붙일 때마다 같이 확인한다.

## 6. API 서버와의 연결

여기서 헷갈리기 쉬운 점: **프론트 서버와 API 서버는 직접 대화하지 않는다.** 대화는 **사용자 브라우저**가 한다.

```
1) 브라우저 ──GET──▶ 프론트 서버   : "화면 파일 주세요"   → index.html, js
2) 브라우저에서 JS 실행
3) 브라우저 ──fetch─▶ API 서버     : "데이터 주세요"      → JSON
```

그래서 API 를 부르는 방법은 두 가지다.

### 방법 1. API 도메인을 직접 호출 (+ CORS)

```ts
const API_URL = import.meta.env.VITE_API_URL;   // <API 서버 주소> (예: api.example.com 의 https 주소)
fetch(`${API_URL}/users/me`, { credentials: 'include' });
```

- 화면은 `www.example.com`, API 는 `api.example.com` → **오리진이 다르다.**
- 브라우저는 보안상 다른 오리진 호출을 기본으로 막는다. API 서버가 "이 오리진은 허용"이라고 응답 헤더로 알려 줘야 통과한다. 이게 **CORS**.
  - `Access-Control-Allow-Origin: <화면 오리진>` (예: www.example.com 의 https 주소)
  - 쿠키를 같이 보내면 `Access-Control-Allow-Credentials: true` 도 필요하고, Origin 에 `*` 를 쓸 수 없다.
- CORS 설정은 **API 서버(백엔드·인프라)** 쪽 일이다. 프론트는 "이 오리진 추가해 주세요"라고 요청한다.
- 개발자도구 콘솔에 `blocked by CORS policy` 가 뜨면 대부분 이것.

### 방법 2. 같은 도메인의 `/api` 로 호출 (리버스 프록시)

```ts
fetch('/api/users/me');    // 화면과 같은 오리진
```

- 프론트를 주는 서버(또는 CDN)가 `/api/*` 요청만 **뒤쪽 API 서버로 넘겨준다.** (3장 nginx 예시의 `location /api/`)
- 브라우저 입장에선 같은 오리진이라 **CORS 가 필요 없다.** 쿠키 다루기도 쉽다.
- 대신 인프라 설정이 하나 더 생긴다.

| | 방법 1 직접 호출 | 방법 2 같은 도메인 프록시 |
|---|---|---|
| 프론트 코드 | API 전체 주소 필요 (환경변수) | 상대경로 `/api/...` |
| CORS | 필요 | 불필요 |
| 쿠키 | 도메인·SameSite 설정 신경 써야 함 | 단순 |
| 인프라 | API 서버 CORS 설정 | 프록시 경로 설정 |

### 개발 서버에서는?

`npm run dev` 로 띄운 `localhost:5173` 도 API 와 오리진이 다르다. 그래서 Vite 의 `server.proxy` 로 방법 2 를 흉내 내는 경우가 많다.

```ts
// vite.config.ts
export default defineConfig({
  server: {
    proxy: { '/api': { target: '<개발 API 서버 주소>', changeOrigin: true } }
  }
});
```

이건 **로컬 개발용**일 뿐, 배포 후에는 동작하지 않는다. 운영에서 같은 효과를 내려면 3장처럼 서버·CDN 에 프록시를 설정해야 한다.

### 쿠키와 도메인

- 쿠키는 **도메인에 묶인다.** `api.example.com` 이 준 쿠키는 기본적으로 그 도메인 요청에만 붙는다.
- `Domain=.example.com` 으로 주면 하위 도메인끼리 공유된다. 하지만 **완전히 다른 도메인**(`example.com` ↔ `other.net`)끼리는 공유할 방법이 없다.
- 그래서 도메인을 새로 붙이면 "로그인 상태가 안 보인다" 문제가 자주 생긴다. (10장)

## 7. HTTPS 인증서

- 인증서는 **도메인 이름별로** 발급된다. `www.example.com` 인증서로 `new.example.com` 을 열면 브라우저가 경고를 띄운다.
- 하위 도메인 전체를 덮는 **와일드카드 인증서**(`*.example.com`)도 있다. 다른 최상위 도메인은 안 덮는다.
- CDN·플랫폼은 대부분 인증서 발급·갱신을 자동으로 해 준다. 직접 운영하면 만료일 관리가 필요하다.
- 발급할 때 "이 도메인의 주인인지"를 DNS 레코드(TXT·CNAME)로 확인하는 경우가 많다. 그래서 **DNS 와 인증서는 보통 같이 요청**한다.

## 8. 캐시: 배포했는데 예전 화면이 나올 때

| 파일 | 캐시 정책 | 이유 |
|---|---|---|
| `index.html` | **캐시하지 않음** (`no-cache`) | 새 배포의 새 JS 파일명을 가리키므로 항상 최신이어야 함 |
| `assets/*-해시.js·css` | **아주 길게** (1년, `immutable`) | 내용이 바뀌면 파일명이 바뀌므로 같은 이름은 영원히 같은 내용 |

- 이 두 가지만 지키면 "배포했는데 사용자 화면이 안 바뀐다" 가 거의 없다.
- CDN 을 쓰면 CDN 에도 복사본이 남는다. 배포 후 **캐시 무효화(invalidation)** 를 `index.html`(또는 전체)에 걸어 준다. 보통 배포 파이프라인 마지막 단계에 넣는다.
- 배포 직후 열려 있던 탭은 예전 JS 로 동작 중이다. 그 상태에서 지연 로딩하는 화면을 열면 예전 파일이 이미 지워져 에러가 날 수 있다. 이전 배포 파일을 한동안 남겨 두거나, 로딩 실패 시 새로고침 유도로 대응한다.

## 9. 배포 파이프라인 (CI/CD)

사람이 손으로 파일을 올리지 않고, 보통 이렇게 자동화돼 있다.

```
코드 push / merge
   │
   ▼
CI 가 실행
   ├─ 의존성 설치         npm ci
   ├─ 검사                lint, test
   ├─ 빌드                환경에 맞는 환경변수로 npm run build
   ├─ 업로드              dist/ → 저장소·서버 (또는 Docker 이미지 빌드·배포)
   └─ 캐시 무효화          CDN 의 index.html
   │
   ▼
배포 완료 → 도메인으로 확인
```

- 환경별(개발·스테이징·운영)로 **빌드 → 올리는 곳 → 도메인**이 한 세트씩 있는 경우가 많다.
- 처음 맡게 되면 CI 설정 파일(레포의 파이프라인 정의 파일)을 열어 위 단계가 각각 어디 있는지 찾아 보면 구조가 바로 보인다.

## 10. 새 도메인을 붙일 때 할 일과 역할

| 할 일 | 누가 | 내용 |
|---|---|---|
| 도메인 결정·구매 | 기획·인프라 | 하위 도메인이면 구매 불필요 |
| DNS 레코드 | 인프라 | A 또는 CNAME 으로 프론트 서버·CDN 에 연결 |
| 인증서 | 인프라 | 새 도메인 포함해 발급 |
| 받는 쪽 호스트 등록 | 인프라 | nginx `server_name`, CDN 대체 도메인 등 |
| SPA fallback | 인프라 설정, 프론트 확인 | 새 도메인에서도 새로고침 시 404 없게 |
| 어떤 빌드를 연결할지 | **프론트가 정해서 요청** | 기존 빌드 그대로? 새 빌드? (11장) |
| CORS 허용 오리진 추가 | 백엔드·인프라 | 방법 1 을 쓰는 경우 |
| 외부 서비스 리턴·콜백 URL 등록 | 해당 서비스 담당 | 본인인증, 소셜 로그인, 결제 등 |
| 쿠키 도메인 | 백엔드 | 새 도메인에서 로그인 유지가 필요하면 |
| 앱 코드 대응 | 프론트 | 호스트별 분기, 절대 URL 정리 |

> "도메인 요청은 프론트가 해야 하나?" → **그 화면을 배포·운영하는 쪽이 프론트라면 요청 주체가 프론트인 게 자연스럽다.** 단, 무엇을 요청하는지는 정확해야 한다. 위 표의 인프라 항목을 **한 번에** 정리해서 요청하면 왔다 갔다 할 일이 줄어든다.

### 인프라 요청서 예시

```
[요청] <신규 도메인> 연결

- 연결 대상: 기존 <서비스> 프론트와 같은 빌드 산출물 (새 빌드 아님)
- DNS: <신규 도메인> → 기존 프론트 CDN/서버와 같은 곳
- 인증서: <신규 도메인> 포함
- 호스트 등록: 기존 CDN/서버에 <신규 도메인> 추가
- SPA fallback: 기존과 동일하게 모든 경로 → index.html
- 리다이렉트·경로 재작성: 없음 (앱에서 처리)
- 같이 필요한 것: API CORS 허용 오리진에 <신규 도메인> 오리진(https) 추가
```

## 11. 하나의 앱에 도메인 두 개 연결하기

### 11-1. 무엇이 "하나의 앱"인가

배포 관점에서 앱 하나 = **빌드 산출물(`dist/`) 한 벌**이다.
도메인 두 개를 그 한 벌에 연결하는 건 생각보다 단순하다. **받는 쪽에 호스트 이름을 두 개 등록**하면 된다.

```nginx
server {
    server_name <기존 도메인> <신규 도메인>;   # 이름만 하나 더
    root <배포 폴더>;                          # 같은 파일
    location / { try_files $uri /index.html; }
}
```

CDN 이면 대체 도메인에 하나 더 추가하고, 인증서가 두 도메인을 다 덮게 하면 끝이다.

이러면 **두 도메인에서 완전히 똑같은 `index.html` 과 JS 가 내려간다.** 서버는 구분하지 않는다. 구분은 **앱이** `window.location.hostname` 을 보고 한다.

### 11-2. 원하는 모습별 선택지

상황: 기존 앱 안에 `/sub/...` 로 분리해 둔 화면 묶음이 있고, 신규 도메인에서는 이 묶음만 보여 주고 싶다.
두 도메인의 경로가 1:1로 대응하지는 않는다. 예를 들어 신규 도메인의 첫 화면 `/` 는 `/sub/home` 이 아니라 `/sub/intro` 이고, 이름이 다른 화면도 있다.

| 원하는 것 | 방법 | 누가 | 주소창 |
|---|---|---|---|
| 신규 도메인 접속 시 `/sub` 로 보내기만 | **리다이렉트** `<신규 도메인>/` → `<신규 도메인>/sub/intro` | 인프라 (또는 앱에서 `navigate`) | `/sub/...` 보임 |
| 주소창에 `/sub` 없이, 경로도 따로 | **호스트 기반 라우팅 + 경로 매핑** — 앱이 호스트를 보고 매핑표대로 라우트를 등록 | 프론트 | 매핑표대로 (`/`, `/done` …) |
| 신규 도메인에 하위 묶음 코드만 배포 | **빌드 분리** — 엔트리를 하나 더 만들어 별도 `dist/` 생성 | 프론트 + 인프라 | `/...` |

- **서버 리라이트**(서버가 `/` 요청을 내부적으로 `/sub/intro` 로 바꿔 처리)는 SPA 에는 효과가 없다. 서버는 어차피 `index.html` 만 주고, 라우터는 서버가 바꾼 경로가 아니라 **브라우저 주소창의 경로**를 보기 때문이다.
- `basename` 은 앱이 `<도메인>/우리앱/` 처럼 하위 경로에 **실제로 얹혀** 배포될 때 쓰는 것이라 이 상황엔 맞지 않는다.

### 11-3. "그 폴더 index 만 올리면 되지 않나?" 가 안 되는 이유

소스 폴더 구조와 배포되는 파일 구조는 **다르다.**

```
소스                                빌드 결과
src/                                dist/
├── main.tsx   ← 엔트리 (하나)       ├── index.html    ← 하나
├── App.tsx    ← 라우터              └── assets/
├── pages/                              └── index-3f9a1c.js  ← 전부 하나로 묶임
│   ├── home/
│   └── sub/   ← 하위 묶음 폴더
└── components/  ← 공용 컴포넌트
```

- 빌드하면 `src/pages/sub/` 라는 폴더는 **결과물에 존재하지 않는다.** 모든 코드가 엔트리(`main.tsx`)에서 시작해 번들 하나(또는 몇 조각)로 합쳐진다.
- `sub` 화면은 공용 컴포넌트·라우터·상태관리에 기대고 있어서 떼어 내면 혼자 동작하지 않는다.
- 진짜로 따로 배포하려면 **엔트리 파일을 하나 더 만들고**(`sub-main.tsx` + `sub.html`) 빌드 설정에서 멀티 엔트리로 빌드해야 한다. 이건 사실상 **앱을 하나 더 만드는 것**이고, 배포 대상·파이프라인·도메인 설정도 한 세트 더 생긴다.

그래서 "기존 앱을 재활용하자"는 방향이라면 **같은 빌드 + 도메인 두 개 + 호스트 기반 라우팅**이 맞는 조합이다.

### 11-4. 호스트 기반 라우팅 + 경로 매핑 요약

경로가 1:1이 아니므로 "앞의 `/sub` 를 자르는" 규칙으로는 안 된다. **매핑표 한 장**을 기준으로 둔다.

| 앱 라우트 (기존 도메인) | 신규 도메인 |
|---|---|
| `/sub/intro` | `/` |
| `/sub/verify` | `/verify` |
| `/sub/terms/:type` | `/terms/:type` |
| `/sub/complete` | `/done` |
| `/sub/home` | (노출 안 함) |

```ts
const SUB_HOST_PATHS = [
  { app: '/sub/intro', sub: '/' },
  { app: '/sub/verify', sub: '/verify' },
  { app: '/sub/terms/:type', sub: '/terms/:type' },
  { app: '/sub/complete', sub: '/done' }
];

// 신규 도메인이면 표에 있는 라우트만, 표의 경로로 등록
const routes = isSubHost
  ? SUB_HOST_PATHS.map(({ app, sub }) => ({ ...allRoutes.find((r) => r.path === app)!, path: sub }))
  : allRoutes;

// 이동: 코드는 계속 앱 라우트 경로로 쓰고, 표로 변환
navigate(toPath('/sub/complete'));   // 기존 도메인 '/sub/complete', 신규 도메인 '/done'
```

- 신규 도메인에는 표에 있는 화면만 등록돼 기존 화면과 섞이지 않는다.
- 이동은 `toPath`(앱 경로 → 지금 도메인 경로), 화면 판별은 `toAppPath`(주소창 경로 → 앱 경로)를 거친다.
- 두 도메인의 URL 구조가 달라서 상대경로 이동(`navigate('verify')`)은 쓰지 않는다.
- 인프라에는 **리다이렉트·리라이트 없이 같은 빌드에 연결 + SPA fallback** 만 요청한다.

코드 전체, 엣지 케이스, 테스트는 [호스트 기반 라우팅 문서](../react-router/호스트_기반_라우팅_경로_매핑.md)에 정리했다.

### 11-5. 도메인 두 개일 때 같이 볼 것

| 항목 | 왜 |
|---|---|
| 인증서 | 두 도메인 모두 포함됐는지 |
| CORS | API 허용 오리진에 신규 도메인 추가 |
| 쿠키 | 기존 도메인 쿠키는 신규 도메인에 안 보일 수 있음 (6장) |
| 외부 콜백 URL | 본인인증 등에서 돌아올 주소에 신규 도메인 등록 |
| localStorage·sessionStorage | **오리진별로 따로** 저장됨. 기존 도메인에 저장한 값은 신규 도메인에서 안 보임 |
| 하위 묶음 → 기존 화면 링크 | 신규 도메인엔 기존 라우트가 없음. 기존 도메인 전체 URL 로 보내거나 없앤다 |
| 분석·로그 | 같은 화면이 도메인별로 다른 경로로 집계됨 |
| 검색 노출 | 같은 내용이 두 도메인에 있으면 필요 시 canonical 지정 |

## 12. 배포 후 확인과 문제 찾기

### 확인 순서

1. **DNS**: `nslookup <도메인>` 이 의도한 곳을 가리키는지
2. **HTTPS**: 주소창 자물쇠 → 인증서에 그 도메인이 있는지
3. **첫 화면**: 열리는지, 개발자도구 Network 에서 `index.html` 과 `assets/*.js` 가 200 인지
4. **새로고침**: 하위 경로(`/home` 등)에서 새로고침해도 404 가 아닌지 (SPA fallback)
5. **API**: Network 에서 API 요청이 성공하는지, 콘솔에 CORS 에러가 없는지
6. **로그인·쿠키**: Application 탭에서 쿠키가 생기는지, 요청에 붙는지
7. **최신 배포인지**: `index.html` 이 가리키는 JS 파일명이 이번 빌드 결과와 같은지

### 증상별 원인

| 증상 | 의심할 곳 |
|---|---|
| 사이트에 아예 접속 안 됨 | DNS, 받는 쪽 호스트 등록 |
| 보안 경고 화면 | 인증서에 그 도메인이 없음 |
| 첫 화면은 되는데 새로고침하면 404 | SPA fallback 없음 |
| 흰 화면 + 콘솔에 JS 404 | 에셋 경로(`base` 설정), 업로드 누락, 캐시된 예전 `index.html` |
| `blocked by CORS policy` | API 서버 허용 오리진 |
| 로그인했는데 다음 요청에서 로그아웃 상태 | 쿠키 도메인·SameSite, `credentials: 'include'` 누락 |
| 배포했는데 예전 화면 | `index.html` 캐시, CDN 무효화 안 함 |
| 개발에선 API 되는데 배포 후 안 됨 | 개발용 Vite proxy 에만 기대고 있었음 → 운영 프록시·CORS 설정 필요 |

## 13. 정리

- 프론트 배포 = **빌드한 정적 파일을 인터넷에 열린 곳에 올리고, 도메인을 거기에 연결하는 것.** 실행은 사용자 브라우저에서 한다.
- 도메인 연결은 **DNS + 받는 쪽 호스트 등록 + 인증서** 세 가지가 한 세트다.
- SPA 는 `index.html` 하나라서 **모든 경로 → `index.html`(SPA fallback)** 이 필수다.
- API 서버와는 **브라우저가** 직접 통신한다. 다른 도메인이면 CORS, 같은 도메인 `/api` 프록시면 CORS 불필요.
- 캐시는 **`index.html` 은 안 하고, 해시 파일은 길게.** 배포 후 CDN 무효화.
- 하나의 앱에 도메인 두 개 = **같은 빌드에 호스트 이름 두 개 등록.** 서버는 구분하지 않고, 앱이 `hostname` 으로 구분한다.
- 소스 폴더 하나만 떼어 배포할 수는 없다. 떼려면 빌드 엔트리를 분리해야 하고, 그건 새 앱을 만드는 일이다.
- 새 도메인 요청은 **DNS·인증서·호스트 등록·fallback·CORS·콜백**을 한 번에 정리해서 보낸다.
